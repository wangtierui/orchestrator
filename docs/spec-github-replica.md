## 2. 五条硬纪律

1. **没有 spec 不动手**：每页先有 `spec-<page>.json`（元素 + 尺寸 + 状态 + 断点）。
2. **门禁断言来自 spec**：禁止"我觉得应该 32px"；失败输出「基线值 vs 当前值」。
3. **一次一页**：复制模板可以，但必须逐项跑该页 spec 比对，不跑不算完成。
4. **视觉只许令牌或 Primer 类**：禁字面色值、禁 `font-size/font-weight/font-family` 字面量。
5. **"一致"必须附三件事**：测了什么、没测什么、怎么测的。

### 4.5 登录态「完整样式链」实测（2026-11-05，补上缺失的 90%）

> 采集工具：`tools/gh_ui_full.py`（按语义角色取代表元素，每元素抓**全部 computed style + 6 层祖先链 + 文本宽度**）。
> 产物：`reports/github-baseline/full-{issues,pulls,commits,contributors}.json`。

**① 字体与行高（此前完全没采，是"数字对、观感不对"的主因之一）**

| 项 | GitHub 实测 | 我们现行 | 影响 |
|---|---|---|---|
| font-family | **`"Mona Sans VF", -apple-system, BlinkMacSystemFont, …`** | `-apple-system, BlinkMacSystemFont, "Segoe UI", …` | 字形、字宽不同 → 同样 14px 文字宽度差 5~10% |
| font-size / line-height | **14 / 21**（比例 1.5） | 14 / 20 | 行高少 1px，累加到 30 行差 30px |
| box-sizing | **border-box**（全局） | 混用 | 同 32px 高，内容区差 2~4px |
| 根字号 | 16 | 16 | 一致 |

**② 搜索框的真实构成（难点：视觉在外层，输入框本身是裸的）**

```
外层 DIV.Box_2 (1047×30, 边框与圆角在此)
  └ INPUT (1047×30, padding 0, border 0, bg 透明, font 14/21)
```

实测：`input` 的 `padding/border/background` 全为 0/透明，**高度 30 由外层 Box 决定**。
→ 我们要复刻时必须把 padding 与边框放在**包装层**，否则 30 会变成 30+2。

**③ 按钮构成（公式已用真实元素验证）**

| 类型 | 实测 | 构成 |
|---|---|---|
| 文字按钮（Author） | **89×32** | padding `0 12` + border 1px（**颜色透明**）+ 文字 |
| 文字按钮（Labels） | 85×32 | 同上 |
| 搜索按钮 | 191×32 | padding `0 12` + border 1px `#d1d9e0` + radius 6 |
| 图标按钮 | **32×32** | padding 0 + border 1px + radius 6 |
| 小图标按钮 | **20×32** | padding `4 6` |
| 徽标 Counter | **37×18**「2.9k」 | 文字 22.6 + `12` + `2` = 36.6 ≈ 37 ✅ |

> 结论：**宽 = 文字 + 24 + 2**（padding 12×2 + border 1×2），高固定 32；徽标高 18、padding `2 6`、radius 20。
> 另：筛选按钮（Author/Labels…）**边框颜色是透明的**——看起来无边框，但占据 2px 宽度。

**④ 侧栏条目 / 行 / 标题**

| 元素 | 实测 | 构成 |
|---|---|---|
| 侧栏 ActionList 项 | **223×32** | padding `6 8` + radius 6 + font 14/21 |
| commits 行 | 1237×71 | `display:grid` + border-bottom 1px + radius 6 |

**⑤ 这条数据解决了什么问题**

用户指出的"采集粒度不够"——此前每控件 8 个属性，导致：
- 只知道按钮 90 宽，不知道 90 = 文字 64 + 24 + 2 → 抄了 90 却做出 88/92；
- 只知道行高 32，不知道 32 = 6+21+... → 自己排成 30 或 34；
- 不知道字体族不同 → 文字宽度天然差 5~10%。

现在这五项（font-family / line-height / box-sizing / padding+border 归属层 / 祖先背景）全部有实测值，可直接施工。

### 4.6 左侧栏重新设计（现状"无业务含义"，必须重做）

**问题诊断**

| 现状 | 为什么没有业务含义 |
|---|---|
| 13 个模块同时出现在**顶部页签**和**左侧栏** | 两处导航重复，侧栏不提供新信息 |
| 侧栏条目是「搜索 / 列表 / 分页」 | 这是**技术锚点**，不是业务维度；用户看不出"我在这里能做什么" |
| 底部没有折叠与反馈入口 | 用户无法收起侧栏腾出宽度，也无处反馈 |

**GitHub 的侧栏到底是什么（实测）**

GitHub 侧栏是**页面语义相关的导航/筛选**，不是全站模块：
- Code 页 → 文件树；Issues 页 → 按 Issues / Assigned / Created by / Mentioned 等**业务切片**；
- Settings 页 → **分组导航**（分组标题 12px/600 muted，条目 32 高）；
- 底部固定两个动作（实测）：

| 项 | 实测 | 说明 |
|---|---|---|
| **Feedback** | 223×32 @y=916，`padding 6 8`，radius 6 | 反馈入口，位于条目流末尾 |
| **Collapse sidebar** | 223×32 @y=952，同规格 | 折叠侧栏，最底部 |

**新设计：侧栏 = 本页业务切片 + 底部固定动作**

```
┌─ 侧栏 239 ────────────┐
│ ▸ 业务切片（本页）      │  ← 每页不同，随页切换
│   ● 全部              │  ← 选中：15% 底 + 左 4px #0969da
```

**验收**
1. 每页侧栏条目 ≥3 条且**全部是业务切片**（不得出现"搜索/列表/分页"）；

### 5.7 下拉选择（原生 select 与自绘面板必须分开看）

**先回答"为什么不复刻展开态"这个问题——原表述是错的，需要拆成两类：**

| 类别 | 展开态由谁绘制 | 能否采集 | 处置 |
|---|---|---|---|
| **原生 `<select>`** | 操作系统（Windows 弹出层） | ❌ DOM 里没有，`getComputedStyle` 拿不到，截图也只在你本机可见 | **不复刻**：只对齐闭合态（高 32 / 1px 边 / radius 6 / 右内 24 放箭头），展开态交给系统——GitHub 自己也一样，这是浏览器行为，不是设计差异 |
| **自绘面板**（GitHub 的 Author / Labels / Sort / 状态切换） | 页面自己（`ActionMenu` / `SelectPanel`） | ✅ 可采（面板宽 320、行高 32、hover `.1`、选中 `.15`、圆角 12） | **必须复刻**：§5.6 已给规格 |

> 结论：**"不复刻展开态"只适用于原生 select**，不能套到 GitHub 的筛选面板上——后者的展开态是页面 DOM，必须逐项对齐。
> 我们的筛选面板已经是自绘（`.lv-pop`），所以要走右列口径，不是"交给系统"。

**原生 select 闭合态规格**：高 32、1px `#d1d9e0`、radius 6、`padding-right 24`（箭头）、字号 14/21。

| # | 规则 | 实测依据 | 状态 |

### 6.10 治理审计 `governance` ↔ Actions（**重新设计**）

**先说问题（用户反馈"两个列表不知道有什么意义"）**

| 现状 | 为什么无效 |
|---|---|
| 运行记录：run_id · 开始 · 结束 · 状态 | 用户不知道**这次运行做了什么、比上次好在哪**；run_id 是机器标识，人读不出信息 |
| 审计日志：时间 · 操作者 · 动作 · 对象 · 字段 | 只有"谁在何时点了什么"，**没有 before→after**，无法判断"这次改动对不对" |
| 两表并列 | 没有主次，用户不知道先看哪个；也无法回答"某次运行导致了哪些数据变更" |

**重新设计：三层结构（回答三个问题）**

```
① 一眼结论（指标条）：最近 24h 运行 6 次 / 失败 1 次 / 平均 52 分钟 / 审计 128 条
② 运行时间线（主视图，左 60%）：每次运行一行，点开看步骤
③ 变更台账（右 40%）：按对象聚合的字段级差异（before → after）
```

**① 指标条（4 格，回答"最近健不健康"）**

| 指标 | 口径 | 数据 |
|---|---|---|
| 近 24h 运行数 / 失败数 | 按 `started_at` 过滤 | `runs[]` |
| 成功率 | 成功 / 总数 | 同上 |
| 平均耗时 | `finished_at − started_at` 中位数 | 同上 |
| 审计条数（近 24h） | `audit[]` | 同上 |

**② 运行时间线（主视图，替代"运行记录表"）**

| 列 | 内容 | 说明 |
|---|---|---|
| 状态点 | 绿/红/灰 圆点 | 一眼看成功失败 |
| 运行 | `RUN-20261104-060011` **缩短为 `11-04 06:00`** + 悬浮显示全 id | 人类可读优先 |
| 结果 | `42 步 · 35 成功 · 7 失败` | 步数与失败数 |
| 耗时 | `56 分钟` | 相对可读 |
| 失败摘要 | 失败步骤名前 2 个 + `+5` | 点开看全部 |
| ▸ | 展开 → **步骤明细表**（步骤 · 状态 · 耗时 · 错误摘要） | 这是现在完全缺的 |

**③ 变更台账（替代"审计日志表"，回答"改了什么"）**

| 列 | 内容 | 说明 |
|---|---|---|
| 时间 | `11-04 06:12` | — |
| 对象 | 政策法规「农业保险条例」 | **显示人类可读名称**（现在只显示 `target_key`） |
| 字段 | `timeliness_status` | — |
| 变更 | **`valid → amended`** | **before → after，现在完全没有** |
| 操作者 | `tools.run_production_refresh` | 悬浮显示完整路径 |

**④ 两表联动**
- 点某次运行 → 变更台账过滤为该 `run_id` 产生的审计；
- 点某个对象 → 跳到对应页面并高亮该行。

**⑤ 筛选与搜索**
- 时间范围（24h / 7 天 / 30 天）；状态（成功/失败）；操作者；对象类型；
- 搜索匹配：运行 id、对象名、字段、操作者。

**⑥ 空态**
- 无运行：「尚未运行过；点此触发一次」；
- 无审计：「本条链未产生数据变更」；
- 无权访问：「治理库未启用」（`status.enabled=false`）。

**验收清单**
1. 指标条 4 格有值，且成功数与时间线一致；
2. 点运行行能展开步骤明细（含失败步骤与耗时）；
3. 变更台账显示 `before → after`（至少 1 条真实记录）；
4. 点运行行后台账被过滤（条数变化）；
5. 三种空态文案可复现。

## 附录 C：图表清单（`web/assets/charts.js` 实测导出）

`charts.js` 是**唯一**图表出口，只导出 **8 种**：

| `liquid` | echarts-liquidfill | 指标·SLI/SLO 达标率（L2330） | 高 **170**，液位=达标率 |
| `rose` | pie + roseType | 指标·主题分布（L2344） | 高 **320**，半径=条数 |
| `sankey` | ECharts sankey | 数据流转（L2122） | 节点按层排布 |
