# ADR-0011 依赖治理与供应链安全（锁定 · 漏洞扫描 · SBOM · 登记簿）

- **状态**：已采纳（2026-10-15，W5 首批落地）
- **关联方案**：《项目最优重构方案》§13.2（依赖管理与供应链安全，P0）、§9.2（ci_check 作业）、§6.6 W5 出口判据
- **决策者**：项目负责人（单人团队；门禁与流程为决策载体）

## 背景

仓内依赖治理此前只有三块相邻基础：`pyproject.toml` 声明（含 C5「死声明清零」正面范式）、
`config/ocr.yaml` 的 Tesseract 路径、§4.5 的 MCP SDK pin 与网络可达核实。缺的是**锁**、
**漏洞扫描**、**SBOM** 与**新增依赖的准入纪律**。实测后果有三：

1. **影子依赖**：`pytest-timeout`（pytest 入口 `--timeout=900`）、`bandit`、`pip-audit`
   长期在用却从未在 `pyproject` 声明——环境里装了、仓里没记，**换机即失配**，审计无从下手。
2. **锁的缺失**：`pip freeze` 的结果从未入库，"跑通的机器"与"锁定的机器"是同一台，
   一旦换机或重建环境，依赖树不可复现，CVE 扫描也无基线可比。
3. **编码防护的幻觉**：跑 bandit 得到的 444 项里绝大多数是噪音（assert/异常吞咽），
   但其中**藏着两个真问题**：① 编排器用裸 `python` 自重启（PATH 可能命中另一解释器）；
   ② `vector_store` 的 SQL 串带无插值 f 前缀。**没有分层的扫描等于没有扫描**。

## 决策

### 1. 锁定：`requirements.lock` 入库（零新工具链）

- 由 `tools/gen_lock.py` 从 `pip freeze --all` 生成（含间接依赖），稳定排序 ⇒ 同环境
  重复生成 diff 为空，可评审。
- **锁文件强制纯 ASCII**：第三方工具（pip-audit）以 **locale 编码**读 requirements 文件，
  含 CJK 的锁在 GBK/cp936 环境下直接 `UnicodeDecodeError`（实测 rc=1 且**零行输出**——
  若不察，会被误读成"扫描通过、无漏洞"，这是**比不扫更坏**的失效模式）。
  散文与理由一律放 ADR / 文档，不放锁。
- 剔除本地可编辑、路径与 VCS 直连条目（不可复现）；升级依赖 = 锁文件的可评审变更。

### 2. 漏洞扫描：`pip-audit` 零容忍 high/critical（`gate_dependency_audit` 判据 D4）

- high/critical ⇒ **FAIL**；medium 及以下 ⇒ 披露。
- **工具缺失或网络不可达 ⇒ SKIP 披露，不判 FAIL**：把网络故障误报成供应链问题会训练
  团队忽略该告警（告警疲劳等于没有告警）。子进程强制 `PYTHONUTF8=1` 并有界超时 180s。

### 3. SBOM：由锁直生 CycloneDX 1.5（`tools/gen_sbom.py`）

- **不引 syft**：其未安装、需外部二进制、且扫描整个文件系统（含 `external/` 的 13GB
  权重与 virtualenv），而依赖证据的**权威来源就是锁**。lock 直生可离线、可复现
  （相同 lock ⇒ 逐字节相同 SBOM），且 SBOM↔lock 的对应关系可用 sha256 直接断言（判据 D5）。
- 复发条件：需要**文件级**成分（容器镜像内的二进制/权重文件清单）时再引 syft。

### 4. 直接依赖登记簿：`config/dependency_policy.yaml`（判据 D3，双向断言）

每个直接依赖绑定「ADR 编号 或 why」，并做**双向**断言：pyproject 有而登记簿没有 =
**影子依赖**（FAIL）；登记簿有而 pyproject 没有 = **死登记**（FAIL）。
新增依赖 = 三处同一变更（登记簿 + pyproject + 重生成 lock/SBOM）。

非 pip 安装的语义工具（DeepKE / SignalGraph / docreader / ParadeDB）单列 `non_pip`，
理由是"为何不在 Python 依赖里"，避免审计时找不到解释。

### 5. SAST 分层：`bandit` 类级跳过 + 机器对冲（判据 D7）

- 逐处核实后做**类级跳过**（每条附理由与**复发条件**）：B101/B102/B103/B105/B110/B112/
  B314/B310/B311/B324/B404/B405/B406/B603/B607/B608。未列出的检查项保持阻断。
- `B607`（子进程部分路径）跳过的同时，用**判据 D7**（AST 断言：子进程 argv 的可执行位
  不得是裸 `python`/`py`）机器守护其唯一真实风险子类 —— 即"类级跳过 + 精确对冲"，
  而不是"整类静默"。
- 排除项（退役层/refactor/tests 等）写在**命令行** `--exclude`：实测 bandit 的 pyproject
  解析器只认 `skips`，`exclude` 被静默忽略（配置写了却不生效是最坏的形态，已在配置里
  写明"不视为生效配置"）。

### 6. CI 接线

`tools/ci_check.py` 新增三作业：`lock`（`gen_lock --check`）、`sbom`（`gen_sbom --check`）、
`bandit`（SAST）；漏洞扫描在门禁侧随 `gates` 作业执行。全部作业在工具缺失时自报跳过，
不产生假红。

## 后果

**正面**

- 依赖树可复现、升级可评审、CVE 有基线、SBOM 可交付（监管"说得出用了什么"的机器证据）。
- 新增依赖必须回答"为什么、谁批准"——把依赖评审从口头习惯变成门禁。
- bandit 从"444 条噪音"变为"0 问题 0 告警"的**可用**作业，并当场挖出两个真问题。

**代价 / 已知局限**

- 锁需随依赖变更同步提交（本仓单人维护，成本可接受；换来换机可复现）。
- `pip-audit` 依赖网络：离线环境下漏洞维度不可见（门禁显式 SKIP 并披露，不静默）。
- SBOM 只覆盖 **Python 包成分**，不含权重文件哈希（权重体积大、逐文件哈希成本高；
  其来源与许可状态由 `semantic_tools.json` 登记）。
- 类级跳过是**有意的权衡**：换取"作业可用"，代价是这些类的新增真实问题不会被 bandit
  捕获 —— 故每条跳过都写明复发条件，且对风险最高的一类（B607）加了机器对冲。

## 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| uv / poetry 迁移 | 单机无分发需求；引入新工具链换取的 lock 能力，`pip freeze` 已足够（权衡 #19） |
| 直接从 HF Hub 加载模型 | `trust_remote_code=True` 会执行**Hub 侧代码**；改为离线迁入本地已审核目录（§7.10 通道）后风险面收敛（复发条件已写死） |
| 保留 bandit 全部告警 | 444 条低危噪音 ⇒ 作业被习惯性忽略；**告警疲劳等于没有告警** |
| 把依赖声明写进文档而非登记簿 | 文档不参与 CI，无法阻断；影子依赖会再次发生 |
