# ADR-0012 SLI/SLO 与错误预算、灾难恢复（RTO/RPO）、明确不做清单

- **状态**：已采纳（2026-10-15，W5 第二批落地）
- **关联方案**：《项目最优重构方案》§13.3（可观测性，P1）、§13.4（灾备与业务连续性，P0）、§13.5（数据质量度量，P0）、§13.12（明确不做清单）
- **决策者**：项目负责人（单人团队；阈值与预算规则的裁决权在人，机器只负责度量与告警）

## 背景

此前可观测性只有「run_id 关联 + 步骤台账 + audit_log + 告警四事件」，缺三样东西：
**SLI/SLO 的量化定义**（多少算好）、**错误预算**（坏到什么程度该停手）、**RTO/RPO**
（出事时先救什么、多久必须恢复）。缺它们的直接后果是：故障复盘只能定性争论
（「最近还行吧」），恢复行动靠临场判断。

## 一、SLI / SLO 与错误预算

### 三个 SLI（唯一事实源 = `config/schedule.yaml` 的 `notify.sli` 段）

| SLI | 定义 | 数据源 | SLO（初值） | 窗口 |
|---|---|---|---|---|
| `sli_chain_success_rate` | 最近 N 次运行中 `failed=0` 的占比 | `run_log`/`run_step` | ≥ 98%（月） | 7 |
| `sli_data_freshness` | 关键产物水位 `age ≤ 族阈值` 的占比（raw 7d/cleaned 10d/clauses 30d/published 30d） | `watermark.produced_at` | ≥ 95% | 7 |
| `sli_gate_pass_rate` | 最近 N 轮 `gates` 全绿占比 | `gate_result` | **100%**（准入门，非渐进指标） | 7 |

- 工具：`tools/check_slo.py`（只读判定 + 快照入 `reports/slo/slo_history.jsonl`）。
  **台账落 `reports/` 而非 `data/run_state/`**：后者整体被 `.gitignore` 忽略（派生状态），
  而 SLI 趋势是**审计证据**（错误预算复盘要用）——与 §7.10 的 reports 分区裁定一致。
- **连续 2 个周期**低于 SLO ⇒ 发 `slo_breach` 告警（防单点抖动误报；事件已登记入
  `NOTIFY_EVENTS` 与 `notify.on`，门禁 S3 双向守护）。
- **错误预算** = 1 − SLO。余额为负 ⇒ 机器**只给建议**（冻结非必需变更），**裁决权在人**
  ——单人团队没有「值班替班」承接 SLO，把它写成自动阻断只会训练团队忽略它。

### 为什么不做 OpenTelemetry

单机脚本链已有 run_id 贯穿 + 步骤台账 + audit_log + 确认台，全链关联可查；OTel 需要常驻
collector 与 exporter，在本场景**无可观测收益**。复发条件：MCP 并发消费方 ≥3 或跨机部署。

## 二、数据质量：DAMA 六维 + 健康度评分

- 工具：`tools/gen_quality_metrics.py`（方案 §13.5）→ `reports/quality/`。
- **不新造检测逻辑**：六维指标全部取自既有机器判据输出（corpus 索引、watermark、
  gate_result、document 表、quarantine 区）；本工具只聚合、评分、比趋势。
- **缺失维度不计入分母**（不以 0 充数）——否则数据源一断，健康度评分就变成谎言。
- 初始**均权**（权重登记在 `QUALITY_WEIGHTS`，改动走本 ADR）。
- 任一维环比劣化 > 10% ⇒ `quality_regression` 提示（事件已登记）。
- **评分只披露不阻断**：质量是渐变指标，用它当准入门会把夜间批处理挡在门外。
- 两处口径陷阱（已实测修正，勿回退）：
  ① `FRESH_DAYS` 键是模板 `raw:{src}`，真实水位键是 `raw:gov` ⇒ **必须按族前缀匹配**
     （精确匹配会只命中 1 条水位，及时性变成假高分）；
  ② 唯一性**不能用 `docno_norm` 判重**——同一文号被多源转载是业务常态，按文号判重把
     正常数据误报为质量问题（实测假低分 75.88）。唯一性 = `doc_ref` 主键唯一率。

## 三、灾难恢复：RTO/RPO（按产物分级，对齐 §6.3.4 L-a~L-d）

| 资产 | RPO | RTO | 恢复手段 |
|---|---|---|---|
| `data/governance.db` | 24h | 4h | 文件级备份 + 重建（水位/台账可重登记自愈） |
| `data/raw`（L-a 事实源） | 0（源可再生但代价高） | 8h | 仓外备份 + 断点续跑兜底 |
| `data/cleaned`、`clauses`（L-a） | 24h | 8h | 单版 + history 近三版 + 全链重跑 |
| `published` 双底座 + FTS5（L-b） | 24h | 2h | 索引**可随时重建**（`build_fts rebuild` 有测试覆盖） |
| `external/models`（13GB 权重） | — | 16h | 离线迁入通道（不依赖网络现场下载） |

- **演练**：季度一次，`governance.db` 与 `raw` 各一次，从备份恢复到服务验证**全程计时**，
  记录落 `reports/dr/dr_drill_log.jsonl`（**入库**：演练记录是审计证据，与 SLI 台账同理）。
  **演练即备份验证**——杜绝「有备份无恢复」
  （与 §7.10 两套备份体系的职责分工配套：`data/` 内是工作备份，仓外 `backups/` 是恢复源）。
- 首次演练随 W5 出口完成（`dr_drill_log.jsonl` 有记录且对照达标）。

## 四、明确不做清单（写死理由，防复发）

| 项 | 不做的理由 | 复发条件 |
|---|---|---|
| OpenTelemetry 分布式追踪 | 单机链 run_id+台账已足；collector 常驻无收益 | MCP 并发消费方 ≥3 或跨机部署 |
| atheris 模糊测试 | 输入是已知结构数据（JSONL/CSV/PDF），非任意字节面 | 出现开放输入端点（如未来 Web 门户） |
| `asyncio.TaskGroup`/`ExceptionGroup` | 31 步串行单进程是**有意的确定性设计**，无并发聚合场景 | 引入并发步骤或 MCP 并发达标 |
| 全仓变异测试 | 成本指数级；高价值断言集中在 `gates/` 与契约层 | 核心层存活率持续 >5% |
| uv/poetry 迁移 | 单机部署无分发需求；PEP 621 + lock 已满足（ADR-0011） | 多机/容器化部署 |
| 网页化文档门户 | loopback 定位与组织受众冲突；wiki 通道已覆盖（§8.9） | 组织决议建门户 |
| 质量评分自动阻断 | 渐变指标当准入门会把夜间批处理挡在门外 | 质量维度全部达标且稳定 ≥ 2 个月后再议 |

## 后果

**正面**：故障判断有量化依据（SLI/预算），数据质量有可复算的六维评分，出事有分级恢复手册与
演练记录；两类"说不清"（最近好不好、数据脏不脏）变成可查数字。

**代价 / 局限**

- SLI 依赖治理库数据完整（新库/无数据环境下相关 SLI 标「不可用」而非假装达标）。
- 六维评分的绝对值意义有限，**趋势与阈值更有意义**；勿把 98.84 当 KPI 汇报。
- 演练需要人参与（恢复验证含服务可用性判定），无法完全自动化。
