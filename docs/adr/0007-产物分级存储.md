# ADR-0007 产物分级存储（文件事实源 / SQLite 索引治理 / PG 可选门槛）

- **状态**：已采纳（2026-10-15，W4；对应方案 §6.3.4 / E-1）
- **来源**：《架构草图评估与融合设计_20261012.md》E-1；草图建议「产物结构化数据，例如 mysql」

## 背景

架构草图建议把产物结构化数据「全量入 MySQL」。本项目实测不支持：

1. **体量倒挂**：治理元数据 28.8MB vs 语料 GB 级（raw/cleaned/published 事实源 GB 级）——
   全量入关系库违背克隆可移植与零服务依赖纪律；
2. **三轨制倒退**：已实证的「文件=内容轨 / SQLite=治理轨」会被推回"库即真相"，
   而文件事实源的备份/恢复/审计链路（内容守恒台账、sha256 逐字节比对）全部作废；
3. **运维成本**：单机部署下服务安装/备份/恢复/升级是真实成本，无对应收益。

但草图指向的真实需求——**产物的结构化查询能力**——值得正面回应。

## 决策

**分级存储 + 需求门槛**，产物分四级：

| 级 | 形态 | 内容 | 本项目实例 | 演进规则 |
|---|---|---|---|---|
| **L-a 事实源** | 文件（JSONL/CSV） | 正文、条款、关系边、发布件——**文件即权威** | `data/raw/*.jsonl`、`cleaned/*.jsonl`、`published/external_records.jsonl`(289MB) | 永不入关系库 |
| **L-b 索引/查询** | SQLite（FTS5 + 可选 sqlite_vec/pgvector） | 检索索引、向量索引——**可随时重建的派生层** | `external_index.sqlite`(908MB FTS5) | 重建命令必须存在且被测试覆盖 |
| **L-c 治理元数据** | SQLite `governance.db` | 水位/血缘/台账/审计/待办/关系投影 | 11 表 28.8MB（目标 <50MB） | 超 50MB 或并发写冲突实测出现 → 评估迁移 PG |
| **L-d 查询服务（可选）** | PostgreSQL（env `PGVECTOR_DSN` 注入） | 多消费方并发结构化查询——**按需启用的服务层** | pgvector 已部署（127.0.0.1:7777，wired=false） | 见下方门槛 |

**引入 L-d 的前置门槛（全部满足才启动评估，缺一不可）**：

1. **实测需求**：并发查询方 ≥2 且 SQLite 实测出现锁竞争/延迟不可接受（记录证据）；
2. **降级链先行**：连接仅经 env 注入（口令不入库，`gate_secret_scan` 守护）+
   不可达时降级 SQLite（同 FTS5 既有范式）；
3. **数据边界**：仅索引/元数据层可入 PG；**事实源（L-a）永不迁移**；
4. **运维成本确认**：服务安装/备份/恢复/升级有明确责任人。

## 后果

- **正面**：草图的结构化诉求有正面回应（L-b/L-d 保留查询能力路径）；克隆可移植/
  零服务依赖纪律不被破坏；治理库 28.8MB 远低于 50MB 门槛——**无需 PG 迁移的证据
  记录在案**（本条即证据）。
- **负面**：产物查询能力上限受 SQLite 约束（并发写场景）；L-d 门槛触发时需重新评估。
- **配套**：README §3 数据字典按四级形态组织；pgvector 的分析视图旁路接线见
  方案 §6.4（W4 出口判据）；双轨决策（文件轨去留）见 ADR-0013——两者共同构成
  产物存储的完整治理。
