# ADR-0010 本地 Web 确认台与文档投放入口

- **状态**：已采纳（W2~W4；对应方案第 8 章）
- **来源**：《本地Web确认台设计方案_20261013.md》《文档投放入口评估与方案_20261013.md》
  《目录体系与worklist闭环审查_20261013.md》（用户 2026-10-13 确认纳入方案）

## 背景

worklist 闭环审查发现五断点：产生 → 消费/披露 → 人工处置 → **反馈回写缺失**
（`worklist_resolve` 只更新 status/resolved_by/at/resolution 四字段，无业务回写）。
人工确认六要素（结构化选项/理由模板/影响面/by/业务回写/验证）需要承载面。

## 决策

1. **自建本地 Web 确认台**（loopback-only，纯标准库零依赖）：MS To Do（无变更
   webhook、delegated-only 令牌、字段贫乏）/ 企业微信（留作未来移动通道，本轮不做）
   / 邮件（解析回传脆弱）/ 日历（完成态语义不符）/ Zapier 等云端自动化（数据出境，
   合规红线）均不满足六要素；
2. **文档投放 = 看板 + wiki，不建门户**：wiki 已解决组织检索（SHA256 双端增量 +
   frontmatter 溯源）；看板做状态/增量/台账；原件走 file 直开，不做 HTTP 文件服务；
3. **H 轨（人机交互层）与主链解耦**：确认台只读治理库 + 经 interfaces 写回，
   不创造第二条业务路径（同 MCP 门面纪律）。

## 后果

- worklist 从「只读披露」升级为「可处置、可回写、可验证」；
- 确认台趋势图复用既有可观测性单点（不新建监控栈）；
- 投放入口不做网页化文档门户（与 §7.10 目录体系 SSOT 一致：docs/= 对外交付物）。
