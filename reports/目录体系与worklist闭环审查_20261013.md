- **审查日期**：2026-10-13
- **审查方式**：仓根全目录实测（规模/内容）、.gitignore 全文、paths.py 常量覆盖比对、目录名字面量引用 grep（代码/配置/门禁三层）、worklist DDL/API/产生方/消费方/发送方全链取证

## 1.2 案例一深析：`reports/` · `data/` · `docs/` 同级——「两个 reports」命名撞车 + docs 单层包装

**现状**：
- `docs/` 下**仅有 `reports/` 一个子目录**（18 文件 = 17 项分析交付 + _manifest.json）——`docs/` 本身是单层包装，无独立内容（README:54 自述「链路总图已并入 README §8」后，docs/ 失去其他子目录）；
- `reports/` 下混合**四类异质内容**：① 按批次重构报告（变更日志属性，入库）② 一次性方案底稿（C2漂移治理底稿/F-L01专项报告/Obsidian_PoC 等）③ 运行手册（`运行手册_编排与定时_20260912.md`，由 gen_schedule_doc 生成）④ `_tmp`（运行台账+步骤日志，**gitignore 忽略**）/`_snap`/`_wiki_sources` 三个下划线前缀目录（入库与否需确认——**待人工确认**）；
- `data/` 与两者职责不重叠（运行期数据，忽略），同级关系本身合理。

**问题判定**：
1. **命名撞车（职责清晰度 -）**：`docs/reports/`（分析交付物）与 `reports/`（过程性文档）同名同级子树——新人检索「reports」命中两个语义完全不同的目录；README §7 把 docs/reports 称「分析交付库」、reports 称「重构报告+台账」，靠文档区分而非结构区分；
2. **docs/ 单层包装（冗余 +）**：一层目录只包一个子目录，无信息增益；若保留「交付物与过程文档分离」的意图，应让层级本身表达；
3. **reports/ 四类混合（职责清晰度 -）**：变更日志/一次性底稿/机器生成手册/运行台账混居——其中 `_tmp` 被忽略而 `_snap`/`_wiki_sources` 状态不明，同一个目录内「入库/忽略」双轨，边界靠 .gitignore 逐条维持。

**调整建议**（三选一，推荐 B）：
- **A. 最小改动**：`docs/reports/` → `deliverables/`（或 `analysis/`），消除撞车；`docs/` 删单层包装；
- **B. 结构分区（推荐）**：`reports/` 按性质分三子目录——`reports/refactors/`（批次报告+CHANGELOG 关联）、`reports/manuals/`（机器生成手册+ADR）、`reports/scratch/`（一次性底稿，可整体忽略或定期清理）；分析交付物留在 `docs/reports/` 但 README §2 目录表明确定义「docs/= 对外交付物、reports/= 对内过程文档」的分层语义；
- **C. 合并**：交付物并入 reports/——否决（交付物有独立 manifest/schema_version 契约与门禁，混入会削弱「交付库」的机器可判性）。

## 1.3 案例二深析：`external/` 与 `tessdata/` 同级——一个工具两个家 + 路径 SSOT 缺失

**现状**（实证）：
- `external/` = 外部大资产统一外置：`models/`（语义权重 13GB）、`PaddleOCR-3.7.0/`（OCR 引擎源码）、`tesseract/`（**junction → 系统 Tesseract 安装目录**，gitignore:注释「external/ 含 tesseract junction → 系统安装目录」）、`upstream/`（DeepKE/WeKnora 源码树）；
- `tessdata/` = 3 个 traineddata（chi_sim/eng/osd）——**Tesseract 的语言数据**；
- 引用实证：`config/ocr.yaml:9`（可执行 `${REG_ORCH_ROOT}/external/tesseract/tesseract.exe`）+ `:10`（数据 `${REG_ORCH_ROOT}/tessdata`）——**可执行与数据分置两个平级目录**；`ocr_engine.py:70` `_TESSDATA_DEFAULT = os.environ.get("OCR_TESSDATA_DIR") or os.path.join(_REPO, "tessdata")`；另有 `supp_ocr_pdf.py:42`、`pbc_recover.py:46`、`doctor.py:129` 共 **5 处各自拼 tessdata 路径**（`_REPO`/`BASE`/`paths.ROOT` 口径不一）；
- doctor 有 tessdata 检查项（doctor.py:128-129/:352）✓。

**问题判定**：
1. **工具跨目录（合理性 部分 -）**：Tesseract 的「可执行（external/tesseract）+ 数据（tessdata/）」被拆到两个仓根平级目录——拆离的**隐式理由**（junction 指向系统目录不可写入数据、或语言包需工作区覆盖）无任何文档记载，属「历史演化残留」而非设计；
2. **paths SSOT 违反（规范性 -）**：paths.py:5-6 纪律「全仓唯一路径解析入口；业务代码禁止硬编码盘符绝对路径」——tessdata 无常量，5 处自拼（虽用 _REPO 派生不触盘符，但违反「唯一入口」原则，与 R4 精神相悖）；
3. **同构问题扩散**：`external/`、`logs/`、`backups/`、`archive/`、`exports/` 均无 paths 常量，各有 2~6 处自拼（retention.py:43 ARCHIVE_ROOT、governance_sync.py:361 exports、logging.py:85/ config.py:66 logs、rfn_backlog.py:64 等）——**目录常量覆盖不全**是本目录体系最系统的规范性问题。

**调整建议**：
- **tessdata 并入 external 家族**：`tessdata/` → `external/tessdata/`（或 `external/tesseract-data/`），ocr.yaml 的 `tessdata_dir` 默认值同步改为 `${REG_ORCH_ROOT}/external/tessdata`；junction 与数据同属「Tesseract 资产」，同目录满足「一个工具一个家」；迁移为同卷 rename（16.4MB，零风险）；
- **paths.py 补常量**（一次性收口）：新增 `EXTERNAL_DIR`/`TESSDATA_DIR`/`LOGS_DIR`/`BACKUPS_DIR`/`ARCHIVE_DIR`/`EXPORTS_DIR`/`GRAPHIFY_DIR`（后三者按需），全部经 `REG_ORCH_ROOT` 派生；5+ 处 tessdata 引用与 retention/governance_sync/rfn_backlog 等自拼点改引常量——**这正是第 7 章代码重构的目录层对应项**；
- **document 决策**：在 README §2 或 ADR 补记「external = 全部外部资产统一外置（含 tessdata），仓根不再平铺工具数据目录」。

## 2.3 反馈路径与流转机制：**整体缺失（最严重断点）**

- `worklist_list(status="resolved")` 的**生产消费方为零**（仅 CLI export/stats 与 tests）——人工决策沉淀在队列里，**不回写任何业务数据域**：

  - `internal_unaligned`（D2）的人工对齐 → 不回写 `align_result.json`；
  - `timeliness_conflict`（D3）的人工裁决 → 不回写 `verification_state.json`；
  - `relevance_boundary`（D6）的 BOUNDARY 裁决 → 不回写 relevance 筛选结果；
  - `rfn_clean_drift_c2`（D4）的人工 supersede 决策 → 不回写桥表 `rfn_clean_bridge.csv`；

- 即：当前闭环 = 「产生 → 披露 → 人工登记结论 → **终点**」，**「结论 → 业务数据 → 下游重跑 → 验证」整段缺失**。

## 2.5 补全方案（worklist 闭环五环）

**目标闭环**：`产生（带 payload+建议+影响面）→ 披露（status/export/aged 告警）→ 人工处置（结构化选项+理由+风险）→ 业务回写（按 kind 的处置动作）→ 验证（回写落盘 + 水位/门禁确认 + 重新打开机制）`

| 环 | 补全设计 | 落点 |
|---|---|---|
| ① 产生增强 | `worklist_add` 的 `payload` 标准化：每类 kind 声明「影响面摘要」（如 rfn_theme_uncertain 附 candidate themes + 各自票数；timeliness_conflict 附冲突双方证据）；`suggestion` 改为「建议选项 + 依据」结构化 | enums 注释扩为 kind 注册表（kind → 产生方/payload schema/建议选项集） |
| ② 处置结构化 | `worklist resolve` 增 `--option <受控选项>`（confirm/reject/defer/escalate/need_info——按 kind 注册表收敛可选集）+ 保留 `--resolution` 自由文本 + `--by <处置人>`（必填，修断点 3）；`defer` 转新状态 `deferred`（带 defer_until），`escalate` 触发 notify 升级事件 | WORKLIST_STATUS 增 deferred；governance_store.worklist_resolve 扩展；commands/worklist.py 增强 |
| ③ 风险与理由 | resolve 前打印「影响面 + 风险评估」：该条目的 payload 影响域（哪些产物/下游会因决议变化）+ 选项语义（confirm=按建议执行/reject=标记无需处置/defer=挂起至日期/escalate=升级评审/need_info=补充材料后重开）；每选项附「理由模板」供 --resolution 快速填充 | commands/worklist.py 新增 `show <item_id>` 子命令（详情+选项菜单+影响面） |
| ④ 业务回写（核心） | 每类 kind 注册「处置动作」（kind → action 映射表，`config/worklist_actions.yaml` 或 enums 同文件注册）：如 rfn_theme_uncertain/confirm → `rfn registry set-theme --rfn X --theme Y`（写归属表）；timeliness_conflict/confirm → `verification_state.override`；internal_unaligned/confirm → align 覆写入口；relevance_boundary/confirm → filter 边界集更新。**动作由各模块既有写口执行**（不新造写口——SSOT 纪律），回写结果写回 worklist 条目的 `resolution` 审计链 + audit_log | 新模块内动作表 + governance_store 增 `worklist_apply`（校验 status=open → 调注册动作 → 记 audit） |
| ⑤ 验证与重跑 | 回写成功后：① 该条目 status=resolved 且 resolution 含「已回写 X（sha/时间）」；② 通知水位系统「该域已变」（GOV_ARTIFACTS 观察型重登记）→ 下游 `--resume` 自然重跑；③ `defer` 到期由 worklist_aged 同机制提醒；④ 门禁扩展：J7 判据从「产生方闭合」升级为「**产生方 + 处置动作注册**双向闭合」（每 kind 必须有 action 或显式 `no_action` 理由） | gate_config_integrity J7 增强 + governance:sync 投影 |

**与重构方案的关系**：②③ 属 W2 后 CLI 增强（低风险纯增量）；④ 的处置动作表与 W3 领域模块（reg_frameworks 的映射复核 kind `regfw_map_review`、implementation_audit 的 `implanudit_gap` kind）**同步设计**——新 kind 诞生时即注册动作，不再欠账；①的 kind 注册表替代现有 enums 注释，成为 J7 判据的机器可读事实源。
