# 双底座优化与 llm_wiki 知识库融入架构方案

> 编制日期：2026-09-12
> 依据：`reports/regulatory-compliance-orchestrator.md`（五步规划）· `reports/代码审查报告_20260911.md` · `reports/中间产物衔接分析_20260912.md` · `reports/流程系统性深度分析_20260912.md` · llm_wiki 项目调研（github.com/nashsu/llm_wiki）
> 目标：以 regulatory_scrapers（外部监管文件）与 internal_policy_base（内部制度文件）为双底座，引入 llm_wiki 构建知识库能力，支撑 regulatory_classifier / internal_policy_drafter / internal_control_management 三模块

---

## 一、背景与目标

规划要求"外部监管→内部制度→内控"的强制来源链。当前双底座各自成链但**对外无统一访问契约**（三份报告已证：跨模块直引、接口空转、5 套归一、时效三源并行）。本方案明确三件事：

1. **底座优化**：把双底座各自"整理"为可发布的稳定契约（Base Contract v1）——字段、索引、目录、更新语义；
2. **调用方式**：三模块对底座数据的统一调用路径（经 interface 层，杜绝直引内部实现）；
3. **知识库融入**：llm_wiki 作为**第三层"知识层"**（wiki 化 + 语义检索 + 图谱），置于结构化底座之上、应用模块之下——**不替代底座、不承载权威字段**。

## 二、llm_wiki 能力画像与融入定位

### 2.1 能力画像（调研结论）

| 维度 | 事实 |
|---|---|
| 形态 | 跨平台桌面应用（Tauri v2/Rust + React），GPL v3.0 |
| 架构 | 三层：`raw/sources`（不可变源）→ `wiki/`（LLM 生成）→ Schema（规则）；三操作 Ingest/Query/Lint |
| 产物 | `wiki/{index.md, log.md, overview.md, entities/, concepts/, sources/, synthesis/, comparisons/}`；每页 YAML frontmatter 含 `type/title/sources:[]`（溯源）；Obsidian 兼容 |
| 摄取 | 两步 CoT（分析→生成页面）；**SHA256 增量缓存**（未变跳过）；持久化串行队列（崩溃恢复/重试）；**源文件夹自动监控**；PDF/Office/图片/网页多格式 |
| 检索 | 四阶段：分词（CJK bigram）+ 可选向量（LanceDB, 启用后召回 58.2%→71.4%）+ 4 信号图谱扩展 + 预算组装；"Read Sources Only"模式 |
| 集成 | **本地 HTTP API `127.0.0.1:19828`**（token）：`/projects`、`/files`、`/search`（混合检索）、`/chat`（SSE，可选 deep）、`/graph`、`/sources/rescan`、`/pages/embed`；**MCP Server**；Agent Skill；Chrome 剪藏 |
| 图谱 | 4 信号关联（直链×3.0/源重叠×4.0/Adamic-Adar×1.5/类型亲和×1.0）+ Louvain 社区 + 知识缺口识别 |

### 2.2 融入定位（关键设计决策）

```
┌─────────────────────────────────────────────────────────────┐
│ 应用模块层  classifier · drafter · internal_control(待建)      │
├─────────────────────────────────────────────────────────────┤
│ 知识层（新增）llm_wiki：wiki 页面·语义检索·图谱·源监控          │  ← 本方案引入
├─────────────────────────────────────────────────────────────┤
│ 结构化层  classifier 分类体系 / merged_view / 明细表（既有）     │
├─────────────────────────────────────────────────────────────┤
│ 底座层（双底座）regulatory_scrapers（外部）· internal_policy_base（内部）
└─────────────────────────────────────────────────────────────┘
```

**定位边界（必须坚持）**：
- ✅ llm_wiki 贡献：文档→wiki 编译、语义检索、实体/概念图谱、知识缺口发现、**源文件夹监控（恰好补"变更监听器"缺位）**；
- ❌ llm_wiki 不承担：权威字段（时效/文号/RFN 等）、结构化校验、交付物生产——这些仍在底座与分类层；
- 关系：底座**发布包 → wiki 源**（单向事实），wiki 检索结果**回供**模块作为语义召回（辅助角色）。

**核对既有问题清单**：llm_wiki 的三大机制可直接缓解本仓已确认缺口——①SHA256 增量 + 源监控 → 对应"同日改写四重隐身（M-10）"与"变更监听器无实现（N14）"；②语义检索+图谱 → 对应"正文级检索全量线性、无统一查询入口（3.4 节）"；③溯源 frontmatter → 对应"引用/关联断裂（M-02 等）"的部分场景。但它**不能**修 M-01/M-05/M-06 等结构化缺陷。

## 三、双底座现状结构分析

### 3.1 外部底座（regulatory_scrapers）

**产物链**：`raw/*.json`（五源，287MB，含附件文本/表格/富内容）→ `cleaned/*.{csv,jsonl}`（双轨，517MB）→ `clauses/*.jsonl`（5 源 4043 行）→ `docs/<source>/`（附件实体 0.5-1GB）→ `clean_index/index.json` → `cache/`。

| 结构问题（引用报告编号） | 底座影响 |
|---|---|
| 双轨不等价（CSV 压平投影 vs JSONL 原生全量；attachments/rich 仅 JSONL）——B-01/B-02 | 下游按轨分化、消费语义不一 |
| 五源 raw 字段 5 套（ID/机关/文号/正文/附件）——H-01~H-08 | 无统一记录契约 |
| clauses 行仅 8 键（无时效/日期/机关）、无 RFN、同日不重建——C-01/C-02/M-09 | 无法直接与分类层 join |
| table_structured 三形态零消费——A-05-2 | 表格类文件（EAST）无出口 |
| 附件文本三处存（raw 内嵌/docs.txt/实体）——G-11 | 无"哪份是权威"声明 |
| 无对外只读接口（消费方各自 glob/读文件）——A-03/B-03 | 访问方式散乱、缺语义 |

### 3.2 内部底座（internal_policy_base）

**产物链**：`originals/`（源文件）→ `processed/{IPN}.json + *_fulltext.json + *_clauses.json/.md + *_rich.json + *_images/`（107 制度）→ `internal_policy_index.json`（107 条）→ `align_result.json` → `merged_view.json`（含 inputs 指纹）。

| 结构问题 | 底座影响 |
|---|---|
| index 重建**剔除主题列**（primary_theme 0/107）——E-01/M-06 | align→merged 链随时断裂 |
| merged_view.inputs 指纹 0 校验（已陈旧 16h 仍 PASS）——E-02 | "视图新鲜度"不可信 |
| 76+/107 制度"条文 0 条"仍产出 rc=0——E-04 | 条款级消费大面积缺件且静默 |
| clauses.json 丢 method/tail_marker/count——E-07 | 元数据不完整 |
| 对外接口 `internal_policy_api` 零调用空壳——A-03 | 无契约访问面 |
| 无 RFN 反向索引（制度→监管仅 merged 一次性字符串匹配 47/107）——D-06/E-06 | 制度↔监管映射弱 |

### 3.3 双底座共性问题（→ 优化方案的靶点）

1. **无"发布契约"**：产物是"内部工作文件"，不是"对外发布件"——下游各自兜底；
2. **无统一主键体系**：RFN 只在分类层完整；底座侧（clean 记录/条款行/制度条款）缺 RFN 或连接键；
3. **无索引层**：全文检索全量线性（335MB JSONL 驻留内存）；
4. **无事件/变更信号**：更新靠人工记忆（M-10 同日隐身）；
5. **无权威轨声明**：双轨/三处存/三形态并存。

## 四、双底座优化方案

### 4.1 目标态：双底座发布契约（Base Contract v1）

**设计原则**：底座**只发布结构化发布件**（权威）；llm_wiki 只消费"发布包"；应用模块只经 interface 读发布件。

**A. 外部底座发布件**（`modules/regulatory_scrapers/published/`，新目录）：

| 发布件 | 格式 | 主键 | 核心字段（契约） | 来源（现有产物） |
|---|---|---|---|---|
| `external_records.jsonl` | JSONL（权威轨） | `record_id`(=dedup_key) + **rfn** | title / document_number / issue_organ / publish_date / effective_date / timeliness_status / verification_source / source / body_text / attachment_count / table_structured / **rfn** | cleaned JSONL + 归属表 join（经 bridge） |
| `external_clauses.jsonl` | JSONL | `record_id`+`article_no` | document_number / title / chapter / article_no / article_body / **rfn** / publish_date / timeliness_status | clauses jsonl + 补键（C-02） |
| `external_attachments.jsonl` | JSONL | `record_id`+`sha256` | file_name / mime / local_path / sha256 / text / ocr_status | raw attachments（补 pbc，A-01） |
| `external_index.sqlite` | SQLite（+FTS5） | — | 表：records / clauses / attachments / **FTS5 全文**（title+body 中文 bigram→trigram 或 jieba 分词表） | 由上述 jsonl 构建 |
| `publish_manifest.json` | JSON | — | snapshot_date / 各文件 sha256 / 记录数 / schema_version | clean_index 扩展 |

**B. 内部底座发布件**（`modules/internal_policy_base/published/`）：

| 发布件 | 格式 | 主键 | 核心字段 | 来源 |
|---|---|---|---|---|
| `internal_policies.jsonl` | JSONL | `ipn` | title / docno / eff_status / primary_theme / secondary_themes / **associated_rfns** / file_type / version | index + align（修主题列 E-01） |
| `internal_clauses.jsonl` | JSONL | `ipn`+`article_no` | chapter / article_no / article_body / **rfns[]**（条文级引用） | processed clauses（缺口化 E-04） |
| `internal_index.sqlite` | SQLite（+FTS5） | — | 同上 + 全文 | 构建 |

**C. 连接键体系（全链统一）**：

| 键 | 语义 | 生成处（唯一） | 用途 |
|---|---|---|---|
| **RFN** | 监管文件唯一编号 | `rfn/registry`（修 M-05 后） | 全链主键（底座↔分类↔制度↔内控） |
| `record_id` | 外部记录内容 sha | `unified_schema.build_dedup_key` | 底座内部去重/锚（bridge 已有） |
| `ipn` | 内部制度编号 | `indexer` | 内部主键 |
| `docno_norm` | 文号归一 | `common_lib.norm.norm_docno`（统一后） | 辅助匹配 |
| `title_norm` | 标题归一 | 同上 `norm_title` | 辅助匹配 |

**D. 索引设计**（SQLite + FTS5，单文件、零服务、Python 标准库 sqlite3）：
- `records(rfn PK, record_id, docno_norm, publish_date, timeliness_status, source, …)` + `records_fts(title, body)`；
- `clauses(rfn, article_no)` + `clauses_fts`；
- `policies(ipn PK, primary_theme, eff_status, …)` + `policies_fts`；
- 覆盖"按 RFN/文号/主题/日期/全文"五类查询——替换现状 16 个线性检索入口中正文级 8 个。

### 4.2 优化路线（与三份报告台账对齐）

| 阶段 | 动作 | 关联问题 |
|---|---|---|
| Step 1（与 P0 修复并轨） | 修结构化缺陷：登记链三修、clauses 补键、时效默认值、覆盖率门禁、OCR 回写 | M-01/05/08/09、D-07 |
| Step 2 | 建"发布层"：双底座 published/ 目录 + 构建脚本（复用 clean_index/rfn/merge 数据）+ manifest | 本方案 4.1 |
| Step 3 | 建 SQLite+FTS5 索引 + `base query` CLI（替换线性检索） | 3.4 节检索瓶颈 |
| Step 4 | 声明权威轨：cleaned JSONL 为权威、CSV=检索投影；attachments 权威=raw 内嵌；table_structured 登记 schema | B-01/G-11/A-05-2 |

## 五、三模块对底座数据的调用方式

**统一纪律**：三模块**只读 published/ 发布件**（经 `interfaces/base_api.py` 新增契约或 `cli.py base query` 命令），禁止直引底座内部目录（根治 E-08/A-03 直引问题）。

| 模块 | 读底座（外部） | 读底座（内部） | 调用方式 | 频度 |
|---|---|---|---|---|
| **regulatory_classifier** | external_records（全字段）+ external_clauses + 时效态（经归属表） | —（不读内部） | `base_api.query_external(filters)` → 写分类体系（base/final/明细） | 每次 clean 快照推进后 |
| **internal_policy_drafter** | 经**分类层**（规划 3.4：政府文件数据强制来自 classifier）：merged_view + 明细表 | internal_policies + internal_clauses（草稿素材） | `base_api.get_policy(ipn)` + `get_merged_view()`；**不直读 external 底座** | 起草任务时 |
| **internal_control_management（待建）** | 经分类层取"监管要求清单"（明细表派生）+ 未来 EAST 统计 | internal_clauses（要求条款） | `base_api.query_internal(theme)` + `query_requirements()` | 检视任务时 |

**字段级契约（三模块共同依赖的最小集）**：
```
external_record: rfn, title, document_number, publish_date, effective_date,
                 timeliness_status(7值), verification_source, source,
                 attachment_count, has_table, body_len, url
external_clause: rfn, article_no, article_body, publish_date, timeliness_status
internal_policy: ipn, title, docno, eff_status, primary_theme, associated_rfns[]
internal_clause: ipn, article_no, article_body, rfns[]
```
（以上即 4.1 发布件的对外投影；`rfn` 与 `ipn` 为跨模块 join 键。）

**调用方式三选一建议**：① `interfaces/base_api.py`（进程内、推荐）；② `cli.py base query --json`（跨进程/调试）；③ 后续可选 MCP 暴露（与 llm_wiki MCP 并列）。**三选一，不得裸读目录**。

## 六、llm_wiki 融入后的整体架构

### 6.1 目标架构（四层 + 双向边界）

```
┌── 应用层 ────────────────────────────────────────────────────────┐
│ classifier(分类体系)   drafter(制度起草)   control(内控检视)        │
│        │ 读                        │ 读              │ 读           │
│        ▼                           ▼                 ▼            │
│  ┌ interfaces/base_api ── 结构化查询（SQLite/FTS5 + 发布件）────────┐│
├──┼─ 知识层（llm_wiki）──────────────────────────────────────────────┤│
│  │  wiki(entities/concepts/synthesis) ← 摄取 ← published 发布包      ││
│  │  /search(混合) /chat(agent) /graph(关联) ← HTTP API 19828 / MCP   ││
├──┼─ 结构化层（既有）clean_index · rfn · base/final · merged_view ────┤│
├──┼─ 底座层（双底座，唯一事实源）────────────────────────────────────┤│
│  │  external: raw→cleaned→clauses→{published 发布件}               ││
│  │  internal: originals→processed→index/align→{published 发布件}    ││
└──┴─────────────────────────────────────────────────────────────────┘
```

### 6.2 数据流（发布 → 摄取 → 检索回供）

```
双底座构建 → published/{external_records.jsonl, …}（+manifest）
     │                                    │
     ▼                                    ▼
 SQLite/FTS5 索引                 同步脚本 → llm_wiki 监控文件夹（raw/sources/）
（结构化精确查询）                       │（SHA256 增量，源文件夹自动监控）
     │                                    ▼
     │                            llm_wiki 两步 CoT 摄取
     │                                    │
     │                                    ▼
     │                     wiki/{sources/, entities/, concepts/, synthesis/}
     │                                    │
     └──────────┬─────────────────────────┘
                ▼
        三模块组合检索：结构化过滤(FTS5, 精确) → 语义召回(llm_wiki /search) → 图谱扩展(/graph)
```

**同步策略（关键）**：
- 只喂"发布包中的**文本件**"（records/制度全文/条款/附件文本）到 llm_wiki —— 结构化字段（时效/RFN）**不进 wiki**（避免双源漂移）；
- **文件命名约定**：`<rfn>__<title前40字>.md`（外部）/`<ipn>__<title>.md`（内部）→ llm_wiki 的 frontmatter `sources` 可回溯到 RFN/IPN；
- 增量：先按 manifest 的 sha256 对比，只复制变化文件（与 llm_wiki 自身 SHA256 缓存双层去重）。

### 6.3 映射设计（我们 ↔ wiki）

| 我们 | wiki | 用途 |
|---|---|---|
| RFN / IPN | 源文件名前缀 + frontmatter `sources[]` | 溯源（wiki 结论→权威文件） |
| 主题 T1-T10 / 子主题 | `concepts/` 页面（每主题一页，标题=主题名） | 主题知识聚合 |
| 上位法/被引关系 | `entities/`（法规实体页）+ 图谱 | 关联分析（替代 clause_graph 无消费者 M-03/D-04） |
| 规划 2.1.1.2 时间线 / 2.1.3.2 交叉影响 | `synthesis/`、`comparisons/` 页面 | 五级交付的"分析型章节"素材（llm_wiki 生成 + 人工策展） |
| 时效状态 | **不映射**（wiki 不做时效）| 由结构化层负责 |

### 6.4 集成点与落地步骤

| # | 步骤 | 说明 |
|---|---|---|
| 1 | **PoC**（1 日） | 安装 Windows 版；建项目；手动导入 10 份代表文件；验证：摄取质量/中文检索命中/`/search` `/graph` 行为、源文件夹监控生效方式、API 是否可程序化触发摄取（`/sources/rescan` 语义）——**这是唯一"待验证"项** |

### 6.5 风险与对策

| 风险 | 级别 | 对策 |
|---|---|---|
| llm_wiki 为桌面应用，工程化/API 覆盖度待验证 | 高 | Step 1 PoC 先行；若摄取不可程序化触发，则降级为"人工导入+源监控"半自动，仍可支撑语义检索 |
| 摄取 token 成本（107+4043 文档全量喂入） | 中 | 分层喂入：①外部只喂"有效+关键主题"摘要+正文；②内部喂全文；③条款级只在需要时喂；用 SHA256 增量 |
| 双源漂移（wiki 内容与底座不一致） | 中 | 边界纪律：wiki 不承载结构化字段；检索结果必须回链 RFN 校验后使用 |
| 桌面应用不可无头运行（服务器场景） | 中 | llm_wiki 定位为"分析师桌面工具 + 本地 API 服务"；批处理管道不依赖它（离线兜底=FTS5） |
| GPL v3.0 许可 | 低 | 独立进程 + HTTP 集成，无链接/无分发改造 |

## 七、结论

1. **双底座的本质问题是"工作目录 ≠ 发布契约"**：产物可读但不可"按契约消费"——本方案以 `published/` 发布件 + RFN 主键 + SQLite/FTS5 索引 + manifest 四件套收敛（§4.1），并与三份报告 P0/P1 台账同序推进。
2. **三模块统一经 `interfaces/base_api` 读发布件**（§5）：classifier 读外部、drafter 读内部+分类映射层、内控读内部条款+要求清单——彻底终结直引与兜底阅读。
3. **llm_wiki 的定位是"知识层"而非"底座"**（§2.2/§6）：贡献 wiki 化、语义检索（召回 58%→71% 的实证）、图谱与**源监控**；不承载权威字段。其源监控机制与 SHA256 增量恰好补足我们"变更监听器缺失（N14）"与"同日改写隐身（M-10）"的信号缺口。
4. **落地顺序**：PoC（验证 API/监控）→ 发布层 → 索引 → 同步脚本 → 三模块检索接入 → 闭环接线；每步均可在现有三份报告修复计划内并行推进。
5. **待验证项唯一**：llm_wiki 的摄取触发方式（源文件夹监控 vs `/sources/rescan` 的编程可达性）——PoC 首日即可澄清，不影响其余设计成立。
