## 二、T1：用户活动让路（设计取舍逐条）

| 决策 | 理由（质量优先） |
|---|---|
| 用 `GetLastInputInfo` 判断"距上次键鼠输入的秒数" | **只读**系统 API：不挂钩、不注入、不读用户内容 ✓ |
| **只在启动转换前**等待，**不**在转换中打断 | LO 转换一旦开始**无法安全中止**（中止会遗留进程/半成品 ✗）⇒ "不开始"是唯一安全的让路方式 ✓；直接对准"用户复制的**那一刻**被打断"这一实际场景 ✓ |
| 等待**上限**（默认 60s，`RCO_QUIET_MAX_WAIT` 可调） | 用户长时间连续敲键盘时不能无限阻塞流水线 ⇒ **延迟**而非**停摆** ✓ |
| **fail-open**：API 不可用/异常 ⇒ 立即继续 | 让路是体验优化，**绝不能**成为流水线单点故障 ✗ |
| 与批 58 共用开关 `RCO_YIELD_TO_USER=0` | 一处开关管全部让路行为（优先级 + quiet 等待）⇒ 语义一致、易解释 ✓ |
| 49.7 天 tick **回绕**处理（`& 0xFFFFFFFF`） | `GetTickCount` 回绕不处理会算出**巨值** ⇒ 永久等待 ✗（健壮性细节 ✓） |
| 自检：`python -m std_lib.scraper_std.user_activity` | 实测输出 `{"enabled": true, "idle_seconds": 13.875, "quiet": true}` ✓（读数正确 ✓） |

**与既有链的配合**：护栏（内容不丢 ✓）→ 缓存（同一内容只转一次 ✓）→ **让路（用户在用时不开始 ✓）**
⇒ W-AT 残余从"每份新内容一个窗口"进一步收敛为"**用户安静时**的每份新内容一个窗口" ✓。

## 三、T2：W-AU 收口（**受控取舍**，非缺陷）
`clipboard_guard` 的保全白名单**恰为** `CF_TEXT`/`CF_UNICODETEXT`/`CF_HDROP`，并新增**精确守卫测试**防止擅自扩张 ✗。
技术依据（写入测试与模块文档）：位图/HTML/RTF/OLE 常为 **delayed rendering** ⇒ `GetClipboardData` 会**反向请求
持有者渲染**（可能唤起其 GUI、阻塞，甚至使 `CloseClipboard` 失败 ⇒ **用户的剪贴板被锁住** ✗✗，危害远大于收益）。
取舍：只保全可确定性读取的格式 + **未保格式在日志明示**（`describe()`）✓。

## 四、过程诚实记录（本轮 3 次失败均为**测试自身**问题，实现自始正确）
1. `test_user_activity` 两处失败 ✗ → 探因：本仓 `sys.path` 同时含仓根与 `std_lib` ⇒ 同一文件存在**两份模块对象** ✗，
   按 `sys.modules` 遍历打桩**实测未生效**（测试读到**真实**活动 ⇒ 等待 4.2s，恰为真实 idle 越过 1.5s 的时刻 ✗）。
2. ⇒ **正解（质量优先）**：为 API 增加**显式注入点** `quiet_fn`（缺省 `is_user_quiet`）——测试**零打桩、确定性** ✓；
   同时发现测试助手 `_quiet` 未体现 `_enabled()` ✗（`RCO_YIELD_TO_USER=0` 用例因此误报 ✗）。
3. 最后 1 处失败经**运行时取证**（`inspect.getsource` + 直接复现 `wait = 0.000` ✓）定位为**我的断言写错** ✗：
   `wait_for_quiet_window` 返回**时间差**（两次 `time.monotonic()` 之差，可能为 `9e-07` ✗）⇒ 全等断言不成立
   ⇒ 一律改**容差比较**（`< 0.05`）✓。
> 结论：**"实现疑云"必须用运行时取证终结**（`inspect`/直接复现），而非继续推测 ✗。
