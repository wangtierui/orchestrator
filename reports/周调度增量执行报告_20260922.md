## 2. 发现与处置

### 2.1 【P0 已修】`gov_collector.py --source all` 必然崩溃（2026-09-15 起）

- **现象**：`python gov_collector.py`（`--source` 默认即 `all`）抛 `KeyError: 'all'`。
- **根因**：`gov_parse.SOURCES` 无 `"all"` 键，而 `main()` 在**子源分发之前**执行
  `cfg = build_config(args)`（`gov_collector.py:599`）→ 多子源模式必崩。
  该顺序缺陷由 2026-09-15 提交 `8f8f9a1`（gov 纳入 zhengceku 子源）引入；
  `tools/run_production_refresh.py` 的 gov 采集命令正是 `--source all`。
- **修复**：按**首个子源**构建公共配置（`RobustSession` 的超时/重试/延时与 `resume`/`out_dir`
  均与子源无关），子源专属 cfg 仍在循环内 `build_config(sub)` 重建。
- **验证**：`--source all --max-items 1 --no-details`（输出到 `%TEMP%`）冒烟通过，两子源正确分发；
  随后真实增量运行成功（见 §1）。

### 2.2 【P0 已修】mof 记录级指纹增量完全失效（两个叠加成因）

诊断（只读、复算 diff）：`ADD=870 / UPD=0 / UNC=0`，而主库恰好 870 条 → **100% 被判"新增"**。

- **成因 a — 主键类型错配**：主库 `id` 为 `int`，`fgk.mof.gov.cn` 列表接口现返回 `str`（同一数值）。
  实测 `OVERLAP_raw=0 / OVERLAP_str=90`。原实现 `prev_by_id.get(rid)` 按原类型取值 → 恒不命中。
- **成因 b — null 口径错配**：修复 a 后仍 `UPD=255`，逐字段定位为**仅 `effective_date`**：
  列表侧 `normalize_date(lSsDate)` 返回 `None`，主库历史值为 `''`（254 条），`None != ''` → 假"变更"。

**后果**：每周对全部 870 条重抓详情并对**每个附件做本地重抽取（单条数秒级）** → 数小时无法完成
（`mof_laws.json` 长期停留在 09-12，非本周才发生）。这正是增量纪律要禁止的"无谓全量重抓"。

**修复**：
- `_canon_law_id()`：主键统一到主库既有约定（纯数字 → int）；**仅规范化比对/记账键**，
  网络调用仍用接口原样 id（不影响请求语义与缓存键）。
- `_sig_eq()`：指纹比较前把 `None` 归一为 `''`（该字段在列表接口中本就不可得，
  排除其 null 形态不损失任何真实可检测的变更能力）。

**验证**：修复后真实运行 `新增 0 / 更新 1 / 未变 869`，**秒级完成**。
