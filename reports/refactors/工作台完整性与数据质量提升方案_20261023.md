# 确认台：完整性盘点与数据质量提升方案（2026-10-23）

> 回答用户第 5 问："工作台是否已完整呈现当前项目？请制定一份通过收集使用中发现的问题、
> 持续提升数据质量与功能建设的执行方案。"
>
> **答案：不完整，但缺口已可枚举**。本文先给**机器可核对的盘点表**（12 个能力域 × 现状），
> 再给**可持续的收集→分类→处置→验证闭环**，最后给**度量指标与节奏**。
> 原则：**不追求"看起来全"**，只追求"缺什么一眼能看见、每条都能追到责任人与验收"。

## 二、问题收集机制（已上线，替代口头反馈）

### 2.1 链路

```
使用者（内网/本机）
   └─ 确认台「留言板」提交（分类 / 严重度 / 页面 / 标题 / 说明 / 域账号）
        └─ POST /api/feedback（内网唯一允许的写口，只追加）
             └─ governance.db `feedback` 表（服务端记录 IP / UA / 时间 / 主机账号）
                  └─ 本机「留言板」处置（ack / closed + 处置说明，留痕）
                       └─ 按分类汇入改进清单（本文 §4 的度量与节奏）
```

### 2.2 设计要点（都写在代码注释里，此处摘要）

| 要点 | 取值与理由 |
|---|---|
| **域账号** | 填写者**自报**（`account_src=self`），格式校验；将来接 Windows 集成认证/反向代理后由可信头注入（`account_src=header`），**两种来源可分辨**，绝不把自报伪装成已认证 |
| **不可伪造字段** | `ip` / `user_agent` / `created_at` / `host_user` 全部**服务端写** |
| **只追加** | 处置只改 `status/handled_*`，**不删行** —— 删了就失去"问题曾经存在"的证据 |
| **限频** | 同 IP 10 分钟 6 条、同账号 1 小时 12 条（内存计数，重启归零；防刷应上网关） |
| **分类** | `bug / data / feature / other` × 严重度 `low/normal/high/blocker`（受控值，前后端共用） |
| **可写范围** | **仅留言板**；待办处置/留言处置/本地文件/宿主诊断/提交详情**仅本机**（`web/policy.py`） |

## 三、从"一句抱怨"到"一条可验收的改进"

每条留言必须能走完这五步（否则就只是抱怨）：

1. **归类**：`data`（数据质量）→ 进数据缺口台账；`bug` → 进缺陷清单；`feature` → 进需求池。
2. **定位**：写出**可复现的最小证据**（RFN/IPN/文号/接口/时间点）。没有证据的留言，先回问，
   不进入排期（避免"感觉不对"占用产能）。
3. **定验收**：必须写"改完怎么证明"——一条断言、一个 SQL、一张守卫测试。
   > 本仓惯例：**先加守卫测试，再改实现**（`tests/` 里每一组守卫都对应一次真实事故）。
4. **处置留痕**：`feedback_resolve` 写 `handled_by/handled_at/handling`。
5. **回归**：跑对应守卫 + 相关门禁；在 `CHANGELOG` 里写明"对应 FB-xxx"。

## 四、度量与节奏（可持续，不靠人盯）

### 4.1 四个度量（都能从库/门禁直接算）

| 指标 | 定义 | 目标 | 取数 |
|---|---|---|---|
| **反馈闭环率** | `closed / total` | ≥ 80%（月度） | `feedback_stats()` |
| **高危未处置** | `severity in (high, blocker) and status=open` | **= 0** | 同上 |
| **首次响应时长** | `min(handled_at) - created_at`（按 ack） | ≤ 3 个工作日 | 同上 |
| **重复问题率** | 同 `page+kind` 且标题相似度高的新建条数 | 逐季下降 | 留言正文 + 手工归类 |

> 为什么不用"留言数量"当 KPI：**数量上升往往说明入口变好用了**，拿它考核会鼓励"少报"。

### 4.2 节奏

| 周期 | 动作 | 产出 |
|---|---|---|
| **每周** | 扫一遍 `open` + `ack`，把 `data` 类转成数据缺口条目 | 本周处置清单 |
| **每月** | 跑 `feedback_stats()` + 门禁报告，算 4 个度量 | 质量月报（含"本月新增/关闭/积压"） |
| **每季** | 复盘：哪些页签问题最多 → 决定"重做/加守卫/加数据" | 季度改进计划 |
| **每批发布** | 本仓惯例：CHANGELOG 记录"本批修了哪些 FB-xxx / TD-xx" | 可追溯的变更史 |

## 五、与既有质量体系的咬合（不另起一套）

本方案**不新建流程**，而是把留言板接到已有的三套设施上：

| 已有设施 | 咬合方式 |
|---|---|
| **门禁（30 道）** | 每条"数据质量"类留言的验收，优先落成**新判据**（能机器判就不靠人） |
| **tech_debt 台账（TD-xx）** | 结构性缺口登记为 TD（可量化 + 有处置建议），避免只在聊天里飘 |
| **守卫测试（tests/）** | "已修"的最终证据 = 一条会失败的测试变成会通过的测试 |
| **CHANGELOG** | 每批写清"对应 FB-xxx / TD-xx"，形成可审计的闭环 |

## 六、下一步建议（按性价比）

1. **把留言板接到周会**（成本≈0，收益立竿见影）：每周只看"高危未处置"和"重复问题 Top3"。
2. **给 20 条未定位关系补文号**（小时级，收益：图谱可见边从 24 → 40+）。
3. **EAST 资料扩采**：现有 1 条直接相关明显不足；建议把"监管数据标准化规范"历年版本
   作为**专项采集目标**（关键词 + 文号族），并在采集配置里登记，而不是靠 FTS 碰运气。
4. **关系定位率**：这是唯一"影响面大且可量化"的技术债（58.6%），建议单独立项。
5. **治理审计按人检索**：处置动作已留 `resolved_by`，但页面没有"按人/按时间"筛选，
   加一个筛选器即可（半天）。
