## 二、任务一：R-C 按子源拆分

### 2.1 拆分依据（**先量化，再拆**）

`gov` 源原为**单条采集步骤**，内部循环两个子源；实测二者在体量/耗时结构/增量语义上完全不同：

| 维度 | `xzfgk`（行政法规库） | `zhengceku`（国务院政策文件库·部门文件） |
|---|---|---|
| 体量 | 约 **605 条**（主库实测） | **12573 条** / 列表 **629 页** |
| 原增量行为 | 列表**逐页**处理，"整页无新增即停" | `for i in range(n_pages)` **恒扫全部 629 页** ⇒ 单轮空转 **20+ 分钟** |
| 详情跳过 | 条目级 resume（已有则整条跳过） | URL 级：**已有正文**跳过详情；无正文者补抓 |
| 历史存量 | 无此问题 | 有"补正文"需求（须扫全页） |

### 2.2 拆分设计（四条边界 + 一致性落点）

1. **步骤边界**：`COLLECT_CMD` 由 `gov` 一条改为
   `gov_xzfgk` / `gov_zhengceku`（+ 独立 `gov_zhengceku_backfill`）三条 —— 各自 **argv / 超时 / 步骤日志 / 采集统计 / 失败隔离**。
2. **调用兼容（别名契约）**：新增 `COLLECT_ALIAS = {"gov": ["gov_xzfgk", "gov_zhengceku"]}` 与纯函数
   `collect_targets()`；排程 `incremental_weekly` 的 argv（`gov,mof,pbc`）与人工命令**逐字不变**，
   但执行粒度已是**子源级**（`collect:gov_xzfgk` / `collect:gov_zhengceku`）。
3. **数据边界（"整体流程一致"的落点）**：两子源**仍写同一主库** `gov_laws.json`
   （`--resume` 合并、`detail_url` 去重、新优先）⇒ 下游 `clean/apply/classify/…` **零改动**。
   ⚠️ 关键细节：子源单跑会各自写主库**信封** ⇒ 新增 `--env-source/--env-category` 由链侧固定为
   `gov` / `行政法规+部门文件`，避免"最后一个子源"覆盖信封标识（实测最终 `source=gov` ✓）。
4. **超时边界（分档，替代一刀切）**：`COLLECT_TIMEOUT`
   = `gov_xzfgk 1800` / `gov_zhengceku 5400` / `gov_zhengceku_backfill 21600` / `nfra 7200` / `mof 7200` / `pbc 3600`
   —— 原"一律 7200s"会让小源失败也等 2 小时才报。
5. **排程边界**：**周度追新**（`incremental_weekly`，含两子源）与**月度存量补全**
   （新增 `gov_zhengceku_backfill`，`0 1 3 * *`，`--only collect:gov_zhengceku_backfill,clean:gov,apply:gov`）
   **分离** —— 原设计"每日全页扫以逐步补全历史存量"的意图**保留**，但代价显式化、可单独评估与调优。

### 2.3 独立可维护性（可验证）

- 单独调用：`--collect gov_xzfgk` / `--collect gov_zhengceku` / `--collect gov_zhengceku_backfill` 均可独立执行（`--only` 亦可）；
- 单独统计：`data/run_state/collect_stats/gov_xzfgk.json`、`gov_zhengceku.json`（每子源一份）；
- 单独失败隔离：子源异常只记 `failed`，不影响另一子源（`--stop-on-error` 才中止）。
- **测试固化**：`tests/test_gov_incremental.py`（13 项）覆盖别名展开、argv 契约（`--source`/信封）、
  `RAW_JSON` 不含子源键（防 clean 体量超时取错）、超时分档、`--backfill` 必带标志。

## 三、任务二：完善 gov 增量抓取（降低无效时长）

### 3.1 先把"无效时长"定义清楚（可度量）

| 指标 | 定义 | 落点 |
|---|---|---|
| **空转页占比** | `list_pages_without_new / list_pages_fetched`（整页无**新条目**的列表页占比） | 采集统计 |
| **跳过的主库既有** | `details_skipped_master`（因"主库已有正文"而**未发详情请求**的条目数） | 采集统计 |
| **阶段时长** | `elapsed_list_s` / `elapsed_detail_s`（列表 vs 详情归因） | 采集统计 |
| **停止原因** | `stopped_reason ∈ {no_new_items, budget, max_items, end, swept_all, list_fetch_failed, no_items, max_pages}` | 采集统计 |

### 3.2 增量判据（明确到字段）

- **去重键**：`detail_url`（唯一）；
- **跳过条件（不发请求）**：`detail_url ∈ 主库 且 full_text 非空`；
- **新条目判据（驱动翻页）**：`detail_url ∉ 主库（全部已知 detail_url 集）` ⇒ 连续 N 页无新条目即停（默认 N=1）；
- **更新检测**：同一 `detail_url` 再次出现时以**本次记录覆盖**（`merge_with_master` 新优先）⇒ 站点改写可被发现；
- **补正文**：`∈ 主库 但 full_text 为空` ⇒ 仍抓详情（顶部窗口内自然补全；历史深页由月度 `--backfill` 承接）。
- **诚实标注**：本实现是**URL 级 + 正文存在性**判据（非内容哈希/版本号）；列表页排序为**发布日期倒序**是早停的前提，
  已在代码注释与本报告写明（若站点改排序，早停会退化为"仅翻首页" ⇒ 由月度 `--backfill` 兜底，且 `new_items` 长期为 0 可反证）。

### 3.3 去重与跳过（机制）

| 机制 | 实现 | 效果（实测） |
|---|---|---|
| 条目级跳过 | `load_resume` → 主库 `(title, url)` 集（xzfgk） | 13000+ 条**不发请求** |
| 详情级跳过 | 主库 `full_text` 非空集合（zhengceku） | 本轮 25 条命中**全部跳过** ⇒ 0 详情请求 |
| 列表级早停 | `should_stop_paging`（纯函数） | **629 页 → 1 页** |
| 主库合并去重 | `merge_with_master`（`detail_url` 去重，新优先） | 主库 13178 条不变（无重复、无丢失） |
| 续跑暂存清理 | `clear_partial`（**主库写成功后**才删） | 消除"每轮重付 899.7MB/12573 条合并 ~10 分钟" |

### 3.4 异常重试与超时控制

| 层 | 机制 | 依据 |
|---|---|---|
| 请求级 | `urllib3 Retry(backoff_factor=1.5, respect_retry_after_header)`；`--timeout 30`；`--retries 4`；UA 轮换 + 随机延时 | 既有实现（未改） |
| **步骤级（新）** | **软预算** `--max-seconds`：到时**停止取新详情并正常落盘退出**（rc=0，`stopped_reason=budget`） | 撞上层 7200s **硬超时会被强杀**，而未走完的产物仍可能落盘被下游采用（N-152 教训）⇒ 以软预算替代硬撞 |
| 步骤级（链） | `COLLECT_TIMEOUT` 分档（见 2.2-4）+ **链侧显式给软预算**：`gov_xzfgk 1500`（硬 1800）/ `gov_zhengceku 5100`（硬 5400）/ `gov_zhengceku_backfill 21000`（硬 21600） | 软预算 = 硬超时 − **收尾余量**（载入 1GB 主库 + 合并 + 原子写，实测 ≈3~4 分钟）；不设则硬超时**先杀**，软预算等于没用（测试 `test_soft_budget_below_hard_timeout` 固化该不变式） |
| 单条隔离 | 详情失败仅计数 `details_failed` 并继续 | 既有语义 |

### 3.5 监控与评估（"降低效果"如何看）

- **落点**：`data/run_state/collect_stats/gov_{sub}.json`（每子源一份、覆盖写；该目录**未纳入 git** ⇒ 无提交噪声）；
- **为何放这里**：既是**运行状态**同目录（`last_run_steps.json`），又**绝不写 `data/raw/`**（事实源不得混入旁路观测）；
- **评估方法**：对比 `空转页占比`（应长期 ≈0 或 100% 且 `pages_fetched=1`）、`elapsed_list_s`（秒级）、
  `details_skipped_master`（应≈命中数）；若 `new_items` 长期为 0 而 `pages_fetched=1`，说明源确无新条目（正常空跑）。

### 3.6 前后对比（**真机实测**）

| 项 | 旧（批 44：`gov --source all` 单步） | 新（拆分为两步 + 早停） |
|---|---|---|
| 步骤耗时 | **2394.9s（39.9 分钟）** | **113.7 ~ 183.0s（1.9 ~ 3.05 分钟）** |
| 列表翻页 | **629 页**（几乎全空转） | **1 页**（连续无新即停） |
| 详情请求 | 视 pending 而定 | **0**（命中 25 条全部"主库已有正文"而跳过） |
| 空转页占比 | ≈100%（629 页里绝大多数无新） | 100% 但**仅 1 页**（`pages_fetched=1`）⇒ 绝对空转量 ≈0 |
| 主库结果 | 13178 条 | **13178 条（一致，无重复/无丢失）** |

> **净效果：步骤耗时降低约 92~95%，且"无效时长"从"每页 ~2s × 628 页"降为"1 次列表请求"。**

## 七、遗留风险

| 编号 | 事项 | 说明 / 建议 |
|---|---|---|
