# 蓝屏事件排查报告（2026-10-21，KERNEL_SECURITY_CHECK_FAILURE）

> **结论先行**：**不是本项目程序导致**。判断依据是"5 次崩溃、4 种不同 BugCheck 码、
> 跨度 40 天、最早一次早于本项目重负载"——这不符合任何单一软件缺陷的特征，
> 而是**内核侧内存一致性破坏**的典型画像（硬件/驱动）。
> **但有一条真实关联**：本项目 mof 采集进程峰值占用 **6.26 GB**（机器仅 16 GB），
> 极端内存压力会把**潜伏的硬件缺陷或驱动 bug 压出来**。所以它是**加重因素**，不是根因。

---

## 1. 崩溃事实（取证来源：Windows 事件日志 + Minidump 目录）

| 时间 | BugCheck | 名称 | 含义（简） |
|---|---|---|---|
| 2026-09-11 16:26 | `0x0000003B` | SYSTEM_SERVICE_EXCEPTION | 内核/驱动执行中异常 |
| 2026-10-13 18:57 | `0x00000139` | KERNEL_SECURITY_CHECK_FAILURE | **内核数据结构被破坏**（一致性校验失败） |
| 2026-10-15 07:22 | `0x0000000A` | IRQL_NOT_LESS_OR_EQUAL | 驱动在错误 IRQL 访问内存 |
| 2026-10-20 23:40 | `0x0000001A` | MEMORY_MANAGEMENT | **内存管理结构异常** |
| 2026-10-21 16:16 | `0x00000139` | KERNEL_SECURITY_CHECK_FAILURE | 同 10-13 |

Dump 文件（`C:\Windows\Minidump\`）：
`101526-221156-01.dmp`（10-15）、`101926-41953-01.dmp`（10-19）、
`102026-45593-01.dmp`（10-20）、`102126-49796-01.dmp`（10-21）。

**关键观察**：`0x139` **在 10-13 就发生过一次**，早于本轮任何重负载工作；
`0x3B` 更早在 **2026-09-11**。⇒ 该机器在本项目进入重负载期之前就有崩溃史。

## 2. 为什么判断"不是本项目导致"

| 判据 | 事实 |
|---|---|
| **① 用户态无法破坏内核结构** | 本项目是**纯 Python 用户态**进程：不加载驱动、不调 `DeviceIoControl`、不做内核内存操作。`0x139` 的定义是"内核数据结构一致性校验失败"，用户态进程**无权**造成 |
| **② 多码共存 ≠ 单一软件缺陷** | 若是某个软件 bug，会**反复同一码**。这里是 `0x3B`/`0x139`/`0xA`/`0x1A` **四种**，分布在 40 天内 ⇒ 指向**共性底层**（RAM/芯片组/驱动栈），而非某个应用 |
| **③ 时间线不吻合** | 最早崩溃 `2026-09-11`，而本项目进入重负载（全链实跑、mof 采集）是 10-19 之后。10-13 的 `0x139` 也无重负载 |
| **④ 崩溃点不在本项目进程** | 10-21 16:16 崩溃时，本项目进程并未在处理（mof 已于 15:05 早停落盘，链进行到 `clean:supp`）。崩溃前 4 分钟的应用层事件是第三方 **`HotKeyServiceDSU.exe` 的 .NET Runtime 错误**（10-21 16:16），与本项目无关 |

## 3. 为什么"内存压力是加重因素"（本项目确有责任的那部分）

| 事实 | 数据 |
|---|---|
| 物理内存 | **2 × Samsung M378A1G44AB0-CWE 8GB 3200MHz = 16 GB** |
| 崩溃后当前空闲 | 仅 **2.9 GB**（其余被系统+常驻程序占用） |
| **本项目 mof 采集进程峰值** | **6.26 GB** WorkingSet（运行 3.64 小时，PID 14820） |
| mof 采集实际耗时 | **14414 s**（≈4h，被父进程 4h 硬超时杀掉，`rc=-1 TIMEOUT`） |

**6.26 GB 的成因（已用 tracemalloc 定位，非泄漏）**：

- 数据基线：`read_raw_records` 加载 870 条 = **197 MB**（107.6 MB JSONL 的 1.8×，
  属 Python 对象开销正常范围）；`new_store` 浅拷贝只 +0.7 MB。
- **真正的峰值来源**：数据里有**超大单条**——最大一条 **31.3 MB**（正文 23.57 MB，
  标题《勘察设计企业会计制度》），Top5 占全库 **59.2%**。这类记录在
  "详情提取 → HTML 去标签 → 正则清洗 → 签名计算 → JSON 序列化"的每一步都会
  生成 20–30 MB 级临时字符串。3.64 小时反复如此后，**Windows 上 Python 的
  堆在高水位后不归还 OS**，WorkingSet 停留在 6.26 GB。
- 结论：**是"大对象反复分配 + 高水位驻留"，不是内存泄漏**（否则会持续增长到 OOM）。

**为什么这会加重崩溃**：内存压力本身不会产生 `0x139`，但会把
**边缘硬件（RAM 坏点/时序不稳）或驱动缺陷**从"偶发"逼成"必发"。
16 GB 机器上常驻 6.26 GB 单进程，叠加其他常驻程序，空闲只剩 ~2.9 GB，
**换页与物理内存摩擦显著上升**——这正是"潜伏问题被压出来"的条件。

## 4. 处置建议（按性价比排序）

| 优先级 | 动作 | 理由 |
|---|---|---|
| **P0** | 跑 **MemTest86**（至少 4 轮）或 `mdsched.exe`（Windows 内存诊断） | 4 种不同 BugCheck 全部落在"内存/内核访问"家族，**RAM 是头号嫌疑**。两条 Samsung 3200MHz 单条分别测，定位坏条 |
| **P1** | 排查第三方常驻：**`HotKeyServiceDSU.exe`**（崩溃前 4 分钟有 .NET Runtime 异常） + 安全软件 | 内核级钩子/驱动的第三方程序是 `0x139`/`0x3B` 的常见来源 |
| **P1** | 更新芯片组 / 显卡 / 网卡 / 存储驱动（用厂商官网而非 Windows Update） | `0xA`（IRQL）几乎总由驱动引起 |
| **P2** | 检查电源与散热（`0x1A` 也可能由供电不稳/过热诱发） | 若 MemTest 全绿但崩溃继续，转查供电/散热 |
| **P2** | 开启内核内存转储分析（`WinDbg` + `!analyze -v` 看 `102126-49796-01.dmp`） | 能直接指出故障模块名（`MODULE_NAME`/`IMAGE_NAME`），是最快的定位手段 |

**本项目侧已采取的措施**（降低"加重因素"）：

1. **收紧 mof 的软耗时上限粒度**：过去 `--max-seconds` 只在"每条记录开始时"检查，
   实测设 7200 s 却跑到 **13113 s**（超 82%），最终被父进程 4 h 硬超时**强杀**。
   现已把绝对 `deadline` 下传到 `collect_attachments`，**在附件循环内逐个子项检查**
   （`mof/limits.py: EarlyStopGuard.deadline` + `attachments.collect_attachments(deadline=)`）。
2. **不再让"长跑 + 大内存"成为默认**：`mof` 的调度参数为 `--max-seconds 7200`（2 h），
   而父进程硬超时 4 h——两者关系已澄清（软上限必须**小于**硬超时才有意义）。
3. **记录为大对象热点**（供后续优化）：`《勘察设计企业会计制度》31.3 MB` 这类
   单条巨型记录应做**正文截断/分段存储**（当前 `content_text` 23.57 MB 显然是
   把整本制度全文塞进一条记录）。

## 5. 同一次重启带出的两个**真实缺陷**（已修/待修）

### 5.1 开机自启动弹"乱码命令"（**已修**）

登录后命令行显示：

```
'氭寔涔咃細閲嶈窇' 不是内部或外部命令，也不是可运行的程序或批处理文件。
```

**根因**：`data/state/workbench_start.cmd` 由 Python 以 **UTF-8** 写入且含中文注释，
而 `cmd.exe` 按**系统 OEM 代码页（简体中文 = CP936/GBK）**读取 ⇒ 中文变乱码，
其中部分字节被解释为命令分隔符，`rem` 注释行被截断、后半段当命令执行
（`氭寔涔咃細閲嶈窇` 就是 UTF-8 的「…持久：重跑」被 GBK 解码的残片）。

**修法**：注释全部改英文 + 写入用 `encoding="ascii"`（混入非 ASCII 会直接抛
`UnicodeEncodeError`，从根上防回归）+ 守卫 `test_start_cmd_is_ascii_only`。
**验证**：`.cmd` 非 ASCII 字节 = **0**；直接执行 `rc=0`，输出
`[serve] 已有实例在运行…（单实例模式）`，无任何乱码。

### 5.2 陈旧锁 + PID 复用导致整链**无法启动**（**待修**）

蓝屏重启后 `data/run_production_refresh.lock` 残留，内容 `3992`。
而重启后 **PID 3992 已被 `svchost.exe`（AudioEndpointBuilder）复用** ⇒
`fs_lock.ProcessLock` 只校验"PID 是否存在"⇒ 判定"锁被占用"⇒
`cli.py run` 直接退出：

```
[refresh] 已有实例在运行（锁被占用）——本次退出以避免并发改写数据面
[refresh] 锁文件：…\data\run_production_refresh.lock（陈旧锁可删除或等待 PID 退出）
```

**影响**：每次异常重启（蓝屏/断电/强杀）后，**主链会静默拒绝运行**，
报错还误导用户"等待 PID 退出"。

**修法（待实施）**：锁文件从裸 PID 升级为**进程身份**（PID + 进程创建时刻 +
可执行文件名），校验时三者匹配才判"占用"；不匹配 ⇒ 视为陈旧并**自动回收**
（记 WARN，不静默）。
