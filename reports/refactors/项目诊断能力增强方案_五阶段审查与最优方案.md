> **证据纪律**：所有结论附「文件:行号」或真实数据查询结果；无法从代码/数据判定的一律标「待人工确认」，不猜测。

## 审查方法与本次审查的独立性声明

原方案自身给出了「项目已有全部原材料」的映射表（原方案 L14-23）。本次审查**不采信该表的任何断言**，而是对每一条重新以代码与真实数据验证。方法上分五阶段，理由是：

- 没有**现状基线**，无法判断"是否符合需求"（原方案多处把"文件存在"当作"能力可用"）；
- 没有**选型基线**，无法判断"方向是否正确"（例如 `audit_log` 表存在 ≠ 有写入方）；
- 没有**用途基线**，无法判断"能力是否匹配"（优化一个 90 天 35 次的事件，而放着 641 条积压不管，是错配）。

run_step 列: ['run_id', 'step', 'rc', 'exit_code', 'elapsed_s', 'skipped', 'note', 'recorded_at']
elapsed_s 为空: 0/5132      note 为空: 34/5132      记录数列: 无

- ❌ **无记录数列（raw_size/record_count）** → 原方案第一章"边宽编码该环节最近一次处理的记录数"、第二章 `step_regression` 规则的「记录数比上次少 12%」**无台账数据源**

## 1.3 取证入口的真实命名（原方案此处为臆断）

```
reports/_tmp/step_logs/ 实际内容：424 个文件
  样例：analysis_gen_1791498164.out.log / .err.log
  以 "clean_nfra_" 开头的文件：12 个
代码拼的 "clean:gov.log" / "clean_nfra.log" 是否存在：False
```

- 写入方：`tools/run_production_refresh.py:609` `log_dir = os.path.join(ROOT, "reports", "_tmp", "step_logs")`
- 命名规则：`{步骤名去冒号}_{时间戳}.{out|err}.log`
- **原方案 L75 的 `reports/_tmp/step_logs/{spec.name.replace(':','_')}.log` 恒不可达**（既无 `.log` 后缀也无时间戳段）

## 1.4 拓扑事实源的关键结构特征（原方案完全未识别）

```
声明面：STEP_ORDER 32 项，其中含 {src} 模板的 4 项：
  ['collect:{src}', 'clean:{src}', 'relevance:{src}', 'apply:{src}']
运行面：最近一次非 dry-run 运行 run_id=RUN-20261015-060005-25388
  实例步数 = 40，其中仍是模板形态的 = 0
  展开实例（样例）：['apply:gov','apply:mof','apply:nfra','apply:pbc','apply:supp',
                     'clean:gov','clean:mof','clean:nfra','clean:pbc','clean:supp', ...]
GOV_ARTIFACTS 19 键中同样含模板：['raw:{src}', 'clauses:{src}', 'cleaned:{src}', ...]
```

**这是本次审查最重要的发现**：拓扑存在**「声明节点（32，含 4 个模板）」与「运行实例（40，全展开）」两层**，且产物键也模板化。

后果：原方案第三章的硬约束「**步骤名必须有来源 —— `topology_api.get_node()` 查不到即拒绝**」（L293）在真实失败场景下**必然失效**：台账里失败的步骤名是 `clean:nfra`，而声明面只有 `clean:{src}` ⇒ `get_node("clean:nfra")` 返回空 ⇒ 诊断在第一步就自我拒绝。整个第三章的可行性建立在一个错误的假设上。

## 1.5 诊断需求的真实频度（用量化数据替代直觉）

```
全库 rc != 0 的记录数            = 35 / 5132  (0.68%)
近 90 天 rc != 0                 = 35          (全部发生在近 90 天)
近 90 天门禁 FAIL                = 19
最近一次真实运行失败步数          = 0
worklist: open=641 / resolved=9 / dismissed=5   → 处置率 2.1%
worklist open 的 kind 集中度：rfn_theme_uncertain 324 + relevance_boundary 211 = 82%
reports/_alerts 目录             = 不存在（notify 默认后端为 file，见 notify.py:73,111）
audit_log 行数                   = 0
```

- `audit_log` 0 行的原因**不是缺写入路径**：`std_lib/common_lib/governance_store/projections.py:47` 有 `INSERT INTO audit_log(...)`，调用方是 MCP 门面（`mcp_server/registry.py:258` "写级审计落 audit_log"）⇒ **MCP 门面从未被真实调用过**。
- `reports/_alerts` 不存在的含义：notify 自落地以来**从未触发过任何告警落盘**（与「近 90 天 rc!=0 = 35」并存，说明这些失败发生在 notify 落地前，或失败步骤未进入 notify 的 `on` 触发点）。

**基线结论**：项目的"运行期症状"极其稀疏（90 天 35 次步级失败、19 次门禁失败、0 次告警送达），而"治理积压"极其庞大（641 条 open 无人处置）。**这是一个"低故障率 + 高积压"的系统。**

| C2 | 641 条 open 的处置策略 | 需业务判断（批量 dismiss / 分批裁决 / 改判据减少产生），非技术决策 |
| C3 | 是否将 `elapsed_s` 之外的执行元数据（argv/开始时间/记录数）纳入台账 | 涉及 schema 变更与写入方改造，属架构决策（会打破"不改主链"约束） |

## 5.2 最优方案

### 核心判断

原方案的**方向正确、落点过半不可执行**。最优解不是修补它，而是**按真实数据重排优先级 + 修正三处阻断级设计 + 把"没用的自动化"换成"高价值的确定性归因"**。

### 设计取舍（三处关键取舍）

| 取舍 | 选择 | 放弃 | 理由 |
|---|---|---|---|
| **拓扑形态** | **双层节点**（`spec` 32 + `instance` 40，映射由 `{src}` 展开派生） | 原方案单层 `node = StepSpec.name` | 单层在真实失败场景下 100% 查不到节点（B1）；双层只需在 `get_node` 加两级查 + `matched_as` 标注，改动 < 50 行 |
| **根因实现** | **规则化"证据包 + 排序"**，不做自动根因断言 | 原方案的"自动沿链归因 + 置信度" | 无记录数列（B3）⇒"穿透深度"无法量化；自动断言会产出**看似精确实则臆测**的结论，违反项目"不确定标待人工确认"纪律 |
| **Self-Improving** | **复用 `worklist.payload_json` 承载经验六要素**，不新增表 | 新建 `experience` 表 + `memory.py` | 既守"零新增事实源"取向（B6），又让经验可被现有 `worklist list/show/resolve` 直接消费 |

### 方案骨架（四波，按"投入产出比 × 前置依赖"排序）

**第 0 波 · 让信号源真实可用（前置，无新能力，纯修复）**
1. **修 `web/snapshots.py:320` 的日志取证路径**（本审查发现的真实缺陷）：改为
   `glob(f"{step.replace(':','_')}_*.out.log")` 取时间戳最大者，并回退 `.err.log`；
2. **`get_step_log(step)` 抽为 `web/snapshots.py` 的公开函数**（确认台与未来诊断共用同一实现）；
3. **告警落盘面**：在 `notify` 的 `on` 事件中确认 `failed_step`/`gate_fail` 的落盘路径可达（写一个自检：`notify` 模块导入时做一次 dry-run 落盘并断言目录可创建）；
4. **audit_log 写入方**（依 C1 结论）：若人工处置需留痕，则 `worklist_resolve` 增加审计写入；若不需要，则把 `audit_log` 在文档中标注为"MCP 使用量代理指标"，避免下一个人误判为"审计面已覆盖"。

> 交付物：修复 + 自检 + 一页《信号源可用性实测表》（每次门禁运行时自动刷新）。

**第 1 波 · 门禁失败归因（U1，19 次/90 天，`detail_json` 已是结构化证据 ⇒ 成本最低）**
- `tools/gate_triage.py`：输入 gate 名 + 最近 run_id ⇒ 输出「判据类别（产物/结构/口径/环境）× 指向的产物键 × 受影响步骤（沿 `GOV_ARTIFACTS.produced_by` 反查）× 证据摘录（`detail_json.problems` 前 N 条）」；
- **全部结论必须携带 `detail_json` 原文片段**，无证据不出结论（沿用 `argument-strength-evaluation` 的纪律）；
- CLI：`cli.py gates --triage <gate>`（复用现有 `gates` 命令加子选项，不新增命令 ⇒ 守住"命令面不过度膨胀"）。

**第 2 波 · 单步失败取证（U2，35 次/90 天）**
- `interfaces/topology_api.py`（只读门面，遵守"不经门面不取数"）：`get_node`（双层）、`neighbors`、`upstream_chain`、`affected_nodes`；
- `tools/step_triage.py`：输入实例步名 ⇒ ① 双层查节点（`matched_as` 标注）；② 取证包 = `run_step` 最近 N 次（rc/exit_code/elapsed_s/note）+ step_log tail（**修正后的路径**）+ 该步 `produces` 的水位状态；③ 输出**证据包 + 排序后的怀疑清单 + 明确写"未取到证据的项"**；
- 复用 `run_step` 的 `elapsed_s` 做**同源耗时对比**（本步近 5 次 vs 全链同层中位数）—— 这是当前数据条件能支撑的最强定量信号，替代原方案不可实现的"记录数少 12%"。

**第 3 波 · 积压治理优先于经验沉淀（U3，最高价值总量）**
- 先做 `tools/worklist_triage.py`：按 kind 聚合 open 项（当前 `rfn_theme_uncertain` 324 / `relevance_boundary` 211 占 82%），输出「产生方集中度 × 建议批量处置动作 × 是否应改判据从源头减产」；
- **判据源头减产优先于逐条处置**：若某 kind 长期产生大量同类项而实际处置率≈0，正确解法是**修正产生方判据**（如同 `gate_sources_config` 曾堵"纸面 collector"），而非让人去处置 324 条；
- 经验沉淀（Self-Improving）置于本波之后：待处置率恢复（>30%）再启用，且以 `worklist.payload_json` 六要素承载。

**第 4 波 · 视图与接入（最后做，不作为交付判据）**
- 确认台 P9 诊断台（读第 1–2 波的产物，零新增取数逻辑）；
- MCP 资源 `topology` + 工具 `diagnose_step`（只读，进 `mcp_server/resources.py:117` 注册表）；
- `notify` 的 `failed_step` 告警正文追加一行"建议执行 `cli.py gates --triage <gate>` / `step-triage <step>`"。

### 明确不做（附理由）

| 不做 | 理由 |
|---|---|
| 自动根因断言 + 置信度 | 无记录数列（B3）；自动断言会产出臆测结论，与项目"不确定标待人工确认"纪律冲突 |
| 新增 `experience` 表 | 违反"零新增事实源"取向（B6）；`worklist.payload_json` 足以承载 |
| 多源信号关联引擎（第 2 波规模版） | 6 类信号 2 类为空（B4）；应先做第 0 波让信号源可用 |
| 四周起步路径 / 运营指标（`诊断覆盖率>80%` 等） | 属运营层，且在第 1–2 波落地前无可测数据（原方案 L785-795 目标值无基线支撑） |
