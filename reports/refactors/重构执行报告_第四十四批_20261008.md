## 二、U1/U2：根因（**证据链**）

### 2.1 调度层事实（唯一事实源 `config/schedule.yaml` + 已装计划任务）

| 作业 | 频率 | argv | 是否采集 |
|---|---|---|---|
| `refresh` | 每日 06:00 | `cli.py run --no-scrape --resume` | **否**（`--no-scrape`；desc 自陈"raw 已抓取，仅重清洗 + 全链"） |
| `nfra_weekly` | **每周二 01:00** | `cli.py run --collect nfra-weekly` | **是（仅 nfra）** |
| `verify` / `publish_wiki` / `monthly_check` | 周一 07:00 / 周一 08:00 / 每月 1 日 | `--only …` / `cli.py gates` | 否 |
| `gov_increment`（event） | `after: refresh` | `cli.py run --collect gov` | 声明"**已并入 refresh**"——**与 `--no-scrape` 矛盾** |

已装计划任务实测（`schtasks` 5 项）：`refresh` / **`nfra_weekly`** / `verify` / `publish_wiki` / `monthly_check`
⇒ **10-06 恰为周二** ⇒ 当日 01:00 跑的正是 `nfra_weekly` ⇒ **"仅 nfra 采集"与调度完全吻合** ✓

### 2.2 能力层事实（**四源能力早已具备，缺的只是排程**）

| 源 | 采集器 | 增量机制（实测/源码证据） |
|---|---|---|
| gov | `gov_collector.py` | **默认即增量**：`--resume`（基于 out_dir 最新同源输出**跳过已抓条目**）+ `--full` 才全量；`--checkpoint-every 200`；子源 `xzfgk`+`zhengceku` |
| mof | `mof_collector.py` | **记录级指纹 diff 增量**（标题/正文/日期/文号/机关/题注） |
| pbc | `pbc_collector.py` | **断点续跑 + 合并去重**（已存在输出⇒跳过已成功详情；`合并后去重条目数`） |
| supp | （无网络采集器） | 本地通道：投放区 `data/inbox/<域>/` → `inbox_drop` 条件触发；或人工批次 `--supp-batch`（triggers.yaml 明写"**不假装自动**"） |

### 2.3 根因结论（三条）

1. **结构性缺排程**：`schedule.yaml` 中**只有 `nfra_weekly` 做采集**；其余四源**从未被排程**，
   而 `refresh` 明确 `--no-scrape` ⇒ **四源 raw 长期不更新**（实测 raw mtime：gov/mof/pbc 均为 **09-29**，nfra 因周链更新）。
2. **失实声明（纸面接线）**：`gov_increment` 声称"已并入 refresh"，而 refresh 不含采集 ⇒ 读者据手册/README
   会以为"gov 每天增量"，实际**每源都没有定时采集**。
3. **下游依赖被静默悬空**：`refresh --no-scrape` 依赖"raw 已抓取"，而**没有任何作业负责"抓"** ⇒
   整条"采集→清洗→关系→报告"链的**首环缺失**（只有 nfra 每周补一次）。

## 三、U3/U4：修复与验证

### 3.1 修复（`config/schedule.yaml` 新增作业 + 修正失实声明）

```yaml
  - id: incremental_weekly
    kind: cron
    when: "0 1 * * 3"                         # 周三 01:00
    argv: ["cli.py", "run", "--collect", "gov,mof,pbc"]
    on_miss: skip
    desc: "gov/mof/pbc 周度增量采集 + 全链（含报告）；supp 走投放区（inbox_drop 触发）"
```

**四条设计取舍（均为据实推演，非拍脑袋）**：

| 取舍 | 理由（证据） |
|---|---|
| **周三**（而非与 nfra 同日） | `nfra_weekly` 周二 01:00 实测最长 **68 分钟**（10-06 汇总 4096.8s）；同日会**重叠**，而链自带单实例锁 ⇒ 后者**直接退出** ⇒ 该周采集**静默缺失**（比不排程更危险） |
| **不带 `--resume`** | `_resume_plan` 的跳过集 = 「上次 rc=0 的**任意**步骤」（**含 `collect:*`**）⇒ 带 `--resume` 会把**采集本身**跳过，作业形同虚设（与 `nfra_weekly` 的一致做法） |
| **supp 不在 argv** | 它**没有网络采集器**（`COLLECT_CMD` 无 supp）；其增量通道是投放区→`inbox_drop` 触发（每日 06:00 refresh 会评估）与人工批次；**不伪造**"网络增量" |
| **`gov_increment` 改指真实承接者** | 原 `after: refresh` + "已并入 refresh" 与 `--no-scrape` 矛盾；改为 `after: incremental_weekly` 并据实描述 |

### 3.2 途中发现并同步修复：**README 定时表漂移（N-186）**

- **现象**：README §5.2「定时与事件驱动任务清单」自称"由 `gen_schedule_doc` 反向生成、勿手改"，
  但**生成器只写手册**（`reports/运行手册_编排与定时_*.md`），README 实为**手工副本** ⇒ 已漂移：
  **缺新作业**，且仍是 N-51 之前的旧 argv（`--only 6.9` / `--only 21.5`）；而判据 **S4 只守手册**
  ⇒ **无门禁守护**。
- **危害与本命题同源**：读者据 README 会误判"哪个源在采集"（正是本次用户问题的形态）。
- **修复**：① `gen_schedule_doc.py` **同时渲染 README 同一段**（同渲染源、静态表头 + 生成行）；
  ② README 该段加 `<!-- SCHED:AUTO -->…<!-- SCHED:END -->` 标记；③ **判据 S4 扩展到 README**
  ⇒ 漂移即 **CI FAIL**（从"自觉重跑"升级为"机器阻断"）。

| **R-A** | **supp 无网络采集器**（设计如此：表格类人工批次 + 投放区） | 保持"不假装自动"；若需自动，须先定义**来源站点**与其增量语义 |
