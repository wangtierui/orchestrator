# 文档投放入口评估与方案（本地监管文件 / 内部制度 / 相关文档材料）

- 评估日期：2026-10-13
- 触发：用户在《本地Web确认台设计方案》签核时新增第 7 项——评估「本地监管文件、内部制度、相关文档材料的投放也通过工作台作为入口实现是否合理」
- 状态：**已签核**（用户 2026-10-13 确认四项，见 §8 决策记录；随主方案一并纳入《项目最优重构方案》）
- 事实基线：全部基于本仓代码/配置实测，推测处标注「待确认」

---

## 1. 结论（先行）

**「投放」不是一件事，是三类事。结论分三层：**

| 内容类型 | 工作台的正确定位 | 结论 |
|---|---|---|
| 运营者自查（本人检索/核验监管文件与制度） | **检索与预览入口（P7）** | ✅ **合理，做**。读模型现成（`base_api` FTS5 + 各 api 门面），loopback 自用无访问模型冲突 |
| 组织内分发（同事获取文件） | **投放管理看板（P8）**：状态、增量、建议命令——**执行留 CLI** | ✅ 合理，但只做「管理与台账」，**不做文件分发本体** |
| 网页化文档门户（他人直接访问工作台取文件） | 独立演进项目（需局域网+认证+权限，与本轮 loopback 决策冲突） | ❌ 本期**不做**，列为未来方向 |

一句话：**工作台做「投放的大脑」（状态与编排可见），不做「投放的手脚」（文件服务与分发通道）；分发维持既有 wiki 通道，不新开第二个内容出口。**

---

## 2. 既有投放通道盘点（事实基线）

评估「是否合理」必须先看清「现在怎么投的」。本仓已有四类成熟通道：

| 通道 | 机制与证据 | 服务对象 |
|---|---|---|
| **llm_wiki 监控源同步** | `tools/sync_wiki_sources.py`：双底座发布件 → Markdown 文件集（`<rfn>__<title>.md` + YAML frontmatter 溯源 + 正文截断 20000 字符 + **SHA256 增量**，`.wiki_sync_manifest.json` 双端增量）；支持 `--scope external\|internal\|all`；链尾条件步骤 `wiki:sync` 触发 | 组织内知识库（llm_wiki 摄取后供全员检索） |
| **分析交付库** | `cli.py analysis gen` → `docs/reports/` **17 项**交付物 + `_manifest.json`（2.1.1.x 子主题结构/演变/关联/完整性，2.1.2.x 主题总览/关联/演进，2.1.3.x 执行摘要/交叉影响/空白识别/覆盖对照/接口矩阵/趋势预判/行动计划，+关系图谱/RFN 补登清单）；`analysis status` 机器核验在位 | 管理层/合规团队的分析结论 |
| **双底座发布件** | `modules/regulatory_scrapers/published/`（external_records/clauses/attachments/relations + FTS5 索引 908MB）与 `modules/internal_policy_base/published/`（internal_policies/clauses + 索引）；`interfaces/base_api.py` 为唯一读取门面 | 程序消费（查询/检索/下游分析） |
| **制度草稿素材** | `internal_policy_drafter/draft_clause`（条款级对照素材，P8 端到端编排输出） | 制度起草人 |
| 原件层 | `internal_policy_base/originals/`（811 个硬链接，`gate_flat_layout.py:29-30` 记载迁移后硬链接保持有效）；`data/docs/<scraper_slug>/`（五源正文原文/附件） | 本地存档/核验 |

**关键观察**：组织内「获取监管文件与内部制度」的既有出口已经是 **wiki 通道**（2026-09-12 知识层接入 §6.2），它天然解决了三件事：组织内检索、摄取侧的版本/增量（SHA256 双端）、以及「人和内容分离」的访问模型。**新增任何投放入口，都是在加第二个内容出口**——这与本仓「唯一事实源/单一出口」纪律直接冲突。

## 3. 三个候选定位的评估

### 定位 A：工作台作为「组织内文档门户/文件服务器」（投放本体）

| 维度 | 评估 |
|---|---|
| 受众访问模型 | ❌ **根本冲突**：投放的受众是组织内他人，工作台已签核为 **loopback-only**（用户 2026-10-13：不需局域网+token）。要服务他人就必须开放局域网 + 认证 + 权限分级——等于推翻已确认的设计前提 |
| 内容形态适配 | ❌ 三类投放物形态各异：结构化记录（JSONL）、**原件大文件**（PDF/DOCX，originals 811 件 + data/docs 附件）、报告文档（17 项 md）。HTTP 服务大文件既非控制台职责，也带来目录遍历/下载审计等新攻击面 |
| SSOT/出口数量 | ❌ 又多一个内容出口（wiki 之外），版本口径可能分叉——本仓 23/24 道门禁计数漂移的教训正是「多出口必漂移」 |
| 安全与审计 | ❌ 无用户体系即无「谁看了什么」的审计；监管文件+内部制度同屏服务，缺权限隔离 |
| 成本 | ❌ 高：认证/权限/文件服务/审计全套，且与 loopback 决策冲突 |

**结论：不合理，不做。**

### 定位 B：工作台作为「投放编排与台账看板」（管理入口）

| 维度 | 评估 |
|---|---|
| 受众访问模型 | ✅ 使用者就是运营者本人（loopback 自用），与已确认设计完全一致 |
| 价值 | ✅ 解决真实盲区：现在「投没投、投了什么、增量多少」要翻 manifest、跑 status、比对指纹——分散在三处；看板一屏掌握，并把「待同步增量数」算出来（发布件指纹 vs `.wiki_sync_manifest.json` 差集） |
| SSOT | ✅ 只读展示 + 给命令，不新开出口、不双写 |
| 成本 | ✅ 低：数据源全部是既有产物文件，无新查询逻辑 |

**结论：合理，做（P8）。**

### 定位 C：工作台内「文档检索与预览」（运营者自查入口）

| 维度 | 评估 |
|---|---|
| 受众访问模型 | ✅ loopback 本机自查，无冲突 |
| 价值 | ✅ 高：处置 worklist 时（如 `rfn_theme_uncertain`）需要顺手查该 RFN 的原文/主题/时效/关系——现在要开多个 CLI 命令；检索页把「确认台 → 原文核验」闭环在一屏内，直接服务 P4 闭环台的影响面预览 |
| 实现成本 | ✅ 低：全部经 `base_api.search_external/search_internal/query_*/get_*` 既有门面（FTS5 索引已建成），零新查询逻辑、零新依赖 |
| 边界 | ⚠️ 原件文件不做 HTTP 服务，走 file 协议直开（用户确认），路径白名单生成 |

**结论：合理，做（P7）。**

## 4. 分类型投放结论

| 投放物 | 组织分发维持现状 | 工作台新增 | 理由 |
|---|---|---|---|
| **本地监管文件**（external_records/clauses/attachments/relations + 原文附件） | wiki 通道（`sync_wiki_sources --scope external`，截断+frontmatter+增量） | P7 检索预览 + P8 wiki 同步看板 | wiki 已覆盖组织检索；原文大文件走文件通道，不进 HTTP |
| **内部制度**（internal_policies/clauses + originals 原件） | wiki 通道（`--scope internal`） | 同左（P7 双库同搜） | 同上；原件 811 硬链接已有稳定文件位置 |
| **相关文档材料**（17 项分析交付、草稿素材、运行台账/报告） | `docs/reports/` 交付库（`analysis gen`）+ 文件共享 | P8 交付库状态卡（`analysis status` 图形化：17 项在位/缺失/生成时间） | 交付库有 manifest 机器核验；工作台只做状态可见 |

## 5. 方案设计（P7 + P8，已并入主方案 §5）

### P7 文档检索与预览（只读）

- 搜索框同查双库（`search_external`/`search_internal`，FTS5 trigram）；精确过滤：rfn / document_number / source / theme / timeliness_status；
- 详情页：正文渲染 + 元数据卡（文号、发布/生效日、时效三态 R13、核验来源、URL、record_id）+ 关联（clauses 条目、relations 边、RFN 登记，经 `clause_index_api`/`relations_api`/`rfn_api`）；
- 原件入口（**file 协议直开**，用户确认）：展示规范路径 + 「打开原件」链接（`file:///...`，新标签页，操作系统关联程序接管；loopback 本机可用；**不做 HTTP 静态目录暴露**；路径白名单生成、禁用户输入拼路径）；
- 与 P4 联动：闭环台详情区的「影响面预览」直接复用本页检索能力（同一 API 同源）。

### P8 投放管理看板（只读 + 可复制命令）

| 卡片 | 数据源 | 内容 |
|---|---|---|
| wiki 同步状态 | `reports/_wiki_sources/.wiki_sync_manifest.json` + `reports/llm_wiki_upstream_state.json` | 已同步条目数、上次同步时间、**待同步增量数**（发布件当前指纹 vs manifest 差集，机器算出）、`--prune` 候选（源已删而 wiki 源残留）、llm_wiki 上游连通状态（`tools/check_llm_wiki_upstream.py`） |
| 分析交付库状态 | `docs/reports/_manifest.json` | 17 项在位/缺失、生成时间、行数（= `analysis status` 图形化） |
| 双底座发布件新鲜度 | `base_api.manifest()` + `governance_api.watermarks()` | 快照日、计数、sha256、schema_version；与上游水位差（stale → 提示重发布） |
| 投放台账 | **结构化台账**（用户确认「后者」）：`tools/sync_wiki_sources.py` 与交付库生成器（`cli.py analysis gen`）每次执行落一行 JSONL（时间/scope/条目数/增量数/prune 数/结果）至 `data/run_state/delivery_ledger.jsonl` | 每次投放可查、可审计；与 `.wiki_sync_manifest.json` 指纹、run_log 的 wiki:sync 记录互相校验 |
| 建议命令卡 | 按状态静态生成 | 可复制命令（`python tools/sync_wiki_sources.py --scope all` 等），执行留 CLI |

> ⚠️ **既有缺陷提示（影响投放触发，非本方案引入）**：《全面检视与重构审查报告》阶段四 D-1 已实证——`triggers.yaml` 的 `publish_manifest_changed` 条件观察 `modules/base_publish/published/publish_manifest.json`，而实际发布清单在 `modules/regulatory_scrapers/published/` 与 `modules/internal_policy_base/published/` 下，该文件不存在 → wiki:sync 条件判定恒「不满足/不判定」（2026-10-12 台账 note 实证）。**P8 看板的「待同步增量数」恰好可作为该缺陷修复前的替代触发依据**（增量>0 即提示执行 sync 命令）；修复 D-1 后看板与链路触发互为校验。

## 6. 为什么不合理的展开：若未来确需网页化门户

正当形态是**独立的文档门户项目**（非本工作台），前置条件与工作台解耦：

1. 网络暴露（局域网/反向代理）+ 认证（AD/SSO）+ 按密级/主题的权限隔离；
2. 文件服务（大文件分片/断点/下载审计）；
3. 与 wiki 通道的职责重划（门户做精读、wiki 做检索，或门户取代 wiki——需组织决策）；
4. 届时工作台 P7 的检索 API 可**原样复用**为门户后端（同源 `base_api` 门面），本期投入不浪费。

在那之前，把门户功能塞进 loopback 工作台，是用一个错误的设计同时破坏「控制台定位」和「投放通道单一性」两个纪律。

## 7. 风险与边界

| 风险 | 缓解 |
|---|---|
| 看板数据与 CLI 口径不一致 | 全部读既有产物文件/门面（manifest、status 同源函数），不新算第二套 |
| 「待同步增量数」计算开销（全量指纹比对 900MB 索引） | 只比对 `publish_manifest.json` 的 sha256/计数/快照日（发布件级，非记录级），毫秒级；记录级差集仅在用户显式点击「计算增量」时执行 |
| 原件路径直开的安全性 | 路径一律经 `paths.py` 注册目录白名单生成，禁用户输入拼路径（防遍历） |
| 投放台账数据缺失 | 已按用户签核采用**结构化台账**：`sync_wiki_sources.py` / `analysis gen` 每次执行落一行 JSONL 至 `data/run_state/delivery_ledger.jsonl`（各 <20 行改动）；与 manifest 指纹、run_log 三方互相校验 |
