# 本地确认台是否引入 Dash —— 选型评估与最优方案（2026-10-22）

> **结论先行**：**不引入 Dash 作为工作台框架**（否决方案 B）。
> **最优方案 = 方案 C（按需增强）**：保留现有**零依赖 + 单文件前端**架构；
> 若确实需要交互式图表（缩放/悬浮/联动），**只引入 `plotly` 这一个库**并在仓内
> 本地托管 `plotly.min.js`，**不引入 Flask/Dash**。
> 依据不是"习惯"，而是下面这组实测数字与三条硬纪律的冲突。

---

## 1. 现状基线（实测，非估计）

| 指标 | 现状 |
|---|---|
| 工作台总代码 | **2450 行**（`web/*.py` 1671 + `assets/index.html` 779） |
| 前端资产 | **单文件 46.9 KB**（零 CDN、零构建、手绘 SVG） |
| 运行时依赖 | `pyproject` 声明 **15 项**（**无任何 Web 框架**：`http.server` 标准库） |
| 锁文件 | `requirements.lock` **137 行 / 116 包** |
| 页面 | 8 页（P0 总览 / P1 数据流转 / P2 数据状态 / P3 指标 / P4 待办闭环 / P5 治理审计 / P6 文档检索 / P7 投放看板 / P8 发布事件流） |
| 性能（治理后） | `/api/overview` 冷态 **118 ms**、`/api/worklist` **107 ms**、`/api/assets` **3.5 ms**（修复前 22163/7613/5965 ms） |
| 运行约束 | loopback-only、无鉴权、单实例锁、日志落盘、开机自启动（计划任务 + `pythonw`） |
| 既有守卫 | `test_console_perf_flake.py`(10)、`test_confirm_console.py`、`test_p3_contract.py`(7)、`test_workbench_service.py`(17)、`test_js_syntax.py` |

**关键事实**：这套东西**当前不依赖任何 Web 框架**，且已把"冷态 22 秒"这种真问题修到
118 ms。也就是说——**"渲染不好"不是框架能力不足造成的**，而是具体画法缺陷
（标签溢出画布、分布集中被误读），上一批已按契约逐个修掉并加了守卫。

## 2. Dash 的真实成本（`pip --dry-run --report` + wheel 实测）

### 2.1 依赖树

`dash==4.4.1` 解析出 **28 个发行包**，其中相对现有锁文件**新增 16 个**：

```
dash  Flask  Werkzeug  plotly  pydantic  pydantic_core
janus  nest-asyncio  retrying  blinker  itsdangerous
annotated-types  typing-inspection  importlib_metadata  zipp  comm
```

（`requests`/`urllib3`/`certifi`/`charset-normalizer`/`setuptools`/`packaging` 等已在仓内。）

### 2.2 体积

| 组件 | 大小 |
|---|---|
| `dash-4.4.1` wheel | **8.53 MB** |
| `plotly-7.1.0` wheel | **9.24 MB** |
| `flask` + `werkzeug` + `pydantic` | 0.79 MB |
| **安装载荷小计** | **≈ 18.6 MB** |
| dash wheel 内 JS（含 dev + sourcemap） | **33.21 MB** |
| plotly wheel 内 JS | **18.58 MB** |
| 前端运行时**实际需下载**（min 版） | `dash_renderer.min.js` + dcc/table bundles + `plotly.min.js`(4.59 MB) ≈ **6–8 MB** |

对比现状：前端 **46.9 KB**，**增加约 130–170 倍**。

### 2.3 离线与"零 CDN"纪律

**结论：离线可行**。Dash 自带 `dash_renderer`/`dcc`/`dash_table` bundle，由自身
Flask 应用在 `/_dash-*` 与 `/assets` 提供，**不需要公网**。
但必须**明令禁止** `external_scripts` / `external_stylesheets` 指向公网 URL
（否则一条配置就能把"离线可用"打穿，而现有门禁 `gate_config_integrity/_js.py`
只约束**我们自己的** HTML，管不到 Dash 运行时注入的标签）。

## 3. 三条硬纪律 vs Dash

| 纪律 | 现状落实 | 引入 Dash 后 |
|---|---|---|
| **零新增依赖**（SBOM/lock/CVE 门禁 D7） | 15 项运行时 / 116 包锁 | **+16 包**（Flask 全家桶 + pydantic-core 二进制）⇒ 锁、SBOM、`pip-audit` 基线全部要重录，**供应链面扩大 14%** |
| **不裸读数据**（一切经 `interfaces/`） | 全部取数经 `*_api` | Dash 回调里**极易**直接 `sqlite3`/读文件（框架心智就是"回调里随手取数"）⇒ 需为每个回调重写一层门面调用，**守卫要跟着改成"扫描 dash callback 函数体"** |
| **单文件前端 / 零构建** | 1 个 46.9 KB HTML | 需管理 `assets/` 目录、组件依赖、`dash_table` 样式；**"零构建"退化为"由框架代管"**（可控性下降，排障需懂 Dash 生命周期） |

另有一条**隐含成本**最容易被低估：

> **现有 2450 行不是"页面代码"，而是"纪律代码"**：`_scrub`（11 类密钥脱敏）、
> loopback 校验、单实例锁、日志双写、`warming` 语义、分级 TTL 缓存、
> 每个数据源故障只影响单卡片的 `_degrade`、SSE 事件流、写路径唯一性（只允许
> `worklist_resolve`）。**换框架 = 这些全部重写一遍并重新验证**。

## 5. 最优方案（C）的具体形态

### 5.1 分阶段，先"验证价值"再"增加依赖"

| 阶段 | 动作 | 依赖增量 | 可回退 |
|---|---|---|---|
| **C0（现在）** | 维持手绘 SVG + 已修的画法缺陷 + P3 契约守卫 | 0 | — |
| **C1（需要时）** | 仅对"真正需要交互"的页面（P3 指标），用 **`plotly`（Python 侧）** 生成 `figure` JSON，前端用**仓内托管的 `plotly.min.js`** 渲染 | **+1 库**（`plotly`，MIT） | 删一个 `<script>` + 一段渲染代码即可 |
| **C2（若 C1 证明价值）** | 评估是否把 `plotly` 纳入 `[console]` extra（**可选依赖**，不影响主链 CI） | 同上，且**不阻塞**主链 | 环境变量开关 |

### 5.2 为什么"只加 plotly、不加 Dash"

- 我们要的是**图表能力**（scale/zoom/hover/linkage），不是**应用框架**；
- `plotly.min.js` 4.59 MB **一次性本地加载**，之后零网络、零 CDN；
- 不引入 Flask/Werkzeug ⇒ **现有 stdlib 服务端、SSE、单实例、日志、脱敏全部不动**；
- 不引入 pydantic-core（二进制）⇒ SBOM/CVE 面不变。

### 5.3 如果将来**确实**要上 Dash：必须同时满足的 6 个前置

1. 以 **`[console]` 可选 extra** 引入（`dash` 不进运行必需依赖，CI 主链不装）；
2. 锁文件与 SBOM 重录，`pip-audit` 基线更新，**并在 CHANGELOG 说明"依赖面扩大"**；
3. `external_scripts/stylesheets` **禁止公网**，并加一条守卫**扫描 Dash 配置**（现有 `_js.py` 只管自家 HTML）；
4. 所有回调取数**必须经 `interfaces/*_api`**，并加守卫断言"callback 函数体不出现 `sqlite3`/`open(`/`os.walk`"；
5. 逐条迁移现有纪律：`_scrub`、loopback、单实例锁、`--log-file`、`warming`、`_degrade`、
   写路径唯一（`worklist_resolve`）、SSE（Dash 需自建路由或退化为 `dcc.Interval` 轮询）；
6. 性能门槛不变：8 页冷态任一 **< 5 s**（现 118 ms），并由 `test_console_perf_flake.py` 继续守。

> 满足这 6 条后 Dash 才"可用"；而满足它们的工作量 ≈ **重写 2450 行 + 返工 34 项守卫**。
> 这就是本方案把 B 排在最后的量化理由。

## 6. 影响与验收

| 项 | 方案 C 的影响 |
|---|---|
| 主链/采集/清洗 | **零影响**（工作台不在链上） |
| 门禁 | 无新增判据；`plotly` 若纳入 extra，仅 `D7/SBOM` 计数 +1 |
| 现有守卫 | 全部保持；C1 需新增 1 条"图表 JSON 字段契约"守卫（复用 `test_p3_contract` 的思路） |
| 交付节奏 | 可按页增量，单页 < 1 天 |
| 回退 | 删 `<script>` + 渲染函数，**无数据/接口变更** |

**验收标准（C1）**：
1. 页面首屏仍在 5 s 内；2. 无公网请求（`netstat`/DevTools 可验）；
3. 数据仍只来自 `interfaces/`；4. `plotly.min.js` 随仓托管且有 SHA256 记录；
5. 关闭 C1（删脚本）后页面**不白屏**（优雅降级为表格）。

---

## 7. 一句话总结

**Dash 解决的是"没有框架"的问题，而我们没有那个问题。**
我们有的是"具体画法缺陷"——已经用契约守卫逐个修掉（P3 三次返工的根因就是
"前端读的键 ≠ 后端给的键"，这与框架无关）。因此：
**保留零依赖骨架；需要交互图表时，只加 `plotly` 一个库、本地托管 min.js；不引入 Dash。**
