## 二、逐项详述

### N-60 / N-61 · 计划任务：改了 yaml，系统仍是旧版

**事实**：第十批把 `schedule.yaml` 的 `verify`/`publish_wiki` 由**阶段号**（`--only 6.9`/`21.5`）改为**步骤名**，
但**未重装**计划任务 → Windows 侧仍执行旧 argv（**空跑**）。而 `cli.py schedule list` **读 yaml**
（非系统），故 `list` 显示"新命令"、**漂移不可见**。

**修复**：① `schedule install` 重装（5 任务）；
② `schedule verify` **纳入 CI**——它本就实现了 `installed_argv()`（`schtasks /query /v` 解析）
+ 与 yaml 的 argv 比对，只是**从未被 CI/链调用**（仅 doctor/status）。
③ 同时修 `verify()` 的平台语义：`schtasks` 不可用（非 Windows）→ 自报 `skipped`（原实现会把
全部任务判"未安装" → Linux/CI **假 FAIL**）。

### N-63 · 治理库"阶段 1"从未入链

`tools/governance_register_artifacts.py` 自述"**阶段 1**（原件注册：`sha256[:16] → path_keys 集合 +
inode + 字节数`）"，而链内只有**阶段 2**（`governance:sync` 元数据四表投影）→ 阶段 1 **无任何调度**
（`STEP_ORDER` 与 `triggers.yaml` 皆无）。后果：`artifact` 表**不随原件库变化刷新**。

**修复**：入链为 `governance:artifacts`，位置在 `internal:update`（原件库变化源）之后、`governance:sync` 之前
（**其自身的分期语义**）。首次执行登记 **1601 件 / 库内 1595 行**（6 行为跨层硬链接的同内容多路径，
正是其 `path_keys` 集合建模的用途）。

### N-64 · `governance:sync` 早于其生产者（一轮延迟）

`governance:sync`（阶段 2）投影 `document` 的 **internal 侧**自 `internal_policy_index.json`，
而该文件的生产者 `internal:update` 在链中**更靠后** → 原顺序使 `internal:update` 真正执行的
**那一轮**投影到的是**上一轮索引**（落后一轮）。修复：把治理库双阶段整体后移至 `internal:update` 之后。

### N-64b · 门禁清单解析脆弱性（由 N-63/N-64 的注释触发暴露）

新增步骤时我在 `STEP_ORDER` 内插入多行说明，其中含**半角括号** `document(internal)` →
`gate_config_integrity._tuple_of_quotes()` 的"**遇 `)` 结束**"把它当成清单边界 → **清单被截断**
（实测 24 项只解析出 **13** 项，判据 R 误报 11 项"未登记"）。
**修复**：解析循环**跳过行内注释**（清单项名不含 `#`，且引号已先行整段跳过，故循环内所见 `#` 必不在引号内）。

### N-58 · 核验与勘误（第十批"撕裂"判断不成立）

逐条核验：`_ingest_state` 878 条目中 **processed 主记录缺失 = 0**、同 IPN 多 sha（**真去重**）= 17
→ `878 − 17 − 0 = 861` 与索引 records **完全自洽**。即**索引写入本就原子、无撕裂**；
"processed 1 522 IPN" 是**历史 IPN 重命名遗留的孤儿**。
**修复**：`stat` **分列** `deduped_duplicates`（去重）与 `missing_processed`（**真断裂信号**，非空即告警）——
原实现把二者合并，正是本次误判的诱因。**并已在第十批报告补"勘误"节**。

### N-59 / N-62 · clause_graph 复核精度

- **N-59**：复核增"**条号超出目标文件条款总数**"判据（`n_articles`）→ `art_check` 四态受控值；
  诊断结论：**`out_of_range = 0`**（正则抽出的条款号无超范围错误）。
- **N-62**：抽查发现 24 条"可疑"边的真因是**形态差异**——`art` 为阿拉伯（如 `'133'`，来自《保险法》第133条），
  而目标条款表键为中文（`'一百三十三'`）→ 仅比 `by_norm` 必然不匹配。补 `by_no`（`articles[].no`）
  兜底后：**`verified` 139 → 163、`in_range_unmatched` 24 → 0**（其余 70 为 `no_table`）。

## 五、遗留风险

1. **`timeliness:verify` / `wiki_sync` 仍需外部条件**：前者需北大法宝 Token（+ 距上次核验 ≥7 天），
   后者需 vault 可达 —— 属**用户侧**，本轮已把"条件判定 + argv 形态 + SKIP 入账"验证到位。
2. **`governance:artifacts` 首次入链的耗时**待观察（879 + 1601 件扫描；本轮实跑在分钟级），
   若后续成为瓶颈可评估增量（按其 `--limit` 支持）。
3. **`graphify_sync` 未装 hook（N-65）**：开发工具（图谱与 HEAD 一致），**不属数据管道**；
   是否接线由使用者决定（是否使用 graphify）。
4. **`retention.py` 未入链**：其设计为**默认 dry-run 的人工策略工具**（"策略声明化 + 可审计"），
   故保持链外；若希望"周期出清理计划"，可后续以**非破坏模式**（dry-run 报告）入链。
5. **`.git-blame-ignore-revs` 仍未启用**：属 git 本地配置（`blame.ignoreRevsFile`），
   按纪律不由工具改写用户 git config。
6. **历史层 mypy**：`follow_imports="silent"` 排除 `scraper_std`/`modules`（owned 层已 0 error 且转阻断）；
   历史层收敛属长期工程。
