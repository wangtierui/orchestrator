## 3. 设计要点（相对参照实现的适配，逐条可审计）

1. **七层结构保留**：`RelationConfig`（词表全外置，换领域只换配置）→ 工具函数 → 三个 dataclass →
   `RelationExtractor`（六类主模式 + 三类辅助）→ `AliasResolver` → `RelationPipeline` → CLI/自检。
2. **归一收口到项目 SSOT**：名称归一用 `norm_title_strict`（保守层，与归属表精确匹配同语义）、
   文号归一用 `norm_docno`；**不另造归一**（参照实现自带一份）。
3. **枚举收口**：`basis_type` 由中文「实体法律依据/程序批准依据」改为受控英文
   `substantive`/`procedural`（项目纪律：受控值统一小写英文），`scope`→`whole/partial/attachment`、
   `action`→`repeal/invalidate/cease/inapplicable/cancel`。
4. **文号形态扩展**：支持法规库形态（`中华人民共和国国务院令第262号`、`令2011年第N号`）与
   半角方括号（`[2019]19号`）。
5. **否定/未生效排除（新增）**：`拟废止/建议废止/征求意见/草案/待废止` 语境不计废止关系
   （真实语料中 `replacement_document` 邻近文本常含"拟"，参照实现无此防护 → 会误报）。
6. **来源偏移 `offset`**：每条关系记录正文命中位置（参照实现只有片段），便于审计定位。
7. **未解析不臆造**：目标无法定位时保留原文名称 + `matched_by="unresolved"` + `confidence=0`，
   与 drafter `verify_regulatory_citations` 的"禁止臆造"同纪律。
8. **程序性依据收紧（实测反例驱动）**：参照实现用 `经[\u4e00-\u9fa5]{2,20}?同意/批准` 最短匹配，
   实测产出 `批准或者未按照`、`依法`、`部门负责人` 等非机关噪声；现要求**法定机关后缀**结尾
   且**不含连接虚词**（全量关系数因此由 82（30 份样本）降噪到 38）。

## 4. 实体解析：两级口径（这是数据可信度的核心）

关系目标的解析分两级，**字段显式区分**，避免"解析率"歧义：

| 字段 | 语义 | 用途 |
| :--- | :--- | :--- |
| `dst_ref` | **强实体**：`RFN`（归属表，1060 → **1155** 条，见 §9.3 补登）/ `IPN`（内部主索引 878 条） | 可直接 join 归属表、底座、发布件、门禁 |
| `dst_key` | **弱引用**：cleaned `dedup_key`（4043 份采集全集） | "已采集但未登记 RFN"的补登记线索 |
| （皆空） | `unresolved` | 名称未在语料中定位（多为《民法典》等未入库法规）→ 保留原文供人工/法规库补全 |

**匹配顺序**（严 → 宽）：`docno_exact` → `docno_sig` → `title` → `title_contains`；
**跨域（内部→监管/内部）一律 `strict`（禁 `title_contains`）**——实测
`中华人民共和国发票管理办法`（法规）会被 contains 误配到内部制度 `…发票管理办法`，把法规当制度。

实测结果（全量 2152 条）：

| 口径 | 值 |
| :--- | ---: |
| 强实体（`dst_ref` 非空） | **25.7%** |
| 语料定位（含弱引用） | **52.7%** |
| 未解析 | 1018（47.3%） |

> 未解析者集中在"被依据的是法律/行政法规"（如《中华人民共和国银行业监督管理法》《民法典》），
> 而归属表只覆盖 **1060 份与人寿保险业务相关的文件**——这是**客观交集限制**，不是抽取缺陷。
> 该部分数据对下游仍有价值（名称 + 出处片段 + 源实体），并可经法宝库/人工补登后自动升级为强关联。

### 9.3 提升路径①：RFN 补登（`dst_key` 线索 → 强关联）

**新增 `tools/rfn_backlog.py`**：从 `dst_class=corpus` 的关系聚合补登候选（去重文件 + 被引次数 +
引用者 + 权威元数据 from cleaned），并给出**主题建议**（三种依据，禁臆造）：

| `decision` | 口径 | 数量 |
| :--- | :--- | ---: |
| `law_to_t0` | 法律/行政法规形态 → **T0 上位法锚点**（项目主题体系既定语义；此类**不**用投票——实测《商业银行法》会被引用者投成 T1） | 80 |
| `votes` | **引用者主题投票**（须唯一最高票） | 15 |
| `uncertain` | 无票／并列／形态不明 → 须人工裁决 | 75 |

**处置**（经 `rfn.register_doc` 唯一写口，幂等 + 自动备份）：

```
候选 170 个 → 登记 95 个（registered 95 / 失败 0）→ 归属表 1060 → 1155
重跑 relations gen → entity 552 → 1044；file_resolved_ratio 31.5% → 59.5%
补登清单收敛：170 → 75 个（余 73 个待人工裁决）
```

**⚠️ 踩坑（重要教训）**：补登后必须处理时效状态——`register_doc` 按设计把新行置 `pending`
（"登记即待核验"），但补登文件**可能已在时效核验 SSOT 中** → 归属表 `pending` 与 SSOT 冲突，
`gate_timeliness_ssot` FAIL。首次尝试调用官方 `verification_state.sync_to_classifier` 修复，
**但该函数的标题匹配是子串包含**（`needle in 归属表.文件名称`），在 3000+ 记录规模下
**误命中并改错 1000+ 行既有状态**、引入大量新漂移。改用**与门禁同口径的键匹配**
（`state_key(发文字号, 文件名称)` 精确查 SSOT，命不中即不改）后仅需改 6 行即收敛。
**教训：跨模块"批量回写"必须用对方的事实源键做精确匹配；宽匹配的批处理在规模上是破坏性的。**

- **无门禁覆盖**：`gates/` 中**无任何**校验交付库的门禁（`gate_flat_layout` 仅把 `docs/reports` 列为
  允许子目录）→ 未登记属**静默游离**，不会被门禁发现。
- **无回归风险**：生成器 `_write()` **只写文件 + 追加 manifest 条目**，无 `glob/listdir/unlink/清理` 逻辑
  → 两份未登记报告**不会被误删或覆盖**（今日 `classify --all` 尾部自动跑 `analysis gen`
  后仍在位，已实证）。
- **状态检查不纳管**：`cli.py analysis status` 只做 **manifest 概览 + 文件缺失检查**（在位校验），
  **不校验 sha、不查目录内多余文件** → 现报"全部交付物在位"，游离文件既不被报缺失也不被报多余。
- **报告非字节确定**：两份报告头部均带**生成时间戳**（实测 `生成于 2026-09-14 01:12:21 / 01:12:39`），
  `extract_relations` 还写入 provenance（`generated_by/generated_at`）→ 每次重跑 sha 必变，
  **manifest 的 `sha256_16` 登记对它们只有血缘留痕意义，不能作一致性判据**（立项方案需据此设计）。
- **当前未陈旧**：派生报告 mtime（01:12:35 / 01:12:39）**不早于**事实源 `relations_index.jsonl`（01:12:35）→ 内容与事实源一致 ✓

### 10.3 真实缺口与建议路径

- **缺口**：`cli.py analysis gen` 不产出这两份 → 数据重建后**不随交付库自动刷新**，
  需人工记得单独重跑（`tools/extract_relations.py --report` / `tools/rfn_backlog.py`）；
  且游离于 manifest 之外，异机克隆/交付验收时不在"2.1 交付库 15 项"口径内。
- **建议（低风险路径，与原"改动风险高"的判断不同）**：**追加式**新增 2 个生成函数，
  复用既有 `_write()` 写入 + manifest 登记，**不改动既有 15 份的内联实现** →
  实为"新增"而非"重构"，风险可控；若需 sha 稳定，登记时可只落 `file/lines/chars`
  或先做时间戳外置（同一改造顺带解决）。
- **触发条件**：当出现"交付库需整库交付/异机复现"或"关系类报告需随库刷新"的诉求时立项。

## 11. 收口：sha 口径统一 + 关系类报告「随库刷新」（2026-09-14）

### 11.1 `sha256_16` 统一切换为**文件字节**哈希

- 改动：`tools/gen_analysis_deliveries.py::_write` 的
  `hashlib.sha256(content.encode("utf-8")).hexdigest()[:16]` → **`_sha16(落盘文件)`**（复用既有二进制读工具）。
- 理由：原口径是"正文串（LF 归一）"哈希，与磁盘字节不符（Windows 行尾转换）→ **不能作一致性判据**；
  统一后平台无关、可直接比对；dry 模式不落盘 → 置空（与原行为一致）。
- 实测：重新生成后 **17/17 项 manifest sha 与磁盘字节完全对齐**；新增用例
  `test_write_registers_disk_byte_sha`（代码级）+ `test_manifest_sha_matches_disk_bytes`（数据级）守住口径。

### 11.2 关系类报告「随库刷新」——此前**只有纳管、缺刷新链与陈旧检测**

§10.4 完成的是"能随 `analysis gen` 重建"，但**关系产物本身**并未接入生产刷新链、且门禁不查新鲜度，
于是存在一条静默链路：**数据更新 → 关系产物陈旧 → 报告"刷新"了却反映旧数据**。本段补齐两处：

| 措施 | 位置 | 作用 |
| :--- | :--- | :--- |
| **新增刷新链阶段 2.6 `relations:gen`** | `tools/run_production_refresh.py` | 关系全量重抽取随库执行（位于阶段 1/2 写 cleaned **之后**、下游消费者 **之前**）；不加 `--report`，报告仍由阶段 6.8 单一写入 |
| **`gate_relations` 新增判据 8「产物新鲜度」** | `gates/gate_relations.py` | 产物**不得早于其数据面输入**（五源 cleaned 最新 JSONL / `internal_policy_index.json` / `processed/*_fulltext.json` / 归属表 CSV）→ 漏跑即 FAIL，不再静默 |

- **范围纪律**：新鲜度只纳入**由阶段 0~2 或链条外操作**推进的输入；阶段 3~6 的产物
  （drift/recall/merged_view/reports/published/交付库）**不写这些文件** → **不会自造 FAIL**。
- **已知取舍（偏严）**：归属表仅"时效状态"列变化也会触发；代价为一次 `relations gen`（~32s，已在链内）。
- **实测生效**：接入后本机**立即检出 6 项陈旧输入**（归属表 + 五源 cleaned）→ 重抽取后 **gates 16/16 PASS**。
