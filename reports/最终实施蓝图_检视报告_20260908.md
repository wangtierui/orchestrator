## 二、单一事实源（SSOT）检视

### P0-1　明细表存在双生成器，蓝图未裁定 SSOT 生成器
- 现状事实：明细表既有 `regulatory_classifier/scripts/build_detail_tables.py`（`FIELDS` 10 列被现行 Gate4 引用），又有 `regulatory_classifier/theme_analysis/node2_rebuild/build_detail_tables_v2.py`（历史 v2 语义，命名计数 `T{n}_{m}`），两份都可写 `data/` 下 11 份明细表（T0_9/T1_195…）。
- 蓝图问题：§4 SSOT 表只写"明细表 11 csv｜唯一写者 build_detail_tables_SSOT"，未裁定 `_SSOT` 指哪一个、是否删除另一个。若不裁定，P4 迁移会把**两份生成器**同时复制进 `modules/regulatory_classifier/scripts/`，双写复现。
- 证据：`scripts/build_detail_tables.py`（现行 Gate4 引用 FIELDS）vs `theme_analysis/node2_rebuild/build_detail_tables_v2.py`（明细计数命名）；`run_retrieval_after_checks.py:445` 引用 `scripts/build_detail_tables.FIELDS`。
- 修订：R1：裁定 **scripts/build_detail_tables.py 为唯一 SSOT**（Gate4 已依赖其 FIELDS）；node2 v2 脚本不迁入（留旧仓），其在 report_builders 中的引用改为调用 SSOT 版。

### P0-2　主题归属表存在 3 个写入者，蓝图未收敛

### P0-3　效力状态存在双路直写归属表，SSOT=verification_state 未闭环

- 修订：R3：新仓**只保留一条传播链**：`timeliness verify(s) → mark_checked(唯一写位) → orchestrator timeliness sync`；`classifier_pkulaw_verify` 的归属表直写与五源回写逻辑抽为 sync 链路的内部步骤（不独立直写）；diff_timeliness 降级为只读比对+报告，不写归属表（或经接口写）。gate_timeliness_ssot 检测非编排路径对归属表时效列的裸写即 FAIL。

## 四、全链路自动化检视

### P0-6　自动化频率语义冲突（每周二 01:00 vs 每日 06:00 vs nfra weekly）
- 蓝图 §5 触发调度写"每周二 01:00：collect→clean→index→retrieval→classify→report"；但同时 nfra weekly_refresh 是**周二 01:00**、五源周二 prompt 也是 01:00——同一时刻多源与 nfra 编排并发由 fs_lock 串行？未定义整链上"哪些命令在 weekly、哪些在 daily、哪些在 timeliness 后"的**频率归属表**；若每周二同时跑五源 collect + nfra weekly，nfra weekly 内部 run_rebuild 又会触发数据变化，造成同批重复。
- 修订：R11：定义**调度矩阵**（见下），并在 orchestrator 内实现"命令级互斥锁（fs_lock）"，同一数据根同时只有一个 pipeline 写者；nfra_weekly 作为 `collect --source nfra --weekly` 子命令存在，不再独立时钟。

调度矩阵（建议）：
| 时间 | 命令 | 说明 |
|---|---|---|
| 周二 01:00 | `collect` 五源 + nfra_weekly | 采集仅此批 |
| 周二 02:00 | `clean --project all` → `index --refresh` | 紧接采集后 |
| 每日 06:00 | `retrieval`（签名幂等）→ `classify`（签名幂等） | 消费最新 cleaned |
| timeliness verify 完成后 | `timeliness sync`（自动）→ 受影响层重建 | 事件驱动 |
| internal 制度发布后 | `internal scan/align`（事件触发） | 事件驱动 |
| 交付前/提交前 | `gates` + pre-commit | 手动+自动 |

### P1-5　retrieval 四门禁与 orchestrator gates 的关系未界定
- 现状：`run_retrieval_after_checks.py` 四门禁（clean/validity/contract/schema）是 classifier 内部数据重跑门禁；orchestrator gates 是交付门禁，二者名似实异。
- 修订：R12：文档界定：**数据门禁**（retrieval 前，校验"能否安全重跑"）vs **交付门禁**（gates，校验"全仓质量"）；gates 不重复跑 retrieval 四门禁数据校验，但保留 hardcoded/lint/契约扫描交集；避免将来"两道门禁语义混乱"。

### P1-6　timeliness verify 对北大法宝 CLI 的失败/超时路径未定义
- 现状：核验依赖 `std_lib/scraper_std/pkulaw_cli.py`（外部工具），checkpoint jsonl 续跑存在；verify_missing 分源聚焦。
- 修订：R13：`timeliness verify` 增加三态：全部成功/部分成功(续跑)/外部不可用(降级置 needs_review 不误标)；每次运行写 reports/核验执行摘要（成功数/复用数/降级数），供告警通道。

### P1-7　C1 自动刷新后对下游报告/明细的联动刷新未定义
- Q2 允许 C1 自动刷归属表标题/文号 → 会影响 recall 的 in_808 判定、明细表标题、报告引用、drafter 六件套条款对照。
- 修订：R14：C1 自动刷新写 audit + 标记受影响层 `needs_rebuild={base, detail, report_builders...}`；由 orchestrator 在下次对应命令签名检测时重建；`gate_rfn_drift` 中 C1 记录不应再报 FAIL（闭环条件：已刷+已传播）。
