# 一、internal_policy_base 完整运行流程

## 1.1 模块构成（5 个脚本，全部 IPB 独立维护）

| 脚本 | 职责（docstring 实证） | 输入 → 输出 |
|---|---|---|
| `scan.py` | 源目录扫描与文件名解构（**零正文解读**） | 制度源目录 → 文件级元数据清单（ipn=md5(文号\|标题)[:16]、docno、title、sha256、size） |
| `extract.py` | 文本抽取与正文规范化 | 原文件 → 规范化正文（normalize_text：控制字符剔除/页眉页脚水印行/空白合并）+ 抽取状态 |
| `indexer.py` | 摄取索引（**幂等**，sha256 游标） | scan+extract 编排 → `data/originals/<rel>` 原件副本 + `data/processed/<ipn>.json` 结构化 + `internal_policy_index.json` 主索引 + `_ingest_state.json` 摄取游标 |
| `align.py` | 制度 × 监管主题（T0–T10）对齐 | 主索引 → `align_result.json`（primary/secondary themes；无命中 → UNALIGNED 桶，R18 只增不删） |
| `merged.py` | merged_view 生成（schema v1.0 冻结） | 主索引 + 归属表（RFN） → `merged_view.json`（861 条：ipn/title/docno/primary_theme/associated_rfns[] + 血缘签名） |

**命令编排**（`commands/internal.py`）：`internal index/align/merged/backfill/reocr/refine-identity`；入链方式 = `triggers.yaml` 的 `internal_update` 触发项（normalize_internal_naming --apply → internal index --only-unindexed → internal align → internal reocr）与 `inbox_drop`（inbox_scan → index --only-unindexed → align）。

## 1.2 与 regulatory_scrapers 共享的脚本/能力（实证：IPB 无任何对 scrapers 包内的直接 import，共享全部经 std_lib 公共库与 interfaces）

| `governance_store` | `std_lib/common_lib/governance_store.py` | `align.py`/`indexer.py` import | 摄取/对齐登记（旁路观测） |

## 1.3 IPB 独立维护的部分（5/5 全部独立）与独立原因

**scan/extract/indexer/align/merged 五个脚本均为 IPB 独有**（scrapers 无对应物）。独立原因与功能边界：

| 维度 | 外部监管域（scrapers） | 内部制度域（IPB） | 结论 |
|---|---|---|---|
| 数据源 | 五源官网网络采集 | 本地文件投放（inbox/人工目录） | 采集逻辑不可共享 |
| 编号体系 | RFN（监管文件号，classifier 权威） | **IPN（独立空间，D-03）** | 主数据不可共享 |
| 更新模式 | 爬虫增量 + 时效核验 | 投放区 new_and_unhashed_only + 摄取游标 | 幂等机制不可共享 |
| 质量要求 | 校验失败隔离 | 原件只读 + 作证备查 + 身份纠正（refine-identity） | 治理语义不可共享 |
| 共享边界 | **底层能力**（抽取/结构/归一/治理/契约）共享，**业务逻辑**（扫描/摄取/对齐/合并）独立 | | |

**结论**：IPB 的独立性是领域驱动的正确设计——与 `gate_no_cross_module_import` 纪律（唯一同仓互引 = classifier→clean_index）完全一致；IPB 全部经 std_lib 公共库 + interfaces/rfn_api 访问 scrapers/classifier 侧数据，**零越权**。

# 二、data/corpus 文件夹设计意图

## 2.1 定位：语料归集本体（审计层）——三层语料架构的中心层

依据 `paths.py:41-47`（v2 §3.12 决策 D-9）、`tools/ingest_corpus.py` docstring、`config/inbox_registry.yaml`：

```
① 投放区   data/inbox/<domain>/        投放/暂存入口（writable=false，不是数据层）
② 归集本体 data/corpus/<domain>/       ★ 只读审计层：sha256 内容去重后的物理归集
③ 归集清单 reports/corpus/<domain>.manifest.json   入库可审计入口（data/ 不入 git）
```

**实测**（2026-10-13）：`data/corpus/dept_policies/`（995 文件）、`data/corpus/regulatory_stats/`（312 文件）；`reports/corpus/` 有 `_index.json` + 两域 manifest（源路径 + 每文件 sha256/大小 + 目标域 + 时间）。

## 2.2 存储的数据类型与交互关系

| 交互方 | 关系（实证） |
|---|---|
| `tools/inbox_scan.py` | 投放区唯一读者：按 inbox_registry 路由，`new_and_unhashed_only`（sha256 命中 corpus 本体或 originals 一律记 duplicate 跳过——防「经 inode 写穿 originals」的自指环）；不可识别扩展名 → worklist（corpus_needs_review），不静默丢弃 |
| `tools/ingest_corpus.py` | 归集入口（--src --domain）：先建 manifest → 物理归集 → 幂等增量（sha256 相同跳过）；`exclude_tops` 顶层目录精确剪枝（EAST 素材的 00.报送文档/核查手册/需求文档等整棵排除） |
| `internal_policy_base/data/originals` | **跨层硬链接**（`tools/dedupe_original_storage.py` 实证）：corpus/dept_policies（A，306MB）与 originals（B，349MB）内容高度重合（A 的 967 个业务文档 B 中全有）；B 中「内容在 A 唯一存在」者替换为指向 A 的硬链接（同卷 NTFS `os.link`），**两路径同 inode、均可用，释放 306MB**；语义警示：修改任一路径影响另一处（原件只读场景可接受），A 被删除/移动不影响 B（inode 引用计数） |
| `regulatory_classifier` recall | corpus 语料支撑召回审计（ingest_corpus.py:31-35 注释：该层「同时服务 classifier 的 recall 与 IPB 的跨层硬链接去重」——这正是 v2 D-9 把它从 `modules/regulatory_scrapers/data/corpus/` **迁到仓根 data/corpus/** 的原因：归属不当 + 迁移必须同卷 rename 保 811 个硬链接） |
| `regulatory_stats` 域 | EAST2.0 素材层（312 文件）；「真法规」子集经 build_east_backlog → supp（见第三章）；consumer 现为 pending_consumer（不假装已消费） |

## 2.3 设立该文件夹解决的问题

1. **外部语料无统一归集口**：EAST2.0/部门制度/保单登记等「未归集数据域」此前散落各处的问题（F-L05）；
2. **双份存储**：corpus 与 IPB originals 内容重合 967 文件的物理双份（306MB+349MB）——以硬链接去重（dedupe_original_storage ②）；
3. **归档可审计性**：manifest 入库（清单是唯一可审计入口，语料本体不入库）+ sha256 幂等 + duplicate 登记；
4. **域→消费者显式声明**：每个域必须声明 consumer/pipeline，`pending_consumer` 是合法但被披露的状态（判据 V 守护，「有产出无消费」不允许静默）。

# 三、EAST2.0 摄取路径归属

**结论：两条路径并存，职责互补——结构化入链走 supp 模块（主路径），素材归档走独立归集脚本（审计层）。**

## 3.1 路径 A：supp 模块入链（结构化 → 主链）

```
EAST 素材目录（金非银检函〔2025〕82号，13 文件）
  → tools/build_east_backlog.py（独立脚本，人工按需）
      pdf→body_text（pypdf→pymupdf 双轨；扫描件降级为可核验元数据声明）
      docx→正文；xlsx×6→table_structured 结构化轨（openpyxl，MAX_XLSX_ROWS=4000）
      jpg(E-R)→rich_object 轨（docs_root("supp")/diagrams/）；.et(WPS)→登记不可解
      → tools/_east_backlog.json（--out 可改）
  → modules/regulatory_scrapers/collectors/supp_ingest_batch.py --backlog（supp 模块入口）
      合并进 supplementary_regulations.jsonl（按发文字号/标题去重，保留既有 F9~F17 记录）
  → run_clean_pipeline --project supp → cleaned 双轨 → clauses/relations/published 主链下游
```

- **触发条件**：① `build_east_backlog.py` 人工按需执行（素材目录更新时，--dir 传入，禁盘符字面量）；② 链上 `supp:ingest_batch` 步骤（`--supp-batch <backlog.json>` 显式触发；backlog 为空 → SKIP rc=0——「不假装自动」，supp 为表格类人工批次）；
- **实证**：`supplementary_regulations.jsonl:60` = task_index=EAST-20250410-01 记录（12 件附件表格结构化）；
- **附件补充**：`supp_ingest_local_dir.py --task-index EAST-20250410-01 --doc-number "金非银检函〔2025〕82号"`（本地目录附件实体归集 + xls/xlsx 的 excel_classified_v2 重建 table_structured；**只更新附件字段/表格结构，不新增记录、不改正文**）。

## 3.2 路径 B：独立脚本归集（素材全量 → corpus 审计层）

```
data/inbox/regulatory_stats/（人工投放 312 文件）
  → inbox_scan（inbox_drop 条件触发：inbox_has_new）
  → ingest_corpus --domain regulatory_stats
  → data/corpus/regulatory_stats/ + reports/corpus/regulatory_stats.manifest.json
  ╘═「真法规」子集（inbox_registry.yaml supp_eligible_subset：include glob
      「*/关于修订…通知/*.pdf」+ exclude_tops 排除 00.报送文档/核查手册/立项申请/需求文档/邮件宣导/相关法规）
      → 交路径 A 的 build_east_backlog 消费（「仅真法规子集经 build_east_backlog → supp」）
```

- **触发条件**：投放区有新文件（inbox_has_new 条件判定）；归集层 `consumer=pending_consumer`（内控要求/规则来源尚未接入——判据 V 持续披露）；
- **场景边界**：报送文档/核查手册/需求文档/邮件宣导等非法规素材**只归档不进主链**（路径 B 的职责）；「真法规」子集才走路径 A 结构化。

## 3.3 两条路径的适用场景与触发条件对照

| 维度 | 路径 A（supp 入链） | 路径 B（corpus 归集） |
|---|---|---|
| 数据范围 | 「真法规」正文 + 表格结构化（EAST 1 条记录 + 12 附件） | 素材全量 312 文件（含报送文档/手册等） |
| 产物 | cleaned 双轨 → 主链下游（clauses/relations/published/分析） | corpus 本体 + manifest（只读审计层） |
| 执行方 | `supp_ingest_batch.py`（supp 模块）+ `build_east_backlog.py`（独立生成器） | `inbox_scan.py` + `ingest_corpus.py`（独立工具） |
| 触发 | 人工 build_east_backlog → `--supp-batch` 显式入链；supp_ingest 触发项 explicit_arg | inbox_drop 条件触发（投放区有新文件） |
| 消费者 | 全链 | pending_consumer（→ W3 改 reg_frameworks） |

**遗留形态说明**：`supp_ingest.py`（手写 4 份保险销售行为主题）是早期手工录入形态（纸面 collector，无执行路径）；`supp_ingest_local_dir.py` 是附件实体补登记入口——三者与路径 A 的关系见《项目最优重构方案》§7.2.1 处置矩阵。

# 四、三项排查对本次重构的方案落点

## 4.1 IPB 共享关系 → 显式化「抽取 SSOT」契约（落入 W4）

- **事实**：`crawler_common.extract_document_text` 是全仓多格式抽取的唯一实现，IPB `extract.py` 是其第二大消费方（仅次于 scrapers 的 `pipeline.py`）——但这一「SSOT 地位」目前只存在于 docstring，无契约登记、无门禁。
- **落点**：① `contract_manifest.json` 新增 `extract_entrypoint` 契约条目（file=std_lib/scraper_std/crawler_common.py，symbol=extract_document_text，consumer=[pipeline, internal_policy_base.extract, docreader_bridge 回退路径]），`gate_contract` 自动断言；② W4 拆分 crawler_common（1234 行）时，**IPB extract 是 import 面契约测试的必须覆盖方**（§7.9 L3）；③ 在 `interfaces/contract.py` 或模块 docstring 写明「6 态抽取语义（extract_status 受控值）全仓一致」——IPB 与 scrapers 的抽取状态口径不得分化。

## 4.2 corpus 定位 → ADR-0007 补记 + 保留策略硬化（落入 W4）

- **落点**：① ADR-0007（产物分级）补一节「corpus = L-a 事实源的审计副本层」：只读、硬链接目标、manifest 为唯一可审计入口；② **retention/.tmp sweeper 的删除类策略必须显式排除硬链接语义误伤**（删 corpus 侧不影响 originals——inode 计数；但「唯一副本在 corpus、originals 是硬链接」时删 corpus 侧同样安全，而删 originals 侧非硬链接的唯一副本危险）——retention POLICY 新增 `corpus_no_delete` 纪律 + `gate_hardcoded_paths` 已有盘符守卫不变；③ `dedupe_original_storage.py`/`reconcile_original_paths.py` 补 independent 登记并入运行手册（§7.2 登记 8 个之一，实际为 tools 16 个已有登记——两者已有 independent ✓，仅需入 runbook）；④ corpus 与 IPB originals 的 inode 一致性列为 `gate_original_resolvable` 的既有职责（已覆盖），不重复造判据。

## 4.3 EAST 双路径 → reg_frameworks 参数化 + 死常量清理（落入 W3/W0）

- **落点 1（W3）**：`build_east_backlog.py` 现为「单一通知硬编码」（docstring 自述「工作②实战」）——W3 的 `reg_frameworks.extract` 应将其**参数化为 framework 驱动**的通用抽取器（输入 = Framework/DataTable 声明 + 素材目录，输出 = DataTable/DataItem + ClauseItemMap），EAST 成为第一个 framework 实例而非特例；`supp_eligible_subset` 的 include/exclude_tops 规则随 Framework 声明迁移（inbox_registry 的域配置引用 framework id）。
- **落点 2（W3）**：regulatory_stats 域 consumer 从 `pending_consumer` → `reg_frameworks`（判据 V 的 pending 披露随之关闭）；素材全量仍只归档（路径 B 语义不变），结构化只产「真法规」子集（路径 A 语义不变）。
- **落点 3（W0，第 7 章 C 类新增 C8）**：`supp_ingest_batch.py:48` 的 `RAW_PATH` 常量仍指向 `supplementary_regulations.json`（批 49 JSONL 化前的旧名）——实际读写已走 `resolve_raw_path` 双格式解析（:62-65/:120-122 实证），该常量是**迁移遗留死引用**（与 `_raw_size` 同类）：修正为 `resolve_raw_path(RAW_PATH)` 单一事实源或直接删除常量，消除「常量说 .json、实际写 .jsonl」的漂移。
