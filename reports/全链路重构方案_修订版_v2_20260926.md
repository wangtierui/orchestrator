**问题 A1：`std_lib → config` 的依赖方向未在纪律中声明。**

# 第 3 章 修订后的重构方案

## 3.0 设计原则与口径

**P1 分层（显式 DAG，单向）**

```
paths ← config ← std_lib ← interfaces ← {gates, commands, tools}
                     ↑           ↑
                  modules ───────┘（modules 只依赖 std_lib/config/interfaces）
```

**P2 唯一事实源**：任何"清单"只允许一份常量定义，其余位置派生或由门禁断言一致。适用范围：模块清单、阶段清单、契约列头/键集、受控枚举、退出码、门禁清单、触发项清单、调度清单。

**P3 失败必须显式**：要么中断（非零退出码 + 结构化原因），要么**计数并落元数据**。禁止"catch → pass → 继续当成功"。

**P6 变更可回滚**：每期任务给出「验收判据 + 回滚动作」，且**不得**以"临时目录不入库"为名制造新的门禁盲区。

## 3.3 元数据与水位整改（对应 §2.2、原方案 D1/D2）

### 3.3.1 水位表加「轮次」，一次性解决原方案的缺陷 1 与缺陷 2

原方案的两处"缺陷"根源相同：**水位只有版本，没有"是否同一轮推进"的语义**。方案：

```sql
-- _SCHEMA_INT: 2 → 3（第二次迁移 3 → 4 见 §3.14.3，新增 worklist 表）
ALTER TABLE watermark ADD COLUMN round TEXT NOT NULL DEFAULT '';        -- 登记时的 run_id
ALTER TABLE watermark ADD COLUMN stage TEXT NOT NULL DEFAULT '';        -- 登记阶段（如 "2.55"/"3"/"6.8"）
```
`dependency_edges()`（`governance_store.py:476-502`）的判定改为三态+：
- 上游 `version` 一致 → `ok`；
- 上游 `version` 不同 **但** 上游 `round == 下游 round` → `ok_within_round`（**同轮推进不算 stale**）；
- 上游 `version` 不同且 `round` 不同 → `stale`（真陈旧）；
- 上游未登记 → `unregistered`（不阻断）。

收益：
- `analysis:manifest`（阶段 6.8 生成、门禁在阶段 6）可安全声明 `inputs=["cleaned:{src}","relations_index"]` 而不恒 FAIL——因为同轮推进被识别为 `ok_within_round`；
- `clauses:{src}` 可声明 `inputs=["cleaned:{src}"]`，阶段 2 的双轨回写不再导致阶段 1 版本"作废"；
- 观察型键从 6 个减到 0，`check_dependencies` 覆盖面完整；
- `gate_watermark` 判据升级为「`stale` 阻断、`unregistered` 披露、`ok_within_round` 记录」。

### 3.14.1 审计方法
