## 1. 结论

**不能开箱稳定运行。** 分三档判定：

| 档位 | 判定 | 依据 |
| :--- | :--- | :--- |
| **代码骨架** | ✅ 可运行 | `cli.py ping` / `source list` 在克隆副本正常（8/14 门禁通过），入口 CWD 无关 |
| **代码全链** | ❌ 不可运行 | 6/14 门禁 FAIL、11/217 用例失败；核心链路依赖的 `data/`、`published/`、`external/`、`tessdata/` 全部不入库 |
| **异机可移植性** | ❌ **存在"假通过"污染** | 受版本控制的 `clean_index/index.json` 内嵌 31 处本机绝对路径，导致克隆副本在**本机**读取的是**原仓数据**（详见 CP-02） |

**最关键的一条**：本报告最危险的问题不是"克隆后跑不起来"，而是**克隆后看起来跑起来了**——因为 `clean_index/index.json` 把 `get_clean_index()` 重定向到 `D:/WorkBuddy/regulatory_compliance_orchestrator/...` 的原始数据。这使得：

- `cli.py timeliness verify` 在**完全无数据**的克隆副本上输出 `cleaned 1939 条 … overall: success`；
- `tests/test_e2e_pipeline.py::test_clean_index_five_sources_latest` 在克隆副本上**通过**。

**这两条成功结果在另一台电脑上必然反转**，因此当前所有"克隆可运行"的验证结论都不具备跨机迁移性。

## 2. 风险清单

严重度口径：**阻断** = 核心链路不可用；**高** = 特定命令不可用或结果不可信；**中** = 需人工干预才能达到文档承诺；**低** = 体验/维护性。

### A. 依赖管理

#### CP-A01 [高] `[ocr]` extra 承载了"非 OCR 刚需"的 PDF 文本层库

**现象**：文档推荐的安装命令是 `pip install -e ".[dev]"`（README:270），但 PDF 文本层抽取所依赖的 `pypdf` / `pdfplumber` **只声明在 `[ocr]` extra 中**（pyproject.toml:31-37），base `dependencies` 无这两个包。

**根因**：`std_lib/scraper_std/crawler_common.py:349-382` 的 `_extract_pdf()` 先用 `pypdf`、回退 `pdfplumber`，两库皆缺时返回：

```380:382:std_lib/scraper_std/crawler_common.py
    if not _pdf_lib_available():
        return {"text": "", "extracted": False, "extract_status": "library_missing",
                "needs_ocr": False}
```

**影响**：`cli.py internal index`（内部制度摄取）是本仓核心链路，其 PDF 会**全部产出空正文**，且 `extract_status="library_missing"` 是**静默状态**、不抛异常、不被 gates 拦截 → 制度底座"看似建成功、实则正文为空"。

**复现**：
```bash
# 全新虚拟环境
python -m pip install -e ".[dev]"
python -c "import pypdf"        # ModuleNotFoundError
python cli.py internal index --source-dir <含 PDF 的制度目录>
# → 记录 extract_status=library_missing，text 为空
```

**建议**：把 `pypdf` / `pdfplumber` 从 `[ocr]` 上移到 base `dependencies`（它们不是 OCR 组件，是 PDF **文本层**解析组件）；`[ocr]` 只保留 `paddleocr` / `paddlex[ocr]` / `PyMuPDF`。

#### CP-A02 [高] `modules/` 不在 setuptools 打包清单 → 非可编辑安装缺全部业务代码

**证据**：`pyproject.toml:42-53` 的 `packages` 仅含 `std_lib / config / interfaces / gates / commands`，`modules/*`（本仓约 70% 业务实现）**完全缺失**。

#### CP-D02 [阻断] ⭐ `clean_index/index.json` 被入库且内嵌本机绝对路径 → "假通过"

**这是本次检视的核心发现。**

**事实**：`modules/regulatory_scrapers/clean_index/index.json` **受版本控制**（`git ls-files` 确认），内容含 **31 处** `D:/WorkBuddy/regulatory_compliance_orchestrator/modules/regulatory_scrapers/...` 绝对路径：

```json
{
  "generated_at": "2026-09-13T16:22:54+0800",
  "scraper_root": "D:/WorkBuddy/regulatory_compliance_orchestrator/modules/regulatory_scrapers",
  "sources": {
    "nfra": {
      "latest": {
        "csv": "D:/WorkBuddy/regulatory_compliance_orchestrator/modules/regulatory_scrapers/data/cleaned/nfra_cleaned_20260912.csv",
        "record_count": 1939
```

**根因**：`get_clean_index()` **只要 `index.json` 存在就直接加载，不校验内嵌路径是否有效、不校验 `scraper_root` 是否指向当前仓库**：

```407:412:modules/regulatory_scrapers/clean_index/__init__.py
    if not rebuild and os.path.exists(INDEX_PATH) and scraper_root == SCRAPER_ROOT:
        if "idx" in _cache:
            return _cache["idx"]
        with open(INDEX_PATH, encoding="utf-8") as f:
            _cache["idx"] = CleanIndex(json.load(f))
        return _cache["idx"]
```

（类内虽有 `is_fresh()` / 类似校验方法在 376-385 行做 `os.path.exists` 检查，但 `get_clean_index()` 的**加载路径不调用它**。）

**实测污染证据**（在**克隆副本**目录内执行，读到的却是**原仓**文件）：
```
$ python -c "...get_clean_index(); [print(s, idx.latest_date(s), idx.record_count(s), os.path.exists(idx.latest_csv_path(s))) ...]"
gov  20260912 605  True
mof  20260912 870  True
nfra 20260912 1939 True
pbc  20260912 571  True
supp 20260912 58   True
```

**连锁假通过**：
1. `cli.py timeliness verify` 在**零数据**的克隆副本上输出：
   `[verify_missing:nfra] cleaned 1939 条 | 效力缺失（空）0 条` … `overall: success`
2. `tests/test_e2e_pipeline.py::test_clean_index_five_sources_latest` 在克隆副本上**通过**（该测试用 `os.path.exists()` 判定"五源快照是否就位"，而路径指向原仓）。

**异机后果预测（分叉行为）**：
- 该测试**必然失败**；
- `verify_missing.py:73-74` 有 `FileNotFoundError` 保护 → 降级 `unavailable`（安全）；
- 但**其他 `clean_index` 消费者未加保护**（`recall_audit/*`、`classify_themes`、`build_detail_tables` 等经 `find_cleaned()` 取路径直读）→ 异机为未捕获异常或空集，行为不确定。

**门禁为何没拦住**：`gate_hardcoded_paths` 只扫 `*.py`（见 CP-B02 代码引用）→ 该 JSON 的 31 处盘符字面量**不在扫描范围**，克隆副本上该门禁仍报 `count=0`。这正是"**门禁全绿 ≠ 可移植**"的机制性根因。

**建议（最高优先级）**：
1. 将 `clean_index/index.json` 移出 git（加入 `.gitignore`），改为运行时 `rebuild_index()` 生成；
2. `get_clean_index()` 增加**路径有效性 + `scraper_root` 归属校验**，失效则自动 `rebuild_index()`；
3. `gate_hardcoded_paths` 扫描范围扩展到 `*.json` / `*.yaml` / `*.csv`（至少含 `*.json`）。

### F. 版本兼容性

#### CP-F01 [中] Paddle 生态宽区间 + 代码写死 3.x 具体参数

#### CP-F02 [中] `disable_mkldnn` 是针对特定 paddlepaddle 版本的 workaround，但该包未被声明


**`paddlepaddle` 本身不在任何 dependency / extra 中**（本机由 pip 单独安装，实测 `paddlex 3.7.2` 在位而 `paddleocr` 缺失）。异机按 `.[ocr]` 安装时，`paddlepaddle` 版本由 `paddlex` 传递解析决定 → 可能落在未修复/已修复的不同行为区间，导致"仍崩"或"白关加速"。

#### CP-F03 [中] `requires-python = ">=3.13"`

### G. 跨平台差异

#### CP-G01 [高] 旧版 `.doc` 抽取强依赖 Windows COM（WPS / pywin32）

```552:553:std_lib/scraper_std/crawler_common.py
        import win32com.client
        app = win32com.client.Dispatch("KWPS.Application")
```

- `win32com`（pywin32）**不在任何 dependency/extra 中**——属隐式系统级依赖；
- 备选路径为 LibreOffice（`std_lib/scraper_std/doc_convert.py:48`，经 `LO_BIN` 环境变量）；
- 而 `.doc` 是本仓主力格式之一（工作区含 **1,545 个 `.doc`** 文件）。

**跨平台后果**：Linux/macOS 上无 WPS → `win32com` 不可用（惰性导入，返回 `None`，**不抛异常**），必须依赖 LibreOffice；若 LibreOffice 未装，`.doc` 会大面积降级为 `extract_status` 非 ok，**且不报错**。这与 CP-A01 同属"静默能力缺失"模式。

#### CP-G02 [中] 进程存活判定存在平台分支，POSIX 分支未在本仓验证

`std_lib/common_lib/fs_lock.py:71` 使用 `os.name == "nt"` + `ctypes.windll.kernel32.OpenProcess`。POSIX 分支的语义（进程存活判定正确性）在 Windows 开发环境下**无测试覆盖**。

#### CP-G03 [中] 无 `.gitattributes` + 103 个受版本控制的中文文件名

- 实测 `git -c core.quotepath=false ls-files` 含 **103 个**非 ASCII 文件名（`docs/reports/*.md`、`modules/*/docs/*.md` 等）；
- 仓库**无 `.gitattributes`**（`Test-Path .gitattributes` → `False`）；
- 在 `LANG=C` / 非 UTF-8 locale 的 Linux 上，这些路径的显示与检出行为未被验证（Windows/macOS 下实测正常）。

#### CP-G04 [中] 无 `.gitattributes` → 换行符差异，影响字节级哈希场景

无 `.gitattributes` 意味着 Windows 上 `core.autocrlf=true` 会把文本文件检出为 CRLF。Python 运行无碍，但本仓存在多处**字节级/哈希级**比对（`clean_index._sha256_file`、`analysis` 的 `_manifest.json` sha 登记、发布件 sha）。相关哈希对象主要是**数据文件**（不入库，不受 autocrlf 影响），故当前风险有限；但属需在异机实测确认的项。

#### CP-G05 [正面] 控制台编码处理到位

- `cli.py:66-70` 强制 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`；
- `tools/run_production_refresh.py:70` 为子进程设 `PYTHONIOENCODING=utf-8`；
- `.devcontainer` 设 `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`；
- 路径拼接统一 `os.path.join`，无手工分隔符（克隆副本 `source list` / `gates` / `ping` 输出中文无乱码）。

#### CP-G06 [低] `.gitignore` 通配过宽，存在未来埋雷

- `data/`（无路径限定）：任何层级名为 `data` 的目录都被忽略（本仓这正是 CP-D01 的成因之一，同时也是"仅靠命名约定保护数据"的脆弱点）；
- `*.pdf` / `*.doc` / `*.docx`（无路径限定）：未来若需入库**样例文档/模板**会静默失效；
- `*_token*`：见 CP-D04。
