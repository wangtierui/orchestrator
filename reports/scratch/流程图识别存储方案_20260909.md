# 监管/制度文件「流程图」识别与存储 —— 现状断言与最优方案（2026-09-09）

## 1. 现状（取证结论）

两条链（regulatory_scrapers 五源 / internal_policy_base 107 制度）对 SmartArt、
自选图形、文本框（DrawingML/OLE）、Excel 内嵌形状、PDF 矢量/扫描示意图：

| 环节 | 现状 | 证据 |
|---|---|---|
| 文本抽取层 | 只取 `w:p→w:t`（docx 段落）、单元格（xlsx）、PDF 文本层+整页 OCR | crawler_common.py:375/410/315；全仓 **0** 处引用 `w:drawing/a:txBody/txbxContent/dgm` |
| 富文档（EAST） | E-R 图等**仅登记**"图像附件非文本不抽取"，status=registered | build_east_backlog.py:190-191 |
| 结构层 | 仅章-条正则，无图形感知 | document_structure.py:94 / clause_index |

断点层级：**文本抽取层**（无 shapes/SmartArt/drawing 解析）+ **存储层无 diagram 轨**。

## 2. 目标数据模型（新增「diagram 轨」，与 table_structured 同构一致）

raw / processed 记录增加（**JSONL/行内为主，CSV 39 列与 processed 元数据零破坏**）：

```jsonc
"diagram_structured": [
  {"index": 1, "kind": "smartart|textbox|shape|ole|image|page",
   "caption": "图1-业务流程图",          // 就近图题（w:caption 或相邻段落）
   "text": "受理→审核→…（形状内文字合并，| 分隔）",
   "image_path": "data/docs/<src>/diagrams/<record>/图1.png"}   // 抽取出的位图
],
"diagram_text": "图1-业务流程图 受理→审核→…",   // 检索轨（供 recall/主题/后续图谱）
"diagram_count": 2
```

## 3. 分层能力档位

### M1 · 内嵌文本+图像抽取（推荐先落地，低破坏、全链受益）
- 共享 `std_lib/scraper_std/diagram_extract.py`（仿 `table_recovery.structured_table_fields` 样板）：
  - `docx`：解析 DrawingML 文本（`a:txBody/a:t`、`w:txbxContent/w:t`）按 shape 收集；python-docx `inline_shapes`；图片从 `word/media` 提出落盘
  - `xlsx`：`xl/drawings/drawing*.xml` 的 `a:t`（文本框/图形文字）+ `xl/media` 图片
  - `doc`：经已有 `doc_convert`（LibreOffice 已装）doc→docx 后复用 docx 路径
  - 统一出口 `diagram_fields(data, name) → {diagram_structured, diagram_text, diagram_count}`（无图形返回空，不破坏既有无图记录）
- 接入：五源附件/正文解析点（gov_fetch_attachments / mof / nfra_fetch_attachments / pbc / supp_ingest+build_east_backlog）；`internal_policy_base/extract`（processed 增 diagrams + `<ipn>_diagrams.json` + images/ 目录）
- 存储：raw/processed 行内 JSON + 图像统一 `data/docs/<src>/diagrams/<record>/`；`map_*` 与 internal PROCESSED_FIELDS 透传收口；contract 登记 diagram_* 轨（如 CLAUSE/表格轨先例）
- 检索：`diagram_text` 并入 recall 的正文拼接收口（一行），供主题/召回命中图形文字

### M2 · 结构语义（进阶）
- 流程形状关系还原（节点/连线）：docx SmartArt/显式连接线难全自动；对 **OLE-Visio(.vsd)** 建议 LibreOffice `.vsd→pdf` 渲染 + 图 OCR（visio 原生解析无成熟开源库，不引入）
- 输出节点列表 {label} 供后续 process 图谱/制度画像（二期，不阻塞 M1）

### M3 · 图像型流程图兜底（PDF 扫描/位图）
- fitz 按页渲染→**区域级 OCR**（整页 OCR 文字并入 diagram_text 已可；进一步按图像块定位存 region text），图片落盘；诚实标注"图形示意（OCR 文本，无结构还原）"，不臆造语义

## 4. 推荐路径（最优组合）

1. **先 M1 落地**（docx/doc/xlsx 内嵌图形文字+图像抽取 → diagram 轨 → 全链透传/检索），一次打通 5 源 + internal 107；与既有 `structured_table_fields` 完全同构，可平行交付与回归测试
2. **并接 M3**（PDF/图片页区域 OCR）补齐扫描类示意，图像统一落 `data/docs/…/diagrams/`
3. M2（流程图拓扑关系）留二期，具备文字+图像底稿后按需演进
4. 消费端：recall 正文拼接口并入 `diagram_text`；主题匹配可带图形文字；internal 富文档视图（draft_clause）图按相对路径可嵌入；`gate_contract`/provenance 类门禁补充 diagram 轨契约断言（沿用 detail/table 先例，量小）

## 5. 工作量与风险
- 改动面：新增 1 共享模块 + 各源 6 处接入点 + map/契约收口 + internal extract；无 schema CSV 变化、无 DB 迁移
- 风险：DrawingML 结构多样（SmartArt 变体/旧 VML）→ 以"尽力抽取 + 图随附件原件"兜底；图形文字噪声（标注箭头 "×/√"）→ text 用分隔拼、不参与条文语义
- 验证：构造含 SmartArt/文本框 docx 样本单测 + 用现仓真实含图 docx（internal originals / mof 附件 528 .doc）冒烟

## 6. 决策点
- A. 是否按"先 M1"启动实施（推荐）
- B. M1+M3 一起做（图型扫描兜底）
- C. 仅先落 1 个试点（如 internal_policy_base）验证质量后再铺 5 源
