## 三、S-A：raw 主库 JSONL 化（已完成 + 等价性证明）

### 3.1 设计与边界

| 面 | 变更 |
|---|---|
| **格式** | `data/raw/gov_laws.jsonl`：**首行 `_meta` 信封**（source/category/captured_at/format）＋其后**一行一记录**（`json.dumps` 转义换行 ⇒ 严格一行一记录） |
| **写入** | `gov_parse.write_outputs` 改流式写（`.tmp` + `os.replace` 原子）；记录数**不入 `_meta`**（单遍写入无法先知总数）⇒ 计数由**旁路索引** `gov_laws.index.json` 的 `count` 承载 |
| **读取** | `pipeline.load_raw_records` **双格式均流式**：`.jsonl` 逐行（跳 `_meta`）/ `.json` 用 `raw_decode` **逐条**（不整表）——**五源同时降峰值**（mof/nfra 各 117MB 亦受益） |
| **兼容** | `_find_master`：JSONL 优先、旧 `.json` 回退；`MasterView`/`load_raw_records`/`raw_loader` 三处读取侧均已双格式支持 ⇒ **迁移期不中断** |
| **口径同步** | `RAW_JSON["gov"]`、`clean.RAW_MASTER_NAMES`、`raw_loader.RAW_FILES`、`build_migration_manifest` 四处名映射 + 4 处活文档串 + 手册 2 行 |

### 3.2 迁移与**等价性证明**（先证后删）

| 步骤 | 结果 |
|---|---|
| ① 流式读旧 `.json` | **13178 条** / 滚动 sha（逐条规范化序列化）= `f784c6e89ed8b9ba` / 167.7s / 1034.8MB |
| ② 流式写 JSONL | 149.2s → **943.6MB**（比旧文件小 **9%**：无缩进） |
| ③ 重读校验 | 13178 条（跳过信封 1 行）/ 滚动 sha **完全一致** ⇒ ① 条数一致 ✓ ② 逐条内容一致 ✓ |
| ④ 替换 | 删除旧 `gov_laws.json`（等价成立后）✓ |

> **口径**：等价判据为"**逐条规范化序列化（`sort_keys=True`）的滚动 sha256**"，非仅计数——可发现任何字段级差异。

## 四、S-B / S-D / S-E 处置

| 编号 | 处置 | 证据 |
|---|---|---|
| **S-B** | 新增 `gov_parse.merge_and_write`：**旧主库逐条读 → 同键用新记录覆盖 → 逐条写** `.tmp`（峰值＝新记录+键集，与主库体积解耦）；`gov_collector` 的 resume 路径改走它 | 单测 `test_merge_and_write_matches_merge_with_master`（与整表合并**逐键等价**）+ **真机幂等**（上表） |
| **S-D** | ① `retention.apply_plan` 增 **`delete: true`** 支持（计划/台账/`--json` 全保留，只把执行动作由 move 改 remove）；② POLICY 新增 **`logs_stale`**（`keep_days 14`，delete）；③ 目录型快照**不**加 POLICY 条目（见下"为何"） ；④ 执行回收 | 实测：**logs 643.5MB → 5.3MB**（删 555 项）+ 归档 143 项（`archive/` 67.5MB）+ 历史隔离件随 `clean_quarantine_stale` 一并归档 ✓ |
| **S-E** | `_backup_keep()`：保留数可经环境变量 **`SCRAPERS_BACKUP_KEEP`** 覆盖（默认 1；连续异常回写场景可临时调 2，代价 ≈2GB/组），无需改码重发 | `_cleanup_backups(keep=None)` 取该值并在日志写明来源 ✓ |

> **为何目录型快照不做 retention 条目**（重要，保留以免复发）：`retention._plan_dir` 的分组只能按**名字**正则；而快照的"源"信息在**目录内容**（`{src}_cleaned_*`）⇒ 按 tag 分组会在同一次运行内误删**本批先建的 gov 快照**（批 46 两次 dry-run 实测暴露的同一陷阱）。故目录型快照由**写入侧上限**（N-197，按 (tag,源) 分组保留 1 份）作唯一权威控制 ✓ 工具侧若要支持，需新增"按目录内容二级分组"能力（已登记）。

## 五、S-C 处置：**勘误**（批 46 的"疑重复存储"假设**不成立**）

| 判据 | 实测 |
|---|---|
| 两字段体积 | `attachments` 139.5MB（10 条，其 `text` 合计 69.0MB）vs 记录级 `attachment_content` 137.4MB |
| **内容比对** | 记录级 sha `3039ebb8…` **≠** 附件 text 拼接 sha `17a5b031…` ⇒ **非重复**，各自独立 |
| 来源 | `pipeline.py:320-321`：记录级 `attachment_content` = 源附件内容 **＋ 追加**富文本（`" [富内容] " + _rt`）⇒ 组合体，非副本 |
| 消费方 | 记录级 `attachment_content` **无下游消费者**（仅该 mapper 自身写入；`contract.attachment_view` 读的是 `rec["attachments"]`） |

**结论与处置**：
1. **勘误**批 46 的"疑重复（137MB）"判断 —— **不成立**（已按证据撤销；队列项判为 `dismissed`）。
2. 真因是"**单条记录合法承载 277MB 附件/富文本**"（10 个附件，其中含巨型表格类文档）。
3. 内存侧放大已由 S-A/S-B **解除**（流式不再整表/重复载入）；**数据侧保持不动**（去重/截断/外置都属改契约与交付口径，需产品决策）⇒ 保留登记（"单记录体积治理"）并写明可行方向：附件原文**阈值+外置**（既有机制 `attachment_content_path`+md5 已在**附件级**存在 ✓ 可扩展到记录级聚合字段）。
