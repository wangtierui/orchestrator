## 一、逐项评估

### ① 分句分词 —— 主张成立，但**漏了第二处实现**（口径二重风险）

**方案主张**：`sentence_split.py` 是"纯正则四级流程，无语义边界识别"。

**代码事实**：✅ **准确**。`std_lib/scraper_std/sentence_split.py`（171 行）实测四级：
`① 标签语义`（`_BLOCK_TAGS`/`_END_TAGS`）→ `② 中文标点`（`_SENT_END`/`_COMMA`）→
`③ 中英文粘连`（`_CN_EN`/`_EN_CN`）→ `④ 兜底连词`（`_FALLBACK_CONJ`），另有
`_LONG_NO_PUNCT` 31 字无标点兜底。链路末端 `pipeline.py:107-108` 调用
`repair_text(cleaned, source="webpage")` → 方案 1.3 点名的 `_clean_record_body`（`pipeline.py:87`）**存在** ✅。

**⚠️ 方案未识别的关键细节（风险点）**：仓内存在**第二套分句实现**
`std_lib/common_lib/relations.py:280 split_sentences()`：
```python
parts = re.split(r"(?<=[。．.；;！!？?])\s*", text)   # 单条正则，无标签/粘连/兜底
```
它是**关系抽取的输入分句**。方案只增强 `sentence_split.py` → 结果是
**同一批正文有两个分句口径**（清洗层走 ML，抽取层仍走单正则），
既不符合"唯一事实源"，也会让第 ④ 项（关系抽取）的增强**被上游分句口径抵消**。

**缺失细节**：❌ 未说明 `sentence_split_ml.py` 的**产物形态**（是 `body_text` 写回还是旁路字段？）。
现有约束是 **`repair_text` 的产物不回写 `body_text`**（`pipeline.py:94` 明文注释：它按"断句"目标插入句末 `\n`）
→ 若 ML 层改成写回，会**改变下游 `body_text` 语义**并可能触发 `gate_clean_schema`/`schema_validation` 相关判据。

**判定**：**可行**（增强层 + 降级链符合本仓风格），但**必须先统一 `relations.split_sentences`**，
否则是"两个分句器"而非"一个更准的分句器"。

### ② 条文结构解析 —— 🔴 **主张与代码事实不符（该项已实现）**

**方案主张**：`document_structure.py` 的 `extract_structure` 是"纯正则，**无法区分'第 X 条'作条文号 vs 作引用**"，
引入 HanLP/LTP 依存句法作为"增强点：识别'第 X 条'作条文号 vs 作引用"。

**代码事实**：❌ **该能力已存在且实现得相当细**（`std_lib/scraper_std/document_structure.py`，**1542 行**）：

| 既有机制 | 位置 | 作用 |
|---|---|---|
| `_prev_allows_head(text, i, kind)` | `:192` | 判定「第X章/条」是**真结构首**还是**内嵌引用**；采用**否定清单**（① 连接性标点 `、，；：` 后的「第X条」几乎必是交叉引用 ② …），并要求前文为句末标点或章标题 |
| `segment_body(body)` | `:215` | **内嵌引用不断行**（文档串明示：`本法第五十三条、第五十四条规定的行为` 保持同条正文） |
| `_heading_shaped` / `_law_title_side_ok` | `:284`/`:296` | 切分候选的形态合法性（长度/两侧内容） |
| `resplit_embedded_anchors(text, kind)` | `:333` | 二次切分的**否证规则**：标记后紧接 `项/款/目/条/章/节/个/是/、/，` → 判为内联引用，**不切**；law 模式额外要求章行以章标记开头（条行内「第五章」必是引用） |
| `parse_score` / `is_fallback` | 全仓引用 | 解析**质量分**与**降级标记**（门禁可判别低质解析） |
| `CLAUSE_ISSUE_SEVERITY` / `CLAUSE_PARSE_MODES` | `config/enums.py` | 相关**受控值闭包**（有 assert） |
| 纪律"**禁止臆造标识**" | 文档串 `:40` | 拒绝把某系统重标条号（"下游会据此生成不存在的条号引用"） |

**结论**：方案把**已实现的能力**列为"缺口"（`:35-40`、`:192-208`、`:333-356` 是完整的引用/条文号判别体系）。
真正**未被覆盖**的只有**"但书"结构**——全文件检索 `但书` **零命中**（✅ 这一半主张成立）。

**风险点**：若照方案"引入 HanLP 重做条文边界识别"，将与上述 1542 行既有逻辑**并列存在**，
产生**两套条号切分**；且 ML 切分若与既有 `parse_score`/`is_fallback`/受控值不同步，
`clause_index` → `base_publish.external_clauses` → `gate_clean_schema`（条文契约自检）
会直接报键集/条号形态不一致。

**判定**：**需修正主张** → 建议改为"在既有 `_prev_allows_head` 否定清单机制上**补但书识别**"
（可由正则局部扩展实现，**零新依赖**），而非整体替换为依存句法。

### ⑦ 文档解析 —— 🔴 **主张含事实错误（状态取值误述；OCR 通路已存在）**

**方案主张**：`extract_document_text` "仅做文本层提取，无版面分析、无多模态处理。
**扫描件 PDF 直接标记 `library_missing`**"；7.3 提出渲染为 JPEG 后"**新增** OCR 补充"。

**代码事实**：❌ **两处与代码不符**。`std_lib/scraper_std/crawler_common.py`（985 行）：

1. **`extract_status` 是 6 态受控取值**（`:282-284` 文档串明文）：
   `ok | empty | needs_ocr（扫描件PDF无文本层） | library_missing（依赖缺失） | unsupported | corrupt`
   → **扫描件是 `needs_ocr`**，而 `library_missing` 专指**依赖缺失**（`:12` 注释：
   "缺失第三方库时标记 extract_status='library_missing'，不静默丢弃"）。
   方案把两者混为一谈 → **误述**（且该区分正是 2026-09-13 CP-A01 修复的成果：
   README 只装 `.[dev]` 时缺 pypdf/pdfplumber 会**静默**返回 `library_missing` → 空正文）。
2. **已有 OCR 通路**：`extract_document_text(..., enable_ocr: bool = False, ocr_timeout: int = 60)`
   （`:269-274`）+ 返回 `needs_ocr` 信号 + `garble_ratio` + `_extract_pdf(data, enable_ocr, ocr_timeout)`
   （`:401`）；`std_lib/scraper_std/ocr_engine.py`（**629 行**）为 OCR 后端，`pyproject` 的
   `[ocr]` extra 已声明 `paddleocr>=3.0,<4` + `paddlex[ocr]>=3.0,<4`；`pipeline.py:134 _ocr_correct_record()` 已接。

**结论**：真实缺口是 **"版面分析/多模态解析"**（docreader 的合理定位 ✅），
而**不是**"无 OCR 通路"。方案 7.3 的"渲染 JPEG → **新增** OCR"属**重复建设**。

**风险点**：docreader 是 **Docker + gRPC（端口 50051）** 的独立服务 →
与项目"**单机零服务依赖**"现状冲突（见 §二-4 可移植性）。

**判定**：**需修正主张 + 重新论证部署形态**。

方案只覆盖外部 → 内部检索将保持"无语义"，形成**能力不对等**且违背 SSOT 精神。

**🔴 架构冲突（方案未论证）**：ParadeDB = PostgreSQL 17 + pgvector + BM25，Docker 部署；
另有 **Redis** 作"异步解析队列"。而本仓当前**零外部服务**：SQLite 单文件发布件
（`base_publish` 的 `manifest`/契约 `Base Contract v1`）+ 已入库的
**《克隆可移植性检视报告》**（`reports/…20260913.md`，CP-A01 即其产物）明确关注"克隆后可运行性"。
引入 PG/Redis 会使：① 克隆后不可运行（须起两个容器）② `gate_watermark`/`gate_provenance`
的"产物即文件"语义需重定义 ③ `pyproject` 依赖与 `[ocr]`/`[dev]` extra 体系需重构。

**判定**：**P3 可行但需前置架构论证**；`build_fts.py` 作为**降级路径保留**是正确设计 ✅。
建议先做**零服务**的语义检索替代（如 SQLite + 本地向量表 / 单文件向量索引），
把 ParadeDB 降级为"仅大规模部署时可选"，并明确 `search_internal` 也须覆盖。

## 三、方案**最大的不完善：零评测方案**（🔴 阻塞级）

8 项全部是"引入语义增强"，但方案**通篇无**：
- 标注集 / 金标准（无 ground truth → 无法算 P/R/F1）
- 基线对比（现有正则的准确率/召回率**从未测量**，则"增强后更好"不可证）
- 阈值标定依据（第⑤项直接给 0.75，无来源）
- 回归口径（新增模块**不得降低**既有指标 → 无护栏）
- 模型指纹入 provenance（**可复现性**，见下）

**与既有纪律的直接冲突**：本仓的断点幂等靠 `input_sha`（`classify_state.json`）、
产物新鲜度靠 `gate_watermark`、来源靠 `gate_provenance`。
ML 输出受**模型版本/权重/torch 版本/CPU-GPU** 影响 → **同一输入可能产出不同产物**，
使"断点跳过"与"水位判据"**语义失真**（会误判"内容未变"或反复重建）。
方案未提"模型指纹（名称+版本+权重 sha）须写入产物 provenance 并纳入 inputs 指纹"。

## 五、结论

1. **方案的点名是准的**（20 个被点名文件/函数**全部存在**，`_clean_record_body`、`themes`、`extract_structure` 等均属实），
   说明撰写者确实看过代码。
2. **但 8 项主张中有 2 项与实现不符**（第②项"无法区分条文号 vs 引用"→ 已实现 1542 行的成套判别机制；
   第⑦项"扫描件标 `library_missing`"→ 实为 `needs_ocr`，且 OCR 通路已存在），
   **1 项链条错位**（第③项把上游事实源"主题归属表"当作产物）。
3. **直接冲突 3 处**（可验证会 FAIL）：`config.enums.REF_MATCH_METHOD` 的 `len==2` 断言、
   `tools/_manifest.json` 的 J1 双向相等、`gate_clean_schema` 对隔离记录的"需人工清理"明文。
4. **最需要补的是评测与可复现性**（标注集/基线/阈值标定/模型指纹入 provenance）——
   缺此则 8 项增强**无法验收**，且会干扰 `input_sha` 断点幂等与 `gate_watermark` 判据。
5. **建议**：先落地 §四 中**零依赖**的三项（分句口径统一、清洗注册表+度量入链、评测基线），
   把"引入模型"整体后移一个批次；对第②/③/⑦ 项**先更正方案文本再实施**。
