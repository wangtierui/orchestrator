# Worklist 推送与回传方案评估报告

- 评估日期：2026-10-13
- 评估对象：将 worklist（人工确认队列）推送至 Microsoft To Do / 企业微信待办、处理完成后回传状态的方案，及替代方案对比
- 前置输入：《目录体系与worklist闭环审查_20261013.md》确立的现状缺口（无结构化选项、resolved_by 恒空、无业务回写、无处置后验证、无每选项理由模板）
- 事实基线：全部基于本仓代码实测 + 本机网络实测，推测处均标注「待人工确认」

---

## 0. 结论（先行）

| 层次 | 推荐 | 定位 |
|---|---|---|
| **主确认界面** | **自建本地 Web 确认台**（读 governance.db worklist 表，局域网访问） | 唯一能完整承载「结构化选项 + 理由模板 + 影响面 + resolved_by + 业务回写 + 处置后验证」六要素的方案；零数据出境、零外部 API 限制 |
| **移动通知层** | **企业微信自建应用消息**（降级态：只读卡片，引导至控制台） | 复用现有 notify 旁路设施纪律（`common_lib/notify.py`），secret 走环境变量；让待办「找得到人」 |
| **移动确认层（可选 P2）** | 企业微信**按钮交互型模板卡片** + 常驻轻量回调服务 | 若回调 URL 可达性可行则升级；userid 天然回填 resolved_by，近实时回传 |
| **Microsoft To Do** | 仅作**可选个人镜像**，不作主通道 | delegated-only 令牌、无变更 webhook、无共享列表、字段贫乏，无法承载结构化决策 |
| **不推荐** | Zapier / Power Automate 云端版、邮件解析回传、日历事件 | 数据出境合规红线 / 回传脆弱 / 语义不符 |

核心理由：**本项目的确认动作不是「完成/未完成」二元勾选，而是带选项、理由、影响面的合规决策**（confirm/reject/defer/escalate + 业务回写）。To Do 类待办应用的数据模型（title/body/dueDate/status）表达不了这个决策，硬套会把治理语义降级为任务勾选。待办平台适合做「提醒与触达」，不适合做「决策界面」。

## 1. 评估基线：本项目的事实约束

| 约束 | 事实与证据 | 对选型的约束 |
|---|---|---|
| 部署形态 | 单台 Windows 机器；Windows 任务计划「唤醒即跑、跑完即退」（实测 7/7 任务 Ready）；无 Docker（semantic_tools.json:400-403） | 任何需要**常驻监听**的方案（回调服务）都是对既有形态的增量破坏，须单独评估 |
| 零外部依赖纪律 | `notify.py:12-14`：默认 file 告警，webhook 可选且 URL **只从 env `REG_ORCH_NOTIFY_WEBHOOK` 读取、禁止入库**；`notify.py:14-16` 告警失败一律降级、绝不中断主链 | 新通道必须继承「旁路设施」纪律：密钥不入库、失败可降级、不阻断主链 |
| 密钥纪律 | 全仓无 vault 文件；`PGVECTOR_DSN`、webhook URL 均 env 注入，`gate_secret_scan` 守护（semantic_tools.json:167） | 企业微信 secret / MSAL refresh token 均需新增「env 注入 + 扫描守护」位，不得落库 |
| 网络出口 | 2026-10-13 实测：`qyapi.weixin.qq.com` gettoken **HTTP 200**；`graph.microsoft.com` **401**（免鉴权拒启，服务可用）；`login.microsoftonline.com` **200**。⚠️ 但 mirrors 实测中 gitee/modelscope/aliendao/hf 官方等**大量站点被重置**（semantic_tools.json:10）→ 出口有过滤，但两平台 API **均未被阻断** | 网络不再是阻塞项（此前最大未知已排除）；但出口过滤存在，需把连通性做成可复跑探测（参照 `tools/check_mirrors.py --probe` 模式） |
| 数据敏感度 | worklist payload 含法规原文片段、内部制度对齐证据、时效核验冲突明细 | **数据可见范围与数据出境是硬约束**——云端自动化工具（Zapier 等）出局 |
| 决策语义 | 闭环审查确立：确认 = 选 option + 填理由 + 看影响面 + 系统回写业务表 | 平台数据模型必须能表达「多选一决策 + 自由文本理由」，而非完成态 |
| 身份缺口 | `resolved_by` 参数存在但 CLI 调用未传（commands/worklist.py:53）→ 恒空 | 回传通道最好自带用户身份（企业微信 userid 天然具备） |

## 2. 候选方案能力明细

### A. Microsoft To Do（Microsoft Graph）

| 维度 | 明细 |
|---|---|
| 接口能力 | `POST/GET/PATCH /me/todo/lists/{id}/tasks`；字段仅 title / body / dueDate / categories / importance / status（notStarted/completed/cancelled）；JSON batch ≤20 请求 |
| 推送实时性 | 即时（写 API 同步返回） |
| **回传实时性** | **无 webhook**：Graph change notifications **不支持 todo 资源**（订阅覆盖 mail/calendar/contacts 等，不含 todo）→ 只能 **delta 轮询**（每 5~15 分钟一次），非实时 |
| 权限模型 | **仅 delegated**（无 application 权限）→ 后台服务必须为**每个操作员**各持一份 refresh token（MSAL public client + token cache 落盘）→ 令牌管理复杂度高，且 token cache 本身成为新秘密形态 |
| 多用户/共享 | 产品层有列表共享但 **API 共享支持有限**；任务归属即列表 owner，「谁完成的」最多追溯到列表 owner，无法精确到操作人 |
| 中国访问 | 实测 401 可达；但企业租户若由中国大陆 21Vianet 运营则端点与全球版不同，需按租户实际确认 |
| 结构化表达 | body 塞 JSON 可行但不可操作；状态只有 completed/cancelled 两态 → **confirm/reject/defer/escalate 四选一表达不了** |

### B. 企业微信（自建应用）

两条技术路线：

**B1. 应用消息 + 按钮交互型模板卡片（有回传）**
- 推送：自建应用发模板卡片（`text/notice` 型或按钮交互型），支持 markdown 正文 + 按钮；
- 回传：用户点「确认 / 驳回」→ 企业微信服务器把点击事件（**含 userid**）POST 到应用配置的**回调 URL**（带 EncodingAESKey 加解密、Token 校验）；
- 实时性：近实时（秒级）；
- 硬前提：**回调 URL 必须被 qyapi.weixin.qq.com 可达**（公网 IP+域名，或内网穿透）→ 需要一台**常驻回调服务** → 与「唤醒即跑即退」形态冲突，是该方案的主要成本；
- 权限：自建应用 secret + **可见范围**（精准控制哪些成员收到/可操作）+ 可信 IP 配置；secret 仍走 env；
- 附带收益：**userid 自动回填 resolved_by**，直接补上身份缺口。

**B2. 应用消息只读通知（无回传，降级态）**
- 只发 markdown 摘要卡片（item_id + kind + subject + 建议 + 控制台链接），确认动作仍回本地控制台；
- 无常驻服务、无公网依赖，完全契合现有部署形态；代价是移动端只能看不能办。

> 「企业微信待办」产品功能本身的开放 API 支持有限（公开 API 主要覆盖消息、日程、通讯录、应用管理）——**以待办 API 官方文档最新能力为准（待人工确认）**；上表按「应用消息 + 模板卡片」这一成熟开放能力评估。

### C. 邮件（SMTP / Exchange）

- 推送：正文带 item_id 与结构化摘要（可复用 notify 的 md 渲染）；即时；
- 回传：① 回复邮件解析（主题/正文约定格式，脆弱：引用、转发、签名会破坏解析）；② 内网链接点击（需内网可达）；③ 最稳的是「邮件只通知、确认回控制台」；
- 优势：零新基础设施、任何企业都有；劣势：实时性低、结构化差、移动端操作链路长、审计需另建（收件箱≠工单）。

### D. 日历事件（ICS / Exchange 日程）

- 语义上只适合「有明确截止时间的待办」（dueDate 天然存在）；但 worklist 多数条目无 deadline，且「完成日历事件 ≠ 完成业务确认」；逐条建事件会污染日历。**不推荐作主通道**；可作为 aged 提醒的辅助形态。

### E. 自建待办系统（本地/局域网 Web 确认台）

- 数据源现成：`data/governance.db` 的 worklist 表 + 9 个产生方语义 + kind 分类；
- 界面：FastAPI/Flask + 少量静态页（项目已有大量报告页/状态页生成经验，技术风险低）；
- 可完整实现闭环审查 §2.5 的五环：结构化选项（受控值）、每选项理由模板与影响面、`--by` 身份（登录或局域网信任 + 操作人名输入）、kind→action 业务回写、处置后验证；
- 部署：随需启动（`cli.py worklist serve`）或常驻服务均可，**不依赖任何公网/外部 API**；
- 认证深度按操作员规模定（内网单团队可用简认证；多角色再上 AD/SSO——待人工确认组织形态）。

### F. 第三方自动化工具

| 工具 | 评估 |
|---|---|
| Power Automate | 连自定义 API 需 premium connector + M365 许可；中国区可用性与数据流向微软云；把已闭环的逻辑搬到低代码平台反而偏离 SSOT（trigger/逻辑双处维护）。**不推荐** |
| Zapier / IFTTT / Make | 数据流经境外云 → **监管合规数据出境，合规红线，直接出局** |
| n8n 自托管 | 数据不出境且可控，但引入 Node 生态又一常驻服务；本项目逻辑用 Python 表达更直接，维护两份栈不划算。仅当未来自动化流程远超 worklist 场景才考虑 |

## 4. 风险与待确认项（不猜测）

1. **回调 URL 可达性**：企业微信回调要求 qyapi 服务器能访问到本机端点——本机是否有公网 IP/域名或已批准的内网穿透通道？**待人工确认**（若否，则 B 方案锁死在只读通知态，确认必须落在自建控制台）。
2. **常驻服务的运维许可**：单机「唤醒即跑即退」形态下新增常驻进程（回调服务或 Web 控制台）是否被运维接受？**待人工确认**。
3. **企业微信「待办」开放 API 最新能力**：若官方已提供完整待办 API，可替代模板卡片路线。**待人工确认**（以官方文档为准）。
4. **操作员规模与角色**：几人处理 worklist、是否按 kind 分岗（timeliness_conflict→时效岗、internal_identity_conflict→制度岗）？决定控制台认证深度与路由表设计。**待人工确认**。
5. **M365 租户是否存在**：决定 To Do 是否值得做个人镜像。**待人工确认**。
6. **出口过滤的长期稳定性**：本次实测两平台 API 可达，但 mirrors 实测显示出口在动态过滤；上线前应把 `qyapi/graph/login` 三个端点纳入可复跑探测（仿 `tools/check_mirrors.py --probe` 的「真实请求而非首页打开」方法），失败即按旁路纪律降级为 file 告警。

## 5. 推荐选型与实施路线

### 5.1 选型结论

**主通道 = 自建本地 Web 确认台；通知通道 = 企业微信应用消息（先只读、后按钮）；To Do 仅作可选个人镜像。** 决策逻辑：

1. 确认动作的六要素（结构化选项、理由模板、影响面、身份、业务回写、验证）只有自建系统能完整承载——这是闭环审查已确立的需求，不是 UI 偏好问题；
2. 待办平台（To Do/企微待办）的价值在「提醒与触达」，放在通知层正好，且企业微信实测可用、境内团队习惯匹配；
3. 零外部依赖、密钥 env 化、失败降级——新通道完全继承 `notify.py:12-16` 的既有纪律，不破坏克隆可移植性；
4. 数据不出内网，守住监管合规数据的可见范围红线。

### 5.2 分阶段路线

| 阶段 | 内容 | 前置条件 |
|---|---|---|
| P0（已完成） | CLI `worklist list/resolve` + aged 告警落 `reports/_alerts/`（notify.py 现有四事件） | 无 |
| P1（核心，建议立即启动） | ① worklist 结构化：`--option` 受控选项 + `--by` 必填 + `deferred` 状态 + `worklist show`（影响面+选项菜单）；② 本地 Web 确认台（读 governance.db，served 局域网）实现六要素 + kind→action 业务回写 + 处置后验证 | 组织侧确认操作员与岗位分工（§4-4） |
| P2（按条件） | 企业微信自建应用：先上**只读卡片通知**（新 notify kind=wecom，secret 走 env，探测+降级）；回调基础设施批准后升级**按钮卡片 → 常驻轻量回调服务 → userid 回填 resolved_by** | §4-1/§4-2 确认；端点连通性纳入 doctor |
| 可选 | M365 租户存在且需要 Outlook 联动时，加 To Do 个人镜像（delta 轮询回传 completed 态，仅同步不决策） | §4-5 确认 |

### 5.3 各方案适用边界（速查）

- **自建控制台**：决策发生地。凡「改业务数据」的确认都必须在这里完成。
- **企业微信只读卡片**：提醒层。让待办在 IM 里被看到，附 item 摘要与控制台链接。
- **企业微信按钮回调**：便捷确认层。仅当回调可达且运维接受常驻服务时启用；confirm/dismiss 级简单决策可移动端办，defer/escalate 仍引导回控制台。
- **MS To Do 个人镜像**：个人工作清单同步，不承担回传与决策。
- **邮件**：兜底告警通道（notify kind=mail），与既有 file/webhook 并列。
- **日历/云端自动化**：不采用（语义不符/数据出境）。
